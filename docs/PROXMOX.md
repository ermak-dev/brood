# Proxmox VE

Агенты brood живут в контейнерах Proxmox VE. Этот документ для
администратора, который подключает узел Proxmox к серверу brood: что brood
делает на гипервизоре, какие права ему нужны, как устроен контейнер агента
и что проверять, когда агент не поднимается.

Слова, которые нужны дальше:

 - **Контейнер** (CT) — непривилегированный LXC-контейнер Proxmox с полным
   Debian и systemd внутри.
 - **Подключение** — адрес API Proxmox, токен и место размещения: узел, пул
   ресурсов, хранилище, сетевой мост, базовый шаблон.
 - **Пул** brood — активированное подключение с бюджетом ёмкости. Агенты
   размещаются в пулах.
 - **Пул ресурсов** — объект самого Proxmox (Datacenter → Permissions →
   Pools). brood кладёт в него свои контейнеры и работает только с ними.

Общая модель объектов описана в [MODEL.md](MODEL.md), запуск сервера — в
[DEPLOY.md](DEPLOY.md).

## Что brood делает на гипервизоре

Сервер ходит только в HTTPS API Proxmox с одним токеном. На узел он по SSH
не заходит и ничего на нём не устанавливает.

Через API сервер:

 - создаёт контейнер из шаблона или связанным клоном образа проекта;
 - запускает, останавливает и удаляет свои контейнеры;
 - превращает сборочный контейнер в шаблон (образ проекта);
 - меняет клону число ядер и объём памяти;
 - читает конфигурацию, состояние, адреса контейнера и состояние своих задач.

Чего сервер не делает никогда:

 - не трогает контейнер, который не прошёл проверку владения (раздел
   «Отметка владения»);
 - не включает привилегированный режим, точки монтирования, проброс устройств,
   hook-скрипты и сырые параметры `lxc.*`;
 - не настраивает сеть, хранилища и брандмауэр узла;
 - не следует HTTP-перенаправлениям и не отключает проверку сертификата API;
 - не повторяет запись, исход которой неизвестен (раздел «Жизненный цикл»).

В контейнер сервер заходит по SSH напрямую, минуя гипервизор: API Proxmox не
умеет выполнять команды внутри контейнера.

## Подготовка узла

Команды выполняются на узле Proxmox от root. Имена `brood`, `local-lvm`,
`vmbr0` и `pve` — примеры; подставьте свои.

### Пул ресурсов, пользователь и токен

```sh
pveum pool add brood --comment "brood agents"
pveum user add brood@pve --comment "brood server"
pveum user token add brood@pve brood --privsep 0
```

Последняя команда печатает секрет токена один раз. Идентификатор токена для
формы подключения — `brood@pve!brood`. С `--privsep 0` токен действует с
правами пользователя, поэтому права ниже выдаются пользователю.

### Роли и права

```sh
pveum role add BroodGuests --privs "VM.Allocate VM.Clone VM.Audit VM.PowerMgmt VM.Config.CPU VM.Config.Memory VM.Config.Disk VM.Config.Network VM.Config.Options Pool.Audit"
pveum role add BroodStorage --privs "Datastore.AllocateSpace Datastore.Audit"
pveum role add BroodTemplates --privs "Datastore.Audit"
pveum role add BroodNetwork --privs "SDN.Use"

pveum acl modify /pool/brood --users brood@pve --roles BroodGuests
pveum acl modify /storage/local-lvm --users brood@pve --roles BroodStorage
pveum acl modify /storage/local --users brood@pve --roles BroodTemplates
pveum acl modify /sdn/zones/localnetwork/vmbr0 --users brood@pve --roles BroodNetwork
```

`/storage/local-lvm` — хранилище дисков контейнеров, `/storage/local` —
хранилище, где лежит файл шаблона. Права на `/pool/brood` действуют на
контейнеры, которые в этом пуле состоят; к остальным гостям узла у токена
доступа нет.

Какой вызов API какого права требует:

| Действие brood | Вызов API | Право и путь |
| --- | --- | --- |
| Подобрать свободный VMID | `GET /cluster/nextid` | любой вошедший пользователь |
| Создать контейнер из шаблона | `POST /nodes/{node}/lxc` | `VM.Allocate` на `/pool/{pool}`; `Datastore.AllocateSpace` на хранилище дисков; `Datastore.Audit` на хранилище шаблона; `SDN.Use` на мост; `VM.Config.Disk`, `VM.Config.CPU`, `VM.Config.Memory`, `VM.Config.Network`, `VM.Config.Options` для параметров контейнера |
| Связанный клон образа | `POST /nodes/{node}/lxc/{vmid}/clone` | `VM.Clone` на образ, `VM.Allocate` на `/pool/{pool}`, `Datastore.AllocateSpace`, `SDN.Use` |
| Превратить в шаблон | `POST /nodes/{node}/lxc/{vmid}/template` | `VM.Allocate` |
| Задать клону ядра и память | `PUT /nodes/{node}/lxc/{vmid}/config` | `VM.Config.CPU`, `VM.Config.Memory` |
| Запуск, остановка, выключение | `POST /nodes/{node}/lxc/{vmid}/status/start`, `.../stop`, `.../shutdown` | `VM.PowerMgmt` |
| Удалить контейнер | `DELETE /nodes/{node}/lxc/{vmid}` | `VM.Allocate` |
| Конфигурация, состояние, адреса | `GET .../config`, `GET .../status/current`, `GET .../interfaces` | `VM.Audit` |
| Состав пула ресурсов | `GET /pools?poolid={pool}&type=lxc` | `Pool.Audit` на `/pool/{pool}` |
| Состояние задачи | `GET /nodes/{node}/tasks/{upid}/status` | задачи токена видны ему самому |

При создании контейнер получает `unprivileged=1`, `features=nesting=1`
(без вложенности systemd в непривилегированном контейнере не работает),
`swap=0`, `start=0`, один интерфейс `net0` с `ip=dhcp` и открытый SSH-ключ
установки в параметре `ssh-public-keys`. Proxmox разрешает `nesting=1` для
непривилегированного контейнера обладателю `VM.Allocate`; другие значения
`features` brood не задаёт.

### Сеть

Контейнер получает адрес по DHCP на мосту подключения, поэтому в сети моста
должен работать DHCP-сервер. Кроме этого нужны два направления:

 - сервер brood должен достигать адресов контейнеров по TCP 22: так он
   устанавливает агента и собирает образы;
 - контейнеры должны достигать публичного адреса сервера
   (`BROOD_PUBLIC_ORIGIN`) по HTTPS: оттуда агент скачивает свои программы и
   туда же держит постоянное соединение.

Контейнеру также нужен выход в интернет: при установке он скачивает
терминальный сервер ttyd с GitHub и пакеты Debian из репозиториев
дистрибутива. brood сеть агента не ограничивает; ограничения, если они
нужны, задаёт администратор сети.

### Базовый шаблон

Базовый шаблон — штатный шаблон Debian 12 из каталога Proxmox:

```sh
pveam update
pveam available --section system | grep debian-12-standard
pveam download local debian-12-standard_12.7-1_amd64.tar.zst
pveam list local
sha256sum /var/lib/vz/template/cache/debian-12-standard_12.7-1_amd64.tar.zst
```

Имя файла берите из вывода `pveam available`: версия со временем меняется.
В форму подключения идут идентификатор тома из `pveam list`
(`local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst`) и сумма SHA-256
файла. Сумму сервер хранит как часть описания пула и сам файл не
пересчитывает.

Дорабатывать шаблон не нужно: всё, чего в нём не хватает, агент ставит сам
при первом старте.

## Подключение и пул

Подключения и пулы видит и меняет только администратор, на странице «Пулы»
панели. Поля формы «Добавить подключение»:

| Поле формы | Поле API | Значение |
| --- | --- | --- |
| Имя | `name` | строчные латинские буквы, цифры и дефисы, не длиннее 48 знаков |
| Адрес API | `endpoint` | HTTPS-адрес без пути, например `https://pve.example.com:8006` |
| ID токена | `tokenID` | `user@realm!token`, например `brood@pve!brood` |
| Секрет токена | `tokenSecret` | после сохранения не показывается и не возвращается API |
| Сертификат CA | `caPEM` | сертификат, которым подписан TLS-сертификат API, текстом PEM; на узле это `/etc/pve/pve-root-ca.pem` |
| Узел | `node` | имя узла, например `pve` |
| Пул ресурсов | `resourcePool` | `brood` |
| Хранилище | `storage` | хранилище дисков контейнеров, например `local-lvm` |
| Сетевой мост | `network` | например `vmbr0` |
| Базовый шаблон | `template` | `local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst` |
| Дайджест шаблона | `templateDigest` | `sha256:` и 64 шестнадцатеричных знака |
| Агенты, CPU, память, диск | `capacity` | бюджет пула, см. ниже |

Сертификат CA обязателен: проверку сертификата API отключить нельзя.

Ёмкость задаётся на всех агентов вместе: число агентов, ядра, память и диск.
Панель переводит её в формат API:

```json
{"actors": 4, "cpuMillicores": "8000", "memoryBytes": "17179869184", "diskGiB": 80}
```

`cpuMillicores` и `memoryBytes` — десятичные строки. Бюджет делится между
агентами поровну с округлением вниз до целых ядер, мебибайт и гибибайт: в
примере каждый агент получает 2 ядра, 4 ГиБ памяти и 20 ГиБ диска. Доля
должна быть не меньше одного ядра, 16 МиБ памяти и 1 ГиБ диска.

Подключение хранится в базе сервера. Изменить его нельзя: чтобы сменить
шаблон или ёмкость, создайте новое подключение и удалите старое.

Действия над пулом:

| Действие | Что происходит |
| --- | --- |
| Активировать | Создаёт пул с ёмкостью подключения. Нужны шаблон, ёмкость и настройки сервера `BROOD_PUBLIC_ORIGIN` и `BROOD_PROXMOX_RELAY_SECRET` |
| Вывести (drain) | Новые агенты в пуле не размещаются, остановленные не запускаются и не пересоздаются; работающие продолжают работать, остановка и удаление доступны |
| Включить (enable) | Возвращает выведенный пул в работу |
| Деактивировать | Удаляет пул. Отказ, пока в пуле есть агенты |
| Удалить подключение | Удаляет подключение и секрет токена. Отказ, пока пул активирован |

Вывести и включить пул можно и из командной строки: `bro pools`,
`bro pool drain NAME`, `bro pool enable NAME` ([CLI.md](CLI.md)).

## Отметка владения

Каждый контейнер, созданный brood, несёт в описании отметку:

```
brood-owned:v1:{"poolUID":"...","actorUID":"...","incarnation":1,"nonce":"..."}
```

В ней идентификатор пула, идентификатор агента, номер его воплощения и
случайное число, записанное сервером до создания контейнера. VMID и имя
хоста владения не доказывают: Proxmox переиспользует номера.

Перед каждой записью (запуск, остановка, удаление, клонирование, изменение
конфигурации) сервер читает конфигурацию контейнера и принимает его, только
если всё сразу верно:

 - описание в точности равно ожидаемой отметке;
 - контейнер непривилегированный;
 - корневой диск лежит в хранилище подключения и назван по VMID контейнера
   (для связанного клона — с базовым томом образа перед ним);
 - сетевой интерфейс один, `net0`: имя `eth0`, мост подключения, `ip=dhcp`,
   без брандмауэра Proxmox на интерфейсе;
 - `features` пусто или равно `nesting=1`;
 - нет точек монтирования (`mp*`), устройств (`dev*`), неиспользуемых томов
   (`unused*`), hook-скрипта и параметров `lxc.*`;
 - контейнер состоит в пуле ресурсов подключения на его узле.

Если хотя бы одно условие нарушено, сервер ничего не меняет и показывает у
агента ошибку `ownership`. Отсюда правило для администратора: не
редактируйте контейнеры brood в интерфейсе Proxmox. Добавленный диск,
изменённое описание или включённый брандмауэр на интерфейсе выводят
контейнер из-под управления.

## Как появляется агент

1. Сервер берёт свободный VMID и создаёт контейнер `brood-<идентификатор
   агента>`: связанным клоном образа проекта, если у проекта есть готовый
   образ в этом пуле, иначе из базового шаблона пула. Клону сразу задаются
   ядра и память по доле агента.
2. Сервер запускает контейнер и читает его адрес из API Proxmox
   (интерфейс `eth0`, IPv4 раньше IPv6).
3. Сервер заходит в контейнер по SSH как root ключом установки. Ключ
   `ssh_identity` (ed25519) создаётся при первом запуске сервера рядом с
   файлом базы данных; его открытую половину Proxmox кладёт в контейнер при
   создании. Ключ хоста контейнера принимается при первом входе и
   запоминается процессом сервера: если при следующем входе в то же
   воплощение агента ключ другой, установка останавливается.
4. По SSH сервер кладёт программу агента `/usr/local/bin/brood-guest`,
   настройки `/etc/brood/agent.env` и юнит
   `/etc/systemd/system/brood-agent.service`, ставит ttyd в `/usr/bin/ttyd`
   (закреплённый выпуск, сверка SHA-256) и запускает сервис.
5. Агент подключается к серверу. Когда соединение установлено и терминал
   отвечает, агент получает состояние «работает».

Ключ `ssh_identity` переживает пересоздание базы. Если файл потерян,
сервер создаст новый, но в существующие контейнеры и образы с ним уже не
войти: образы придётся собрать заново, агентов — пересоздать.

## Relay

Relay — постоянное исходящее соединение агента с сервером. Агент
открывает WebSocket на `wss://<публичный адрес>/api/proxmox/guest/<агент>/<воплощение>`,
и через него сервер открывает терминал, доставляет сообщения и
выполняет команды агента. Входящих соединений, кроме SSH на время
установки, контейнеру не нужно.

| Настройка сервера | Значение |
| --- | --- |
| `BROOD_PUBLIC_ORIGIN` | HTTPS-адрес сервера, каким его видят контейнеры, например `https://brood.example.com` |
| `BROOD_PROXMOX_RELAY_SECRET` | секрет не короче 32 байт |

Из секрета сервер выводит токен каждого воплощения агента и ключ, по
которому агент узнаёт сервер. Токен действует только для одного агента и
одного воплощения и только пока агент должен работать: остановленный или
удалённый агент подключиться не может. Если сервер слушает TLS сам
(`BROOD_TLS_CERT`), его сертификат передаётся агенту как доверенный корень.

Без обеих настроек пул нельзя активировать. Устройство каналов описано в
[GO.md](GO.md).

## Жизненный цикл

Агент проходит операции создания, запуска, остановки, сброса и удаления.
Каждая операция сначала записывается в базу, затем сервер отправляет запрос
в Proxmox, получает идентификатор задачи (UPID), записывает его и ждёт
окончания задачи. Раз в пять секунд сервер сверяет каждого агента с
Proxmox и продолжает операцию с того места, где она остановилась, в том
числе после перезапуска сервера.

| Операция | Что происходит с контейнером |
| --- | --- |
| Создание | создать, затем запустить и установить агента |
| Запуск | запустить существующий контейнер; рабочий каталог сохраняется |
| Остановка | остановить; контейнер и рабочий каталог сохраняются |
| Сброс | остановить, удалить, создать новый контейнер (новое воплощение) и запустить; рабочий каталог уничтожается |
| Удаление | остановить и удалить; место в пуле освобождается только после того, как Proxmox подтвердил, что такого VMID больше нет |

Перезапуск (`restart`) контейнер не трогает: он перезапускает сессию Claude
Code внутри него.

«Исход неизвестен» значит следующее. Сервер отправил запись в Proxmox и не
получил ответа: соединение оборвалось, истёк срок, пришёл неразборчивый
ответ. Запрос мог дойти и выполниться, а мог не дойти. Повторить его
вслепую нельзя: второй запрос создания занял бы ещё один VMID, второй
запуск или удаление попал бы в контейнер в неизвестном состоянии. Поэтому
сервер оставляет операцию как есть, показывает у агента ошибку `uncertain`
и ждёт решения человека. Отказ, полученный до отправки (нет прав,
не прошла проверка владения), таким не считается: сервер знает, что ничего
не изменилось, и повторяет попытку сам.

## Образы проектов

Образ — контейнер-шаблон, собранный для проекта в пуле: сервер создаёт
сборочный контейнер из базового шаблона, получает репозиторий на заданном
коммите, выполняет в контейнере плейбук `brood.yaml`, выключает контейнер
и превращает его в шаблон Proxmox. Агенты проекта в этом пуле создаются
связанными клонами самого нового готового образа, поэтому появляются
быстро и почти не занимают места. Образы несут ту же отметку владения, что
и контейнеры агентов. Подробности — в [BUILD.md](BUILD.md).

## Агент внутри контейнера

Агент — программа `brood-guest`, которую systemd запускает от root юнитом
`brood-agent.service` и перезапускает при любом выходе. Настройки она
читает из `/etc/brood/agent.env` (режим 0600):

| Переменная | Значение |
| --- | --- |
| `BROOD_GUEST_ACTOR_UID` | идентификатор агента |
| `BROOD_GUEST_GENERATION` | номер воплощения |
| `BROOD_GUEST_RELAY_URL` | адрес relay |
| `BROOD_GUEST_RELAY_TOKEN` | токен воплощения |
| `BROOD_GUEST_RELAY_HOST_KEY` | ключ, по которому агент узнаёт сервер |
| `BROOD_GUEST_CA_PEM_B64` | сертификат сервера, если сервер слушает TLS сам |

При каждом старте агент доводит стоковый Debian до рабочего состояния и
создаёт только то, чего нет:

 - пользователя и группу `actor` с UID и GID 1000, домашний каталог
   `/workspace/home`;
 - каталоги `/workspace`, `/workspace/home` и `/workspace/project`
   (рабочий каталог проекта);
 - каталоги `/etc/brood` и `/var/lib/brood`;
 - пакеты `git` и `ca-certificates`, если их нет.

Затем агент скачивает с сервера набор программ: `brood-guest`, клиент `bro`
и Claude Code (`claude`). Сервер отдаёт манифест с размерами и суммами
SHA-256, агент сверяет каждый файл и кладёт набор в
`/opt/brood/releases/<идентификатор набора>`; ссылка `/opt/brood/bin`
указывает на текущий набор, `/opt/brood/previous` — на прежний. Набор, уже
лежащий на диске и совпадающий с манифестом, заново не скачивается. После
этого агент перезапускает себя из скачанного набора, поэтому новая версия
сервера доходит до агентов при их следующем старте.

Дальше агент получает секреты проекта и адрес репозитория, клонирует
репозиторий в `/workspace/project` и запускает сессию Claude Code от
пользователя `actor`. Обращения к модели и к Git с серверными учётными
данными идут через локальные адреса агента (`127.0.0.1:8317` и
`127.0.0.1:8318`), которые пересылают их на сервер; ключей модели и Git в
контейнере нет.

Терминал сессии отдаёт ttyd на `127.0.0.1:8080` внутри контейнера; наружу
он не слушает, сервер достигает его через relay. Режимов два:

 - `rw` — обычный терминал с вводом, открывается владельцу роя и
   администратору; им же пользуется `bro attach`;
 - `ro` — снимки экрана без ввода.

## Диагностика

Ошибка агента видна в списке агентов панели и в `bro agents`; у каждой
есть устойчивый код.

| Код | Что случилось | Что проверить |
| --- | --- | --- |
| `permission` | Proxmox отказал токену (HTTP 401 или 403). Ничего не изменено, сервер повторяет попытку | Роли из раздела «Роли и права»: `pveum user permissions brood@pve`. Срок действия токена. Что хранилище, мост и пул ресурсов в подключении названы так же, как в ACL |
| `ownership` | Контейнер не прошёл проверку владения. Ничего не изменено | Сравните конфигурацию контейнера (`pct config VMID`) со списком из раздела «Отметка владения»: описание, диск, `net0`, `features`, состав пула ресурсов. Верните прежнее или удалите агента |
| `task_failed` | Proxmox начал задачу и сообщил о сбое | Журнал задач контейнера в интерфейсе Proxmox: нет места в хранилище, шаблон не найден, мост не существует, блокировка контейнера |
| `task_pending` | Задача идёт дольше 15 минут. Сервер продолжает ждать | Идёт ли задача в Proxmox; нагрузку на хранилище |
| `uncertain` | Proxmox не подтвердил, началась ли операция. Сервер её не повторяет | Существует ли контейнер с этим VMID. Если нет — удалите агента; если есть — подождите и обновите список |
| `provider_unavailable` | Сервер не достучался до API Proxmox. Повторяет сам | Доступность адреса API с сервера, сертификат CA в подключении, сетевые ограничения сервера |
| `agent_waiting` | Контейнер запущен, но не отвечает по SSH. Сервер ждёт | Получил ли контейнер адрес (`pct exec VMID -- ip -4 addr show eth0`), работает ли DHCP на мосту, достигает ли сервер этого адреса по TCP 22 |
| `agent_install` | Шаг установки агента в контейнере завершился ошибкой; шаг назван в сообщении | Для шага `terminal server` — выход контейнера на GitHub и в репозитории Debian. Свободное место в контейнере |
| `agent_not_connected` | Агент не подключился за две минуты после запуска контейнера | В консоли контейнера: `systemctl status brood-agent`, `journalctl -u brood-agent`. Достигает ли контейнер `BROOD_PUBLIC_ORIGIN` по HTTPS, доверяет ли он его сертификату |
| `other` | Остальное; причина в тексте | См. ниже |

Сообщения с кодом `other`, которые относятся к установке:

 - `agent binary is not published; BROOD_ARTIFACTS_DIR must hold brood-guest` —
   на сервере не опубликован набор программ агента ([DEPLOY.md](DEPLOY.md));
 - `installation SSH identity is unavailable` — сервер не смог прочитать или
   создать `ssh_identity` рядом с базой;
 - `container SSH host key changed since first contact` — по адресу
   контейнера отвечает другой хост: проверьте, не выдал ли DHCP этот адрес
   повторно.

Если агент не подключается, а в журнале сервиса видно
`guest artifact delivery unavailable or unsafe`, сервер не отдаёт набор
программ: проверьте `BROOD_ARTIFACTS_DIR` и его `manifest.json`.
