# Пулы Proxmox

## Два разных пути исполнения

Класс `lxc` у обычного Substrate WorkerPool запускает LXC внутри worker pod.
Такой актор не является CT, управляемой Proxmox. Эти пулы и полные профили
`development`/`coding` сохраняются без смены runtime при выкладке сервера.

Управляемый пул Proxmox использует другой путь:

```text
Brood Go API + SQLite
  -> проверенный HTTPS API Proxmox
     -> отдельная unprivileged CT для каждого актора
        -> доверенный root supervisor
           -> Go PTY holder + Claude Code/ttyd от UID/GID 1000
```

В этом пути нет фиктивного Kubernetes worker или `workerAssignment`.
Пул показывает собственное резервирование, а актор — provider, node, CTID,
поколение и фазу. Рой сохраняет свою настоящую привязку к Substrate atespace;
права проекта и роя проверяются до обращения к provider.

## Ограниченный профиль

Первый профиль называется `claude-proxmox`:

- отдельная непривилегированная CT;
- инструментарий разработки, ttyd и bootstrap-бинарь brood-guest из
  закреплённого OCI-образа; claude в образ не входит — bootstrap скачивает
  brood-guest/bro/claude с сервера при старте CT (настройка
  `BROOD_ARTIFACTS_DIR`, #155);
- постоянные `/workspace/home` и `/workspace/project` внутри диска CT;
- терминал через аутентифицированный обратный relay;
- root-owned DNS/HTTP proxy и nft policy, не управляемые процессом актора;
- UID/GID 1000, `NoNewPrivs=1`, без effective/ambient capabilities;
- без Docker/kind, доступа к host kernel log и memory checkpoint.

Новый workspace пуст, пока у актора нет origin; с origin первый старт
приложения клонирует его (см. «Origin и первый клон»). Секреты оператора,
SSH-конфигурация, `.env`, сессия Brood и credentials модели в образ или
workspace не копируются. Запуск
`claude --version` или открытие CLI не является проверкой платного model task.
В новом guest image Claude использует локальный шлюз CLIProxyAPI установки:
`ANTHROPIC_BASE_URL=http://127.0.0.1:8317`, discovery моделей включён.
Какие модели Claude Code запрашивает, задаёт установка (#263), см. «Модели
Claude Code актора»; без настроек выбирает сам Claude Code.
`ANTHROPIC_AUTH_TOKEN=brood-local` — несекретная локальная заглушка для CLI,
не ключ модели и не полномочие сервера. Root gateway подставляет scoped relay
токен только на TLS-запросе к своему серверу, сервер — отдельный API key
CLIProxyAPI. При отсутствии серверной настройки запрос получает явный отказ.

Остановка и повторный запуск той же CT сохраняют workspace. **Reset создаёт
новую CT и безвозвратно удаляет прежний workspace.** Интерфейс требует явного
подтверждения. Удаление актора также удаляет его диск. Suspend с memory
checkpoint не поддерживается и отклоняется до внешних действий.

## Приватная конфигурация установки

`BROOD_PROXMOX_POOLS` и `BROOD_PROXMOX_TOKENS` — JSON-объекты в `.env`.
Координаты PVE, bridge, storage и ссылка на credential задаются явно: дефолтов
машины разработчика нет. Секрет токена находится только во втором объекте;
API панели возвращает разрешённые публичные поля подключения, а не credential
reference, CA или значение секрета.

Исходные поля подключения: `endpoint`, `tokenID`, `node`, `resourcePool`,
`storage`, `network`, `credentialRef`, `caPEM`. Установка с одним лишь
подключением остаётся read-only: просмотр не создаёт пул и не обращается к PVE.

Для исполнения добавляются все три поля одновременно:

```json
{
  "template": "templates:vztmpl/brood-claude-proxmox-<archive-sha256>.tar",
  "templateDigest": "sha256:<archive-sha256>",
  "capacity": {
    "actors": 2,
    "cpuMillicores": "4000",
    "memoryBytes": "4294967296",
    "diskGiB": 32
  }
}
```

Это **суммарные** ограничения пула. Пример даёт каждому из двух акторов
2 CPU, 2 GiB памяти и 16 GiB диска; профиль делит ёмкость на равные доли с
округлением вниз до целых CPU, MiB и GiB. Неподдерживаемые размеры отклоняются.
Провайдер не считает свободные ресурсы всего PVE-хоста разрешением превысить
эти ограничения.

Также требуются:

- `BROOD_PUBLIC_ORIGIN`: явный HTTPS origin сервера, доступный из CT и
  соответствующий TLS-сертификату;
- `BROOD_PROXMOX_RELAY_SECRET`: отдельный случайный ключ не короче 32 байт,
  не равный session secret. Он остаётся на сервере.

Настройки доставляются только в Secret и env сервера. Изменение Secret
меняет checksum pod template и вызывает обычный rollout даже при том же
образе. Egress сервера к PVE ограничивается разрешёнными IP подключения и
точным TCP-портом; отказ DNS прекращает выкладку, а не открывает широкую сеть.
Устройство выкладки и защищённые переменные описаны в [DEPLOY.md](DEPLOY.md).
Ротация relay key отзывает прежние guest tokens и меняет SSH host key:
текущим CT нужен контролируемый stop/bootstrap/start. Одна лишь выкладка
сервера не переписывает окружение уже работающего гостя.

Пул активируется администратором явно. Состояние «настроено» означает наличие
конфигурации, а не успешную проверку гостя или готовность актора.

## Подключение из панели

Администратор может создать подключение через `POST /api/proxmox-connections`:
`name`, `endpoint`, `tokenID`, `tokenSecret`, `caPEM`, `node`, `resourcePool`,
`storage`, `network`. Endpoint и CA вводятся явно, PVE token не передаётся
гостю. Поля `template`, `templateDigest`, `capacity` необязательны, но для
runtime задаются вместе в форме, точно в формате выше. Без них подключение
видно в инвентаре, но активировать его нельзя. Runtime-имя — lowercase DNS
label не длиннее 48 символов. Ввод проверяется теми же правилами, что env;
неизвестные поля, повторы JSON-ключей и дополнительные JSON-документы
отклоняются.

SQLite хранит подключение, CA, write-only token secret и одобренную runtime
конфигурацию. API не возвращает token secret или CA; строковые и JSON
представления входной структуры также их скрывают. База и резервные копии
содержат credential в открытом виде и требуют такого же ограничения доступа,
как Secret установки. Миграция v5 -> v6 добавляет runtime без сброса строк.
Изменение и ротация подключений через API пока не поддерживаются.

Для независимой приёмки нового guest image администратор может вызвать
`POST /api/proxmox-connections/{uid}/clone`, где `uid` — UID подключения
из БД. Тело содержит только обязательные `name`, `template`, `templateDigest`
и `capacity` в формате выше. Неизвестные поля, регистровые варианты имён,
повторы ключей, `null`, неверные типы и выход за ограничения runtime отклоняются.
Endpoint, tokenID, token secret, CA, node, resourcePool, storage и network
наследуются сервером из текущей записи источника; переопределить их нельзя.
Клонирование env-подключений не поддерживается.

Запрос требует действующую сессию администратора, same-origin `Origin` и
CSRF token. Перед записью сервер повторно проверяет сессию и текущую роль.
Ответ `201` — обычный metadata DTO подключения, без token secret и CA.
Ошибки не возвращают credential или исходный payload: `400` — неверная
структура, `422` — отсутствующие или невалидные поля, `404` — нет DB UID,
`409` — имя занято в БД или env. Создаётся только новое подключение:
сетевых запросов к PVE нет, источник, его пул и акторы не меняются.
Активация и удаление нового подключения/пула выполняются обычными API;
это не обновление immutable snapshot существующего пула (#109).

Активация выполняется отдельно:
`POST /api/proxmox-pools/{name}/activate` с пустым телом. Она сохраняет
снимок пула, но не проверяет PVE сетевым запросом. Дальнейшие операции акторов
используют сохранённые координаты и credential; перезапуск сервера не требует
переносить их в `BROOD_PROXMOX_POOLS` или `BROOD_PROXMOX_TOKENS`. При этом
`BROOD_PUBLIC_ORIGIN` и `BROOD_PROXMOX_RELAY_SECRET` по-прежнему обязательны
для runtime, даже когда env-пулы вообще не заданы.

Имена подключений env и БД не могут совпадать: создание из формы и запуск
сервера при такой коллизии отказывают. `DELETE /api/proxmox-connections/{uid}`
отклоняется, пока у подключения есть неудалённый managed pool или актор.
Сначала требуется подтверждённая очистка акторов и отдельное удаление пула;
исторические tombstone не препятствуют удалению подключения.

Сохранение формы не меняет сетевую политику кластера: доступ сервера к новому
PVE endpoint должен быть разрешён оператором отдельно. Форма не загружает
шаблон, не выдаёт токену права и не проверяет доступность реального PVE.

## Сборка и публикация образа

`.ci/proxmox-guest.sh OUTPUT_DIRECTORY` собирает Linux/amd64 OCI `.tar` из
чистого committed HEAD. Контекст компиляции и финального образа разрешён
явным списком; секреты и ignored-файлы рабочей копии не берутся. Скрипт
проверяет закреплённые версии и checksum инструментов и выдаёт
`proxmox-guest.tar` плюс `metadata.json` с commit и SHA-256 архива.

claude в образ не входит (#155): образ содержит тулчейн, ttyd и
bootstrap-бинарь brood-guest; runtime копии brood-guest, bro и claude
bootstrap скачивает с сервера при старте CT из каталога настройки
`BROOD_ARTIFACTS_DIR` после поднятия сети (адрес приходит по DHCP) и до
секретов и сервисов актора, с проверкой sha256 и ELF каждого артефакта.
Набор ставится в каталог `/opt/brood/releases/<id>`, а `/opt/brood/bin`
становится ссылкой на него (#184, «Обновление гостевых бинарей»):
установщик сверяет sha256 из манифеста на спуле до rename (#265), доставка
с другим digest не публикуется, и следующий старт снова качает набор. Без
настройки или артефактов новый образ отказывает fail closed; точное имя
настройки называет отказ сервера при неверном значении. CT из шаблонов до
#155 маршрут не вызывают и работают со встроенными бинарями как раньше.
Claude и MCP-сервер `bro` запускаются по прежним путям `/opt/brood/bin/*`.

Непустой output directory и перезапись результата запрещены. Сборка требует
Docker buildx; выбранный `BUILDX_BUILDER` используется и для компиляции, и для
финального образа. Опциональный `--seed` добавляет очищенный снимок проекта
как bundle в `/opt/seeds`; supervisor автоматически его не устанавливает.

Архив публикуется в template storage под неизменяемым именем с digest. Перед
активацией оператор проверяет соответствие содержимого, имени и настроенного
`templateDigest`. Runtime API token не получает права загружать шаблоны.
В установленном PVE должна поддерживаться распаковка OCI `.tar`; наличие
обычной LXC template storage само по себе этого не доказывает.

OCI import в PVE заменяет env значениями образа. Поэтому provider после
создания выполняет отдельный `ConfigureBootstrap` остановленной CT: проверяет
владение и digest конфигурации и меняет только bootstrap env через digest CAS.
Перед каждым новым поколением токен и параметры relay задаются заново.

## Браузерный терминал driftty

Новый guest image содержит только браузерный клиент driftty v3.0.0
(`mdp/driftty`, commit `a4b8b2b38ee29b8fa5b979e70d37e1565b09cb0e`).
`brood/dev/pins.json` закрепляет commit, SHA-256 исходного архива,
SHA-256 готового `index.html` и digest образа Node для сборки. Docker build
проверяет архив до распаковки, ставит зависимости через upstream
`package-lock.json` с `npm ci --ignore-scripts`, затем собирает UI без сети
от непривилегированного пользователя. Итоговый образ получает только
`dist/index.html` и MIT license в `/usr/local/share/brood/driftty/`;
Node и gateway driftty из build stage в него не копируются.
После проверки upstream HTML добавляется локальный `driftty-storage.js`:
actor-view сохраняет `sandbox allow-scripts` с opaque origin, поэтому
недоступные localStorage/sessionStorage заменяются памятью текущей вкладки.
Ослаблять sandbox ради хранения настроек терминала не требуется. Тест
совместимости исполняется в build stage до публикации HTML.

Гостевой ttyd использует `--index /usr/local/share/brood/driftty/index.html`
на прежнем `127.0.0.1:8080`, с `--writable` и `--check-origin`. Клиент
обращается к прежним `/token` и `/ws` относительно пути терминала.
Новых публичных listeners, credentials, auth routes и разрешений relay нет.
Go PTY holder (#162) держит процесс Claude независимо от браузера. Ttyd
запускает только фиксированный `brood-guest --brood-guest-attach`; исходные
байты PTY доходят до driftty без промежуточного терминального эмулятора.
Закрытие вкладки отсоединяет клиента, не останавливая Claude. Headless VT
наблюдает поток только для снимков MCP и восстановления состояния экрана
при reconnect; его ответы терминалу не отправляются приложению.
Root создаёт `/run/brood/pty.sock` (root:1000, 0660) в защищённом каталоге и
передаёт listening FD 3 фиксированному UID 1000 процессу. `/run` в CT не
tmpfs и переживает остановку, а жёсткая остановка PVE не удаляет сокет: при
старте root заменяет только собственный сокет, на котором никто не принимает
соединение (#271); живой слушатель, другой владелец или не-сокет — отказ
старта. Модель не выбирает
путь, команду или окружение holder. Writer и источник размера один:
второй browser writer, конфликтующие MCP input/resize и workspace-операции
с остановкой сессии отвергаются; read-only наблюдатели не меняют размер PTY.
Явные lifecycle stop/reset/delete CT сохраняют прежнюю семантику. Broker и внешние MCP/API
контракты сохранены; tmux больше не участвует в новом guest runtime.
При выходе приложения holder завершает оставшихся участников его группы
процессов до освобождения PID лидера. Если подтвердить очистку нельзя, он
возвращает `unknown`, удерживает идентичность и запрещает новый сеанс;
клиент и supervisor получают причину, а не успешное завершение.
Если bootstrap обновил бинарь старого образа без index, он сохраняет штатный
клиент ttyd; одна выкладка серверного бинаря не добавляет driftty в старые CT.

Выкладка сервера не заменяет уже работающий гостевой runtime. Переход
существующего актора с tmux требует согласованного перезапуска его сессии:
переноса живого Claude из PTY tmux в другой PTY нет. Новый набор гостевых
бинарей актор получает своим следующим stop/start с сохранением home и
workspace, если его CT создана из шаблона с bootstrap #184; CT прежних
шаблонов после выкладки, изменившей артефакты, stop/start не переживают
(«Обновление гостевых бинарей»).

Для приёмки после интеграции нужен новый committed guest image:

```sh
BUILDX_BUILDER=<builder> .ci/proxmox-guest.sh /tmp/brood-160-image
```

Каталог результата должен отсутствовать или быть пустым. Оператор публикует
полученный OCI-архив под именем с его SHA-256, сверяет `metadata.json` и
создаёт отдельное fixture-подключение через clone API с новыми `template` и
`templateDigest` (см. выше). Существующие подключения, пулы и пользовательские
акторы не обновляются и не reset-ятся ради этой проверки.

В отдельном fixture-пуле проверить новый актор через настоящий Go actor-view:
мобильную клавиатуру и resize, ввод/вывод команды с уникальным маркером,
разрыв и повторное открытие вкладки с сохранением PID/start/epoch и маркера,
обычные restart/recycle и MCP agents/send. Проверить HTTP index, `/token` и
WebSocket `/ws` под префиксом actor-view, отсутствие внешних JS/CSS/font
загрузок и нового gateway, прежние отказы без ticket/сессии, при чужом ACL и
после смены поколения. Проверка через прямой порт ttyd не заменяет эту
приёмку CSP и прокси. Удалять можно только созданные fixture-ресурсы после
отдельного подтверждения оператора, не чужие акторы.

## Обновление гостевых бинарей

Bootstrap шаблона с #184 на каждом старте CT ставит текущий набор
артефактов сервера отдельным релизом и переключается на него: штатный
stop/start оператора и есть обновление. Нового действия API, изменения схемы
и автоматического перезапуска акторов нет; `/workspace/home` и
`/workspace/project` обновление не трогает.

```text
/opt/brood/                                root, 0755
  releases/<id>/{bro,brood-guest,claude}   проверенные наборы, файлы root 0755
  bin -> releases/<id>                     текущий набор
  previous -> releases/<id>                прежний набор для отката
  bin.legacy-<n>/                          плоский bin прежнего bootstrap
  .lock                                    flock bootstrap
```

`<id>` равен sha256 канонического текста манифеста: строка
`brood guest release v1`, затем строка `имя размер sha256` на каждый
артефакт в порядке `bro`, `brood-guest`, `claude`
(`guest.ArtifactManifest.ReleaseID`). Тот же набор даёт тот же id при любом
порядке и форматировании JSON, другой файл даёт другой id. Номера версии нет.
Целостность текущего набора в CT проверяет та же формула: вывод команды
совпадает с именем каталога из `readlink /opt/brood/bin`.

```sh
cd /opt/brood/bin && { echo 'brood guest release v1'; for f in bro brood-guest claude; do
  echo "$f $(stat -c %s "$f") $(sha256sum < "$f" | cut -d' ' -f1)"; done; } | sha256sum
```

Порядок старта, весь в bootstrap-стадии, до секретов, сервисов и процессов
актора:

1. DHCP, затем манифест сервера машинным маршрутом.
2. `/opt/brood` и `releases` открываются без следования ссылкам; они должны
   принадлежать root и быть закрыты на запись группе и остальным, иначе
   отказ. Доверенный каталог получает ровно 0755, чтобы актор дошёл до
   `bro` и `claude`. Затем `flock` на `.lock`: второй bootstrap ждёт первого.
3. `bin`, который не является ссылкой (плоский каталог прежнего bootstrap
   или файл), переименовывается в первое свободное `bin.legacy-<n>` и не
   удаляется. Ссылка не на `releases/<id>` просто заменяется.
4. Из `releases` убирается всё, кроме текущего, прежнего и нужного наборов:
   staging прерванного старта, старые наборы, посторонние записи. Ссылки
   удаляются сами, их цели не трогаются.
5. Существующий `releases/<id>` проверяется заново: каталог root 0755 ровно
   с тремя файлами, каждый обычный файл root 0755 с размером и sha256
   манифеста. Целый набор берётся без загрузки, повреждённый или неполный
   удаляется и качается заново. Полное хеширование выбрано вместо отметки об
   установке: отметка не ловит порчу диска и ручную правку, а sha256 310 МБ
   стоит около 0,25 с с SHA-NI плюс чтение с диска, меньше загрузки.
6. Отсутствующий набор качается в `releases/.stage-<id>`: спул
   `.<имя>.part`, ровно `size` байт, сверка sha256, 0755, fsync, rename в
   имя; после трёх файлов fsync и rename каталога в `releases/<id>`.
   Неполный набор под именем `<id>` не появляется.
7. Переключение: сначала `previous` получает прежний текущий набор, затем
   `bin` новый. Каждая ссылка создаётся рядом (`.bin.next`,
   `.previous.next`) и ставится rename поверх, с fsync `/opt/brood`:
   переключение не показывает ни отсутствующего, ни неполного набора.
8. Уборка до двух наборов: текущий и `previous`. Текущий не удаляется.
9. exec `/opt/brood/releases/<id>/brood-guest` как runtime-стадии. Runtime
   ничего не ставит; PATH и пути `/opt/brood/bin/{bro,claude}` разрешаются
   через ссылку в тот же набор, а ссылка до следующего старта не меняется,
   поэтому процессы актора не видят смешанного набора.

Отказы fail closed, как до #184: нет манифеста или артефактов, неверный
digest, размер или ELF, небезопасный корень, lock не получен за срок
загрузки, ошибка записи или переключения. Bootstrap выходит с короткой
причиной (`guest bootstrap failed: ...`), CT останавливается, runtime не
стартует. Отказ уборки (шаги 4 и 8) старт не останавливает: bin указывает на
проверенный набор, а неудаляемая запись иначе отказывала бы каждому старту.
Он печатается в консоль CT как `guest bootstrap warning: guest release
cleanup failed`, остальные лишние записи всё равно удаляются; остаток
прерванной установки, который мешает загрузке, остановит её собственным
отказом. Установленный набор без проверенного
манифеста сервера не загружается: runtime всё равно нужен сервер (relay,
секреты, origin). Отказ до шага 7 оставляет `bin` на прежнем наборе, кроме
двух случаев: повреждённый текущий набор удалён перед повторной загрузкой
или плоский `bin` уже отодвинут. Тогда `bin` до следующего успешного старта
никуда не указывает; процессов, которые его читают, в этот момент нет.
Следующий старт с доступным сервером доводит установку до конца. Крах в
любой точке оставляет только состояния, из которых следующий старт сходится
(`go/cmd/brood-guest/release_test.go`).

Откат: выкладка прежнего релиза сервера возвращает прежний манифест;
следующий stop/start находит его набор в `previous`, проверяет и включает без
загрузки. Повторный старт того же набора `previous` не теряет; набор старше
прежнего качается заново. Место на диске CT: до двух наборов (около 620 МБ)
и третий на время загрузки; `bin.legacy-<n>` остаётся, пока оператор не
удалит его сам.

Правило действует только в CT, чей образ несёт bootstrap #184. Bootstrap
шаблонов от #155 до #184 ставит артефакты прямо в плоский `/opt/brood/bin` и
отказывает, если там другие файлы: после выкладки, которая меняет хоть один
артефакт (правка `cmd/brood-guest`, `cmd/bro`, их пакетов или пина claude),
такой актор не переживает stop/start, а остановленный не запускается.
Работающий продолжает работать до остановки.

## Новый шаблон гостя и переход пула

Bootstrap входит в образ, а не в артефакты сервера, поэтому его правка
доходит до актора только с новой CT из нового шаблона. Что умеет код:

- шаблон пула неизменяем, пока у пула есть акторы: другая пара
  `template`/`templateDigest` в конфигурации делает пул недоступным, а
  `UpdateManagedPool` отказывает (#109 закрыт без исправления);
- актор хранит свой снимок шаблона, и reset пересоздаёт CT из этого снимка.
  **Reset сам по себе новый bootstrap не приносит;**
- новый шаблон получает новое подключение (clone, см. «Подключение из
  панели») и его пул; актор между пулами не переносится.

Смена шаблона существующего пула, после которой reset брал бы новый шаблон,
требует кода (#109). Без него переход выполняет оператор:

1. Сборка из чистого checkout коммита main на машине с Docker buildx:
   `BUILDX_BUILDER=<builder> .ci/proxmox-guest.sh <пустой каталог>`.
   В `metadata.json` сверить `source_commit` и `archive_sha256`.
2. Публикация: `proxmox-guest.tar` загружается в vztmpl-хранилище PVE
   (то же, что в `template` пула) под именем
   `brood-claude-proxmox-<archive_sha256>.tar`, через интерфейс PVE или
   копированием на хосте; runtime token права загрузки не имеет. На хосте
   `sha256sum` файла должен совпасть с `archive_sha256`.
3. Пул на новом шаблоне, один из двух путей:
   - при ближайшем пересоздании установки (партия схемы) новое подключение
     сразу получает `template`
     `<storage>:vztmpl/brood-claude-proxmox-<archive_sha256>.tar` и
     `templateDigest` `sha256:<archive_sha256>`;
   - без пересоздания: `POST /api/proxmox-connections/{uid}/clone` с
     `name`, новыми `template`, `templateDigest` и `capacity`, затем
     `POST /api/proxmox-pools/{name}/activate`. Оба пула резервируют ёмкость
     одного PVE: на время перехода её должно хватить обоим, иначе старых
     акторов удаляют раньше.
4. Приёмка на fixture-акторе нового пула: после старта в CT (`pct exec`
   после сверки владельца по UID в описании CT) `readlink /opt/brood/bin`
   показывает `releases/<id>`, а `ls /opt/brood/releases` один набор;
   stop/start оставляет тот же id и время изменения файлов (загрузки нет);
   после выкладки с изменённым гостем stop/start даёт новый id и `previous`
   на прежний. Fixture удаляется после подтверждения оператора.
5. Акторы пересоздаются в новом пуле: это та же потеря home и workspace,
   что reset. До этого рой останавливается, незапушенная работа забирается.
   Актор удаляется в старом пуле и создаётся с тем же именем, ролью и
   origin в новом (шаблон актора `claude-proxmox-<новый пул>`), роли роя
   привязываются заново (`bro swarm bind`). Workers, созданные master
   командой `add`, попадают в пул master.
6. Пустые старый пул и подключение удаляются обычными API.

Дальше обновление гостевых бинарей сводится к выкладке сервера и stop/start
актора в удобный момент. Пока акторы на прежнем шаблоне, их нельзя
останавливать после выкладки, меняющей артефакты, включая выкладку самого
#184. Обход без потери данных из анализа #184 (на остановленной CT после
сверки владельца удалить `/opt/brood/bin/{bro,brood-guest,claude}` через
`pct mount`) идёт мимо контроля brood.

## Терминал и сеть

Гость сам открывает WSS на
`/api/proxmox/guest/<actorUID>/<generation>`. Внутри соединения идёт SSH с
закреплённым публичным host key. Терминальный канал ведёт только к
`127.0.0.1:8080`; отдельный `brood-swarm-msg` передаёт ограниченные запросы
сообщений роя. Произвольные exec, SCP и port forwarding не предоставляются.
Гость получает HMAC-токен своего UID/поколения, но не установочный relay key,
PVE token или browser session. Публичная TLS chain передаётся в base64.

Machine route имеет собственную аутентификацию вне cookie/CSRF middleware.
Браузер использует прежний actor-view сессией, ACL, CSP и ticket, дополнительно
привязанным к managed UID и поколению. Просмотр не запускает остановленный
managed actor неявно. Подключённый relay ещё не означает готовность:
нужна успешная HTTP-проверка настоящего ttyd после завершения PVE task.

До запуска актора root supervisor завершает DHCP и устанавливает nft policy,
ограниченный DNS и HTTP/CONNECT proxy. Прямой IPv4/IPv6 egress UID 1000 закрыт;
proxy разрешает только точные одобренные публичные имена и порты. Проверяются
все resolved addresses, затем соединение открывается к уже проверенному IP.
Private, loopback, link-local, multicast и unspecified targets не становятся
разрешёнными из-за DNS rebinding. Удаление proxy env актором не снимает nft.

Loopback внутри CT для UID 1000 открыт целиком: TCP и UDP через `lo` к
`127.0.0.0/8` и `::1` в обе стороны, поэтому `go test ./...` с `httptest`
и тестами резолвера на эфемерных портах работает в госте (#250). Это не
расширяет границу: root слушает на loopback только 3128 (proxy), 5353 (DNS),
8317 и 8318 (gateways), и все они были доступны актору и раньше; ttyd на
`127.0.0.1:8080` запускает сам актор как UID 1000. Собственный адрес `eth0`
гостя тоже маршрутизируется через `lo`, но вне `127.0.0.0/8` остаётся закрыт.
Трафик UID 1000 с любого другого интерфейса по-прежнему заканчивается
`reject`, а снаружи фиксированные порты закрыты `input` chain.

Отказ enforcement не разрешает запуск с добровольным proxy-only режимом.
Повторный supervisor должен эксклюзивно создать nft table и не может принять
или удалить правила уже работающего supervisor. Для этого профиля не нужно
менять глобальные PVE firewall, AppArmor, sysctl или bridge policy.

## Автономный запуск Claude

Claude стартует без человека у терминала. При загрузке, после DHCP, секретов,
origin, gateway и сервисов актора, root supervisor запускает собственный
бинарник с фиксированным `--brood-guest-autostart` от UID/GID 1000 с
NoNewPrivs и фиксированным env. Helper выполняет idempotent `ensure` через
защищённый сокет Go PTY holder. Живая сессия не заменяется; новую запускает
holder фиксированной командой `brood-guest --brood-guest-app`, как restart.
Сам holder и ttyd остаются в `/workspace/home`; только app wrapper выбирает
`/workspace/project`. Browser attach не создаёт и не оживляет сессию после
её явной остановки. Отказ helper пишется одной строкой в stderr supervisor
и повторяется с паузой от 1 до 30 секунд до успеха или остановки; supervisor
от него не падает. Проектные секреты читает только app wrapper, а не holder
или browser attach.

В свободной сессии wrapper запускает
`claude --dangerously-skip-permissions --mcp-config ...`, как mop: brood
добавляется к MCP-серверам и настройкам актора. Сессию после подтверждения
workspace он запускает строже («Сессия шага»). Перед exec он сливает в `~/.claude.json`
`hasCompletedOnboarding=true`, `theme` (если не задан, `dark`),
`resumeReturnDismissed=true` и
`projects["/workspace/project"].hasTrustDialogAccepted=true`, а в
`~/.claude/settings.json` пишет `skipDangerousModePermissionPrompt=true` и
автономный профиль (ниже). Прочие ключи сохраняются байт в байт. Запись
атомарна (новый inode и rename),
symlink, hard link, чужой владелец и файл больше 1 MiB — отказ без
изменений; повреждённый файл или не-объект заменяется минимальным объектом
с этими ключами, но не пустым файлом. Неудача настройки — предупреждение в
терминале, Claude всё равно стартует.

Bypass снимает запросы разрешений внутри CT: модель выполняет инструменты
без подтверждения. Граница остаётся прежней — UID 1000 без capabilities,
nft, DNS и HTTP/CONNECT proxy root supervisor, machine credentials вне
актора. Не выдавайте проекту секреты, которые его код и модель не должны
использовать ([SECRETS.md](SECRETS.md)).

### Автономный профиль

У актора нет человека у терминала, поэтому обе сессии, свободная и сессия
шага, держат один профиль Claude Code (#164, по mop):

- `crossSessionInbound: "accept"`: сообщения других сессий принимаются без
  диалога Deliver/Deny. Без него закреплённая 2.1.310 в bypass-сессии держит
  сообщение без `from-mode` (`no-mode-asserted`) и сообщение, пришедшее до
  готовности сессии (`mode-unknown`), а `from-mode` конверта учитывает только
  при включённом флаге `tengu_harbor_kite_mode_emit`. Явная настройка решает
  раньше всего этого. Проектные настройки (`.claude/settings.json`, в
  свободной сессии и `.claude/settings.local.json`) могут лишь ужесточить её
  до `hold` или `refuse`;
- `permissions.deny` для `SendMessage`, `ListAgents`, `AskUserQuestion`,
  `EnterWorktree`, `ExitWorktree` и `SendFeedback`. Deny убирает инструмент
  из списка модели (и из ToolSearch), не только отказывает при вызове, и под
  `--dangerously-skip-permissions` тоже. Встроенный обмен видит только сессии
  этого CT, сообщения роя идут через MCP `brood`; `AskUserQuestion` паркует
  сессию; worktree уводит работу из `/workspace/project`; черновики отзыва
  показывать некому;
- `feedbackDrafts: "off"`, а в фиксированном окружении
  `DISABLE_FEEDBACK_COMMAND=1` и `CLAUDE_CODE_DISABLE_FEEDBACK_SURVEY=1`: ни
  черновиков, ни `/feedback`, ни опроса качества. Проектный секрет этих имён
  не переопределит.

В свободной сессии wrapper сливает ключи в `~/.claude/settings.json` при
каждом старте: `crossSessionInbound` и `feedbackDrafts` принадлежат brood и
ставятся заново, в `deny` дописываются только недостающие имена после
записей актора. `allow`, `ask`, прежние `deny`, прочие члены `permissions`,
модели, hooks, `env` и неизвестные ключи не меняются; `permissions`
не-объектом или `deny` не-массивом Claude Code не прочитал бы, они
заменяются. Сессия шага этот файл не читает и получает те же ключи из
drop-in root («Сессия шага»): `crossSessionInbound` и `feedbackDrafts`
Claude Code берёт только из управляемых настроек, флагов и настроек
пользователя. Drop-in существует только в режиме шага, на свободную сессию не
действует. Списки инструментов и приём сообщения без `from-mode` и с чужим
`from-mode` в обоих режимах проверены запуском закреплённого бинарника без
сети против локального фальшивого API.

Не переносятся из профиля оператора: URL и токены, plugins и MCP-серверы,
`NODE_TLS_REJECT_UNAUTHORIZED=0`, предпочтения интерфейса (vim,
fullscreen, thinking, effort по моделям) и `CLAUDE_CODE_MAX_CONTEXT_TOKENS`.
Окно контекста принадлежит модели установки, а не профилю: закреплённая
2.1.310 применяет эту переменную только к модели с именем не `claude-*` без
окна в каталоге модели (одно значение на основную, малую и модели
подагентов), а без неё считает такой модели 200000 токенов. Настройки
установки для окна пока нет, и переменная не задаётся.

Изоляцию подагентов в worktree (`isolation: "worktree"` у Agent tool)
настройкой 2.1.310 не выключить: её отключает только
`CLAUDE_CODE_EVAL_CONFINED` харнесса оценки plugins с иными побочными
эффектами. Файлы worktree подагента в `.claude/worktrees/` откажут
следующему подтверждению шага («Сессия шага»).

## Origin и первый клон

Bootstrap env остаётся совместимым с прежними образами: новых
`BROOD_GUEST_*` переменных origin нет. Новый root supervisor при загрузке
получает `{"origin":"...","mode":"gateway|direct"}` через
`GET /api/proxmox/workspace/{uid}/{generation}` с scoped guest token и
проверкой TLS. Пустой origin возвращается вместе с пустым mode. Путь,
поколение, активная привязка роя и namespace проверяются как при доставке
проектных секретов; пользовательская cookie не заменяет guest token.
Supervisor проверяет HTTPS origin, отсутствие credentials/query/fragment,
DNS-имя и лимит 1024 байта. Direct host обязан входить в
`BROOD_GUEST_ALLOWED_HOSTS`. Неверный ответ останавливает загрузку до актора.
Старый guest image нового endpoint не вызывает: он продолжает загружаться,
но не клонирует origin. Для clone нужен новый образ; наличие origin в панели
само по себе не подтверждает, что старый образ создал checkout.

Вместе с origin сервер отдаёт Git-идентичность актора (#249):
`"gitIdentity":{"name":"brood <актор>","email":"<актор>@<домен>"}`, домен —
настройка установки `BROOD_ACTOR_GIT_DOMAIN` (`.env` сервера, без дефолта в
коде, `docs/DEPLOY.md`). Идентичность названа актором, а не проектом: по
истории видно, какой актор сделал коммит, а домен принадлежит установке, не
репозиторию, поэтому в Broodfile её нет. Без настройки поля нет, и гость
ничего не пишет; без origin поля тоже нет: клона, куда её писать, не будет.
Supervisor принимает ровно объект из двух строк: имя до 128 байт UTF-8 без
управляющих символов, `<`, `>` и пробелов по краям, адрес `local@domain`
видимым ASCII до 254 байт с DNS-доменом в нижнем регистре; иное — отказ
загрузки, как неверный origin. Старый сервер поля не отдаёт, новый гость
ведёт себя как прежде.

Тот же ответ несёт модели Claude Code установки (#263):
`"models":{"model":"glm-5.3","smallModel":"glm-5.3-flash"}`, только заданные
имена; в отличие от идентичности — и без origin, потому что Claude
запускается в каждом акторе. Значения и окружение — «Модели Claude Code
актора».

Origin не секрет, но env приложения фиксирован и не расширяется из browser attach.
Поэтому root supervisor до запуска актора пишет пару в
`/run/brood/workspace-origin.json` (root:1000, 0440, рядом с проекцией
секретов), а UID 1000 wrapper `--brood-guest-app` читает его без symlink и с
той же проверкой; идентичность и модели едут в том же файле. Каждый start
CT пишет файл заново: сервер пересчитывает режим при каждом start.

Клонирует wrapper при старте приложения, до файловых секретов, и только
если `/workspace/project` пуст. `gateway` — `git clone
http://127.0.0.1:8318/origin.git`, `direct` — `git clone <origin>` через
egress proxy. Remote `origin` клона указывает на тот URL, через который
клонировали, поэтому fetch и push идут тем же путём; канонический origin
записывается в `git config brood.origin`, идентичность — в `user.name` и
`user.email` того же `.git/config` клона, не в home: Git актора и helper
читают home без конфигурации (`GIT_CONFIG_GLOBAL=/dev/null`), а клон — его
рабочая копия. Git запускается без системной и
пользовательской конфигурации, без credential helper, prompt и redirects,
только с протоколом `http` (gateway) или `https` (direct).

Git получает отдельный приватный staging-каталог в `~/.config/brood`, а не
живой workspace: при неудаче сам Git может рекурсивно удалить destination.
После успешного клона и записи `brood.origin` wrapper заново проверяет пустоту
workspace и переносит записи через `renameat2(RENAME_NOREPLACE)`, `.git` —
последней. Конкурентная запись не перезаписывается; частичная публикация
оставляет маркер и требует явного reset. Staging и workspace должны быть
на одной файловой системе, как в образе brood. Обычная ошибка удаляет только
созданный staging; после SIGKILL его остаток не публикуется и не даёт права
очищать workspace.

Ошибка клона — одна строка причины в терминале сессии; Claude всё равно
запускается. Следующий старт повторяет клон только при пустом workspace.
Непустой каталог не очищается автоматически даже после ошибки Git или при
маркере `~/.config/brood/workspace-clone.pending`: там могла появиться работа
между попытками или во время клонирования. После прерывания оператор явно
подтверждает reset, если требуется заново создать рабочую копию. Клоны
сериализуются flock; маркер не является разрешением на удаление данных.

### Git gateway

В режиме `gateway` root supervisor слушает `127.0.0.1:8318` (рядом с model
gateway на 8317; nft пропускает UID 1000 к этому порту только по loopback).
Принимаются только Host `127.0.0.1:8318` и пути
`/origin.git/info/refs` (GET, query ровно `service=git-upload-pack` или
`service=git-receive-pack`), `/origin.git/git-upload-pack` и
`/origin.git/git-receive-pack` (POST, без query). Dumb HTTP, другие
репозитории, percent-encoded пути, `Origin` header и тело у discovery —
отказ до сервера.

Запрос уходит на `https://<хост relay>/api/proxmox/git/<uid>/<generation>/<op>`
с scoped relay token в `Authorization: Bearer`. Authorization, cookies и
прочие заголовки актора отбрасываются; передаются только `Accept`,
`Content-Type`, `Content-Encoding`, `Git-Protocol`, обратно — `Content-Type`,
`Content-Encoding`, `Cache-Control`. Redirect — 502, 401/407 сервера —
403, чтобы Git актора не спрашивал пароль. Тела идут потоком в обе стороны
без буфера model gateway: upload-pack до 64 MiB, receive-pack до 1 GiB,
весь запрос до 30 минут, одновременно не более четырёх запросов. Учётные
данные Git (проектный credential или remote) остаются на сервере.

## Подтверждение workspace

Рой подтверждает commit workspace привязанного актора операцией
`workspace_attest` по тому же `brood-session-rpc-v1` (#183). Аргументы —
ровно `swarm`, `step` (идентификатор попытки шага), `origin`, `commit`
(полный SHA-1) и `challenge` (32 байта base64url без паддинга). Поля
идентичности в запросе нет: UID и поколение берутся из bootstrap root.
Бюджет вызова на обеих сторонах — 10 минут вместо 20 секунд.

Root supervisor берёт тот же gate, что restart: при активном rw-терминале —
отказ. Origin запроса обязан совпасть с bootstrap origin актора. Затем
runtime останавливает **весь** актор: holder, ttyd, Claude и любые процессы
UID 1000 снимаются тем же SIGKILL-sweep, что при остановке CT. Остановки
одной сессии мало: процессы UID 1000 могут трассировать друг друга, а
демон с `setsid` вне `/workspace/project` пережил бы её. Недоказанная
остановка — отказ, runtime завершается с сохранённым enforcement; неудачный
перезапуск актора тоже завершает runtime.

Пока процессов UID 1000 нет, root запускает фиксированный
`--brood-guest-session` с внутренней операцией `workspace_checkout`; с relay
она отклоняется. Helper:

- проверяет репозиторий как `recycle`, дополнительно отвергает
  `.git/info/attributes` и gitlink в индексе; при идентичности из bootstrap
  записанные `user.name` и `user.email` обязаны ей равняться. Другая
  идентичность — отказ с причиной до эффекта, как локальные изменения:
  checkout не переписывает молча то, что записал актор, а оператор видит
  в `detail` шага, что клон подписывал другим именем. Актор снимает ключи
  сам или оператор делает reset; смена `BROOD_ACTOR_GIT_DOMAIN` поэтому
  требует reset акторов с прежней идентичностью. `workspace`, `wipe` и
  `recycle` идентичности не знают и принимают любые значения этих ключей,
  как с #125: allowlist ключей не ослаблен, значение проверяет только
  checkout;
- после проверки чистоты, до fetch, записывает идентичность в `.git/config`
  клона (клон до #249 получает её первым подтверждением; отказ записи —
  «HEAD and files unchanged»);
- сравнивает дерево с `HEAD` по содержимому через временный индекс: stat-кэш,
  assume-unchanged и skip-worktree не прячут изменения, excludes и attributes
  из home актора отключены. Сравнение побайтовое: атрибуты читаются из пустого
  дерева (`git --attr-source`), поэтому `.gitattributes` самого дерева
  (`ident`, `text`, `eol`, `working-tree-encoding`, `filter`) ничего не
  преобразуют, и правка внутри `$Id: ... $` или CRLF вместо LF видна.
  `core.attributesFile` этого не даёт: по gitattributes(5) у него низший
  приоритет. Staged, изменённые tracked и видимые untracked — отказ, ничего
  не меняется;
- получает commit из источника, выбранного root: gateway
  `http://127.0.0.1:8318/origin.git` или direct origin через egress proxy.
  Сначала по SHA, затем ветками в `refs/remotes/origin/*`; без tags, hooks,
  gc и redirects;
- сам хэширует commit, корневое дерево и все деревья и blob снимка: Git не
  перепроверяет blob при чтении, подложенный объект иначе попал бы в дерево;
- выполняет `checkout --detach --no-overwrite-ignore`, без `--force`: ветки,
  commits и untracked не удаляются, ignored-файл на tracked-пути — отказ.
  Файлы пишутся байтами commit, без преобразований;
- проверяет, что `.git/HEAD` — ровно этот commit, индекс равен дереву
  снимка, содержимое совпадает и видимых untracked нет.

Проект с `* text=auto` на Linux не преобразуется и подтверждается. Клон,
который обычный checkout преобразовал (`ident`, `eol=crlf`,
`working-tree-encoding`), с байтами commit не совпадает: отказ с пометкой
о побайтовом сравнении, ничего не меняется. `--attr-source` требует Git
2.42+ (в образе — Git Debian trixie); старый Git отвергает опцию, а не
молча её пропускает, как `GIT_ATTR_SOURCE`. Окружение и флаги Git у helper
те же, что у `workspace`, `wipe` и `recycle` (`gitEnv`, `gitFlags`), кроме
`--attr-source`: эти операции показывают и восстанавливают клон в виде самого
проекта, с его `.gitattributes`.

После окна root перезапускает актора и сессию Claude, и только при успехе
всего подписывает. Ключ — `HMAC-SHA256(guest token,
"brood/proxmox/workspace-attestation/key/v1")`, подпись — base64url
`HMAC-SHA256` от `brood/proxmox/workspace-attestation/v1`, UID, поколения,
`swarm`, `step`, `origin`, `commit`, `challenge` через NUL. Сервер вычисляет
guest token из relay secret, новых секретов нет. Ответ — JSON с этими
полями и `signature`; любой отказ подписи не несёт.

Сервер проверяет ответ пакетом `proxmox/attest`. `Registry.Issue` выдаёт
challenge из crypto/rand, живущий 15 минут; новая выдача для той же попытки
шага вытесняет прежнюю, число ожидающих ограничено. `Consume` сжигает
challenge до проверки: повтор, подделка и опоздание его не воскрешают.
Ключ выводится из выданных UID и поколения, не из присланных: ответ другой
инкарнации — `ErrIncarnation`, чужое поле — `ErrMismatch`, подпись —
`ErrSignature`. Выданные challenge хранятся в памяти сервера: перезапуск
отвергает все прежние ответы, а схема SQLite challenge не хранит.

Доставка шага (#212) зовёт `workspace_attest` после зафиксированного резерва
попытки: шаг `attesting` с UID, инкарнацией и `request_id` (он же `step`
запроса) и workspace-lease `workspace_attest`, исключающий restart, wipe,
recycle и dispatch к актору. Перед вызовом сервер заново проверяет, что шаг
всё ещё `attesting` этой попытки: остановленный за время ожидания relay рой
гостя не трогает. Ответ принимается, только если его `challenge` выдан этой
попытке, и challenge живёт один вызов: отказ, мусор и потерянный ответ его
сжигают (`Registry.Revoke`). `Consume` идёт до транзакции записи, которая
заново проверяет инкарнацию и привязку роли, origin и commit снимка и
переводит шаг в `delivering`; только после неё уходит инструкция. Отказ
гостя или подписи, ответ другой попытки — шаг `refused` с причиной, lease
отпущен; потерянный ответ — `unconfirmed`, lease остаётся неподтверждённым
до явного освобождения. Подтверждение отвечает, как только сессия запущена,
не дожидаясь её inbox: инструкцию, которую гость ещё не может отправить
(`notSent`, «Приём сообщений в госте»), сервер повторяет сам (#244).
Порядок и состояния — [MODEL.md](MODEL.md), «Шаг актора».

Подтверждение утверждает состояние в окне тишины, не позже. Файлы, скрытые
правилами ignore (артефакты сборки, файловые секреты проекта), в
утверждение не входят, кроме путей настройки Claude Code (ниже, «Сессия
шага»). Операция рвёт терминалы и перезапускает сессию, как restart. Нужен
новый brood-guest; прежний отвечает `unsupported`, и шаг не доставляется.

### Сессия шага

Сессия, которую запускает подтверждение, — сессия шага (#224, решение
оператора 2026-11-11): код, сохранённый актором в `/workspace/home`, с ней
не стартует, ни до доставки инструкции, ни во время шага. После
проверенного checkout, ещё в окне тишины, root:

- пишет `/run/brood/step-gitconfig` (root:1000, 0440) — всю глобальную
  конфигурацию Git сессии: `user.name` и `user.email` идентичности #249, без
  `core.fsmonitor`, `core.hooksPath`, фильтров и include; без идентичности
  файл пуст;
- пишет drop-in управляемых настроек Claude Code
  `/etc/claude-code/managed-settings.d/brood-swarm-step.json` (root 0644 в
  каталогах root 0755) с `allowManagedHooksOnly: true`,
  `skipDangerousModePermissionPrompt: true` и автономным профилем
  (`crossSessionInbound`, `feedbackDrafts`, `permissions.deny`, «Автономный
  профиль», #164) и ничем больше: ни hooks, ни `env`, ни MCP, ни plugins;
  базовый `managed-settings.json` не трогается. Путь в закреплённой 2.1.310
  фиксирован: переопределение `CLAUDE_CODE_MANAGED_SETTINGS_PATH` из
  публичной сборки вырезано;
- переименовывает `~/.bash_profile`, `~/.bash_login`, `~/.profile`,
  `~/.bashrc` и `~/.bash_logout` в `<имя>.brood-<время UTC>` рядом, с
  номером, если копия того же момента уже есть. Так они приводятся к образу,
  где их нет: актор создан с `--no-create-home`, и bash читает только
  `/etc/profile` и `/etc/bash.bashrc`. Rename не читает содержимое, не идёт по
  symlink и ничего не теряет;
- последней пишет отметку `/run/brood/step-session.json` (root:1000, 0440).

Отказ любого пункта снимает уже записанное, подписи нет. Отказ проверки
(локальные изменения, другой commit) запускает свободную сессию. Режим лежит
в `/run/brood`, а не в home: это решение root, UID 1000 там ничего не создаёт
и не удаляет.

App wrapper читает отметку перед запуском Claude: нет отметки — свободная
сессия, отметка не того владельца, режима или содержимого — отказ запуска. В
сессии шага он сначала переименовывает `~/.claude/.config.json` и
`~/.claude/remote-settings.json` в `<имя>.brood-<время UTC>` рядом, как
rc-файлы. Claude Code 2.1.310 применяет `env` обоих при любом
`--setting-sources`: `.config.json` — устаревшее место глобальной
конфигурации, и непустой обычный файл (в том числе по ссылке) Claude читает
вместо `~/.claude.json`; `remote-settings.json` — кэш управляемых настроек с
сервера, который Claude ставит вместо drop-in brood, когда сессия для них
подходит. С `ANTHROPIC_BASE_URL` brood она не подходит, но признак зависит и
от входа, сохранённого в home. После переноса глобальная конфигурация —
только `~/.claude.json`; член `env` из него уходит в
`~/.claude.json.env.brood-<время UTC>` (ссылка или не-объект — отказ
запуска, `~/.claude` ссылкой или чужим каталогом — тоже). Выбор файла и
применение `env` проверены запуском закреплённого бинарника без сети против
локального фальшивого API. Затем wrapper запускает
`claude --dangerously-skip-permissions --setting-sources project
--strict-mcp-config --mcp-config ...` с `GIT_CONFIG_GLOBAL` на файл root и
`SHELL=/bin/bash` поверх окружения свободной сессии. Имена ключей и флагов
сверены с документацией Claude Code и строками закреплённого бинарника.
Закрыто:

- hooks пользователя, проекта, локальных настроек, plugins и frontmatter
  агентов, monitors plugins; `statusLine`, `subagentStatusLine` и
  `fileSuggestion` берутся только из управляемых настроек
  (`allowManagedHooksOnly`), а управляемых hooks brood не ставит;
- `~/.claude/settings.json` и `.claude/settings.local.json` не читаются
  (`--setting-sources project`): их `env` (`PATH`, `GIT_CONFIG_*`,
  `LD_PRELOAD`, `BASH_ENV`), `apiKeyHelper`, `enabledPlugins` иначе обошли бы
  остальные пункты. Пользовательские skills, agents и `~/.claude/CLAUDE.md`
  в сессии шага не загружаются;
- настройка проекта приходит из подтверждённого commit. С
  `--setting-sources project` Claude читает `.claude/settings.json`
  (`env`, `enabledPlugins`, permissions), `CLAUDE.md`, `.claude/CLAUDE.md`,
  `.claude/rules`, agents, skills и commands, вложенные — когда модель
  заходит глубже, и правила ignore ему безразличны. Поэтому checkout
  подтверждения считает локальным изменением ignored-файл на путях
  настройки Claude на любой глубине: каталоги `.claude`, `.claude-plugin`,
  `.mcpb-cache` и файлы `CLAUDE.md`, `AGENTS.md`, `.mcp.json`,
  `.claude.json`, `.lsp.json`, `.worktreeinclude` (собственный список путей
  настройки закреплённого Claude). Каким правилом файл скрыт — `.gitignore`,
  `.git/info/exclude` или блоком `claude-code-runtime`, который Claude сам
  дописывает туда для своего состояния, — не важно; отказ ничего не трогает,
  файл остаётся у актора. Файловый секрет проекта — тоже ignored-файл:
  на этих путях он отказывает подтверждению, а `.claude`, `.mcp.json` и
  `CLAUDE.md` projectsecret и так не принимает. Вне утверждения остаются
  `.claude/settings.local.json` и `CLAUDE.local.md`: сессия шага их не
  читает. Commit со ссылкой на этих путях (например, `.claude` в home)
  checkout отвергает до перемещения HEAD. Что Claude читает, а что нет,
  проверено запуском закреплённого бинарника без сети;
- MCP — только brood (`--strict-mcp-config`): серверы `~/.claude.json`,
  `.mcp.json` и frontmatter агентов не стартуют;
- глобальная конфигурация Git Claude и его команд — файл root
  (`GIT_CONFIG_GLOBAL`): `~/.gitconfig` и `~/.config/git/config` не
  читаются, пока `env` проектного `.claude/settings.json` подтверждённого
  commit не задаст `GIT_CONFIG_*` сам (это видно в commit). `.git/config`
  клона checkout уже проверил по allowlist;
- снимок shell (`$SHELL -c -l` с `source ~/.bashrc`) читает только файлы
  образа; `SHELL` закрепляет bash, даже если в образе появится zsh.

Режим держится до перезапуска вне шага. Restart и recycle снимают отметку,
drop-in и файл Git до остановки старой сессии; отказ снятия — «session
unchanged». Отметка снимается первой; если она не снялась, drop-in и файл
Git остаются на месте, так что отметка без `allowManagedHooksOnly` не
бывает. Старт runtime снимает их до запуска актора: `/etc` переживает
перезапуск CT. `/etc/claude-code` или его `managed-settings.d` ссылкой, не
root или с записью для группы и прочих — отказ старта с путём и причиной,
даже если шагов ещё не было, как на `/workspace`, который пишут другие: кто
пишет этот каталог, задаёт управляемые hooks и `env`, которые сессия шага
сохраняет. Нужны каталоги root с режимом 0755; отсутствующий каталог —
не отказ. Сессия, которую holder поднимает заново внутри шага
(`ensure`), остаётся сессией шага. Перенесённые rc-файлы, файлы `~/.claude`
и `env` назад не возвращаются: актор берёт их из копий сам. Свободная сессия
запускается как до #224: hooks, MCP, настройки, `~/.gitconfig` и rc актора
работают.

Остаётся открытым:

- модель сама меняет дерево и home: это её работа, видимая в транскрипте.
  Она может вернуть rc-файлы, вызвать код из home командой или выполнить
  `git commit` с hooks `.git/hooks` клона; следующий шаг проверит дерево
  заново;
- проектные настройки и CLAUDE.md подтверждённого commit сами могут
  сослаться за его пределы: `@`-импорт CLAUDE.md подгружает указанный файл
  как инструкцию, `env` может задать `GIT_CONFIG_*` или `BASH_ENV`. Это
  содержимое commit, видимое в его diff;
- plugins, которые включают проектные настройки, могут загрузить из
  `~/.claude/plugins` skills и LSP-серверы; hooks и monitors не загружаются;
- restart или recycle посреди шага, в том числе гостевой `restart` самой
  модели, возвращает свободную сессию до следующего подтверждения;
- повторной проверки дерева непосредственно перед доставкой (вариант 3
  разбора #224) нет.

## Приём сообщений в госте

Гостевой relay обрабатывает входящий `brood-swarm-msg` отдельно от терминала:
до восьми доставок, не более 128 KiB на запрос и ответ, ожидание до 300 секунд.
Закрытие канала или SSH-сессии отменяет доставку. Root supervisor не читает
actor-owned session files и не открывает указанные в них сокеты. Он запускает
только собственный проверенный бинарник с фиксированным
`--brood-guest-message`, UID/GID 1000, без supplementary groups и bootstrap env.
Helper проверяет личность, сбрасывает capabilities и устанавливает NoNewPrivs
до чтения `~/.claude/sessions` и обращения к Unix-сокетам.

Получатель выбирается по единственной живой сессии `/workspace/project`.
Конверт заявляет `from-mode="bypass"`: managed Claude запускается с
`--dangerously-skip-permissions`. Сессия любого режима принимает его с
`crossSessionInbound: "accept"` («Автономный профиль»), поэтому ни
`mode-mismatch`, ни `no-mode-asserted`, ни `mode-unknown` сразу после старта
не ставят сообщение в диалог Deliver/Deny; удержать его может только
проектная настройка `hold`. Peer key передаётся первым кадром; обратный
сокет создаётся рядом с inbox, принимает квитанции только своего UID,
ограничивает их размер и сверяет `orig_msg_id`. `notify_when_idle` имеет
отдельный идентификатор.

`delivered` возвращается только по явной совпавшей квитанции. `held`, `denied`,
`refused`, `expired`, `dropped` остаются отрицательными вердиктами. Запись кадра
без квитанции даёт `submitted; delivery unconfirmed`, даже если отдельно
подтверждён idle: ни доставка, ни попадание в очередь этим не доказаны.
Автоматический повтор после такого результата может создать дубликат.

Квитанцию `peer_message_status` Claude Code шлёт, когда сессия приняла
сообщение, а не вместе с записью: прежних 250 мс не хватало, и доставленные
шаги и ответы оператора выглядели неподтверждёнными (#245, #260). Без
ожидания простоя (`waitSec` 0: шаг роя, ответ на запрос, `send` по умолчанию)
helper ждёт квитанцию до 15 секунд (`command.ReceiptWait`) и отвечает сразу,
как придёт квитанция или отказ; не дождавшись — `submitted; delivery
unconfirmed` без ошибки канала. С ожиданием простоя квитанция ждётся в том же
окне `waitSec`, как прежде, и предел квитанции его не удлиняет. 15 секунд с
запасом покрывают квитанцию сессии, которая приняла сообщение, и держат ответ
оператора на запрос роя в пределах 20 секунд. Сессия, занятая длинным ходом,
может не подтвердить и за это время: её исход остаётся неизвестным, ждать её
весь ход доставке не нужно.

Пределы вложены, чтобы ожидание квитанции не стало обрывом канала: Exchange
кончается через ожидание (квитанции или простоя) плюс 5 секунд на подключение
и запись (`ccmsg.WriteTimeout`), supervisor убивает helper через ожидание плюс
10 секунд, relay гостя держит канал ожидание плюс 15 секунд
(`command.CallTimeout`: 30 секунд без простоя). Тот же предел у каждого звена
гостевой команды — MCP-адаптера, `bro --guest`, broker гостя и relay сервера,
поэтому неподтверждённая квитанция доходит до отправителя вердиктом. Сервер
ждёт доставку шага и ответа на запрос дольше канала (`requestDeliveryTimeout`,
40 секунд; [MODEL.md](MODEL.md), «Запросы роя»).

Отказ до записи кадра в inbox помечен в ответе `"notSent": true` (#244):
supervisor не запустил helper (не root, неверный запрос, helper недоступен),
helper не прошёл проверку личности, не нашёл единственной живой сессии
`/workspace/project` (так бывает сразу после `workspace_attest` и restart:
новая сессия ещё не записала файл и не слушает inbox), не нашёл ключа peer
или `ccmsg.Exchange` отказал до записи (`ccmsg.ErrNotSent`: неверный ввод,
обратный сокет, inbox не принял соединение). Такое сообщение заведомо не
ушло, и повтор дубля не создаёт. Ошибка записи, оборванный helper, мусор в
ответе и всё после записи поля не несут: исход неизвестен. Поле
необязательное: ответ без него — прежний вердикт неизвестного исхода, и
сервер, и прежний гость читают друг друга как раньше. Повторяет такие
отказы только доставка шага роя ([MODEL.md](MODEL.md), «Шаг актора»).

Claude получает дополнительный MCP-сервер `brood` через `--mcp-config`, без
перезаписи пользовательских MCP-настроек. Инструменты `agents` и `send` используют
локальный root-owned broker; credentials остаются у supervisor. Сервер
выводит отправителя из текущей SSH identity и ограничивает список и доставку
managed-акторами того же роя. Native-акторы пока не адресуются этим каналом.
Протокол, ограничения и проверка описаны в [MCP.md](MCP.md).

## Серверный шлюз моделей

Managed-доступ к CLIProxyAPI требует `CLIPROXY_URL` и отдельного серверного
`CLIPROXY_API_KEY`. Это клиентский ключ прокси, не management key. Его значение
остаётся только у сервера; root supervisor гостя использует свой scoped relay
токен текущего UID/поколения. Для proxy с частной цепочкой TLS
`CLIPROXY_CA_PEM_B64` задаёт доверенные PEM-сертификаты в base64: доверие
проверяется явно, `InsecureSkipVerify` не используется. Для публичной цепочки
переменная не нужна. Эти корни применяются только к CLIProxyAPI backend.

Если акторы должны использовать другой proxy (например, существующий сервер
mop), задаются `BROOD_ACTOR_LLM_URL`, `BROOD_ACTOR_LLM_API_KEY` и, для частной
TLS-цепочки, `BROOD_ACTOR_LLM_CA_PEM_B64`. Origin обязан быть HTTPS, ключ —
явным и непустым. Эта настройка применяется только к managed-маршрутам:
`CLIPROXY_URL`, public `/v1/` и management-панель остаются на прежнем backend.
Без override используются общие настройки CLIProxyAPI выше. Accounts,
OAuth-файлы и список ключей чужой установки автоматически не переносятся.

Machine endpoints:

- `GET /api/proxmox/llm/<uid>/<generation>/v1/models`;
- `POST /api/proxmox/llm/<uid>/<generation>/v1/messages`;
- `POST /api/proxmox/llm/<uid>/<generation>/v1/messages/count_tokens`.

Для pinned Claude Code 2.1.310 оба gateway допускают только канонический
`limit=1..1000` у каталога и точный `beta=true` у messages/count_tokens.
Остальные, повторные и percent-encoded query-параметры отвергаются;
разрешённый query сохраняется до upstream. Проверка настоящим CLI в
контейнере без сети включает catalog discovery, synthetic SSE и раскрытие
`mcp__brood__agents`/`mcp__brood__send` через встроенный ToolSearch.
Модельные ответы этой проверки фиксированные, реальный provider не вызывается.

Сервер проверяет текущий start/running intent перед запросом, подставляет
серверный ключ и направляет запрос только в настроенный CLIProxyAPI origin.
Cookies, forwarded identity, management headers и guest Authorization upstream
не передаются. Отдавать `Set-Cookie`, следовать redirects или обращаться к
management paths через этот шлюз нельзя. Публичный `/v1/` сохраняет прежнюю
авторизацию клиентским ключом и не получает серверный ключ из этого маршрута.

Тело ограничено 8 MiB и 30 секундами чтения; ожидание response headers —
30 секунд, весь запрос — 30 минут. SSE передаётся без буферизации. Разрыв
клиентского соединения отменяет upstream; stop/reset отзывает новые запросы
сразу, уже открытый поток отменяется при проверке авторизации раз в секунду.
Наличие серверного шлюза само по себе не настраивает proxy внутри старого гостя.
Изменение guest image не должно уничтожать workspace работающего актора.

## Модели Claude Code актора

Модели — настройки установки в `.env` сервера, без дефолта в коде и каждая
сама по себе (`docs/DEPLOY.md`): `BROOD_ACTOR_MODEL` — основная,
`BROOD_ACTOR_SMALL_MODEL` — быстрых задач, например `glm-5.3` и
`glm-5.3-flash`. Имя — от 1 до 256 байт печатаемого ASCII без пробелов
(пакет `actormodel`); иное — отказ старта сервера и выкладки с именем
настройки. Сервер отдаёт заданные имена в ответе workspace (см. «Origin и
первый клон»), а не в bootstrap env: прежние образы отказывают в загрузке на
незнакомое `BROOD_GUEST_*` имя. Supervisor принимает ровно непустой объект
из `model` и `smallModel` строками той же формы; иное — отказ загрузки, как
неверный origin. Wrapper `--brood-guest-app` добавляет их к окружению Claude
Code (закреплённая 2.1.310) после проектных секретов, которым имена
`ANTHROPIC_*` запрещены:

| Настройка | Переменные Claude Code |
|---|---|
| `BROOD_ACTOR_MODEL` | `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_OPUS_MODEL`, `ANTHROPIC_DEFAULT_SONNET_MODEL` |
| `BROOD_ACTOR_SMALL_MODEL` | `ANTHROPIC_DEFAULT_HAIKU_MODEL` |

`ANTHROPIC_MODEL` — модель сессии; при следующем запуске она сильнее выбора
`/model`, сохранённого в home актора. Псевдонимы `opus` и `sonnet` закрывают
`opusplan`, `model` в определениях агентов и параметр модели Agent tool;
`haiku` Claude Code берёт и для фоновых задач, поэтому устаревший
`ANTHROPIC_SMALL_FAST_MODEL` не нужен. Подагент без своей модели наследует
модель сессии, поэтому `CLAUDE_CODE_SUBAGENT_MODEL` не задаётся: малая модель
в нём молча понизила бы делегированную работу. `ANTHROPIC_DEFAULT_FABLE_MODEL`
тоже не задаётся: имя из неё Claude Code считает моделью Fable (подпись,
промпт, fallback) и назвал бы так основную модель. Явный выбор `fable` или
`best` поэтому уходит к имени Claude и без его ключей в proxy получает отказ.

Окно контекста модели установки гость не задаёт
(`CLAUDE_CODE_MAX_CONTEXT_TOKENS`, «Автономный профиль»): для имени не
`claude-*` Claude Code считает 200000 токенов.

Без настроек поля нет, окружение Claude прежнее и модель выбирает Claude
Code; старый сервер поля не отдаёт, и новый гость ведёт себя так же. Задана
только одна настройка — вторая группа остаётся выбором Claude Code; для
провайдера без моделей Claude нужны обе. Строгий разбор ответа — у
runtime-гостя, которого bootstrap качает с сервера (#155); CT шаблона до
#155, чей встроенный гость уже читает workspace, при заданных моделях
отказывает в загрузке.
Supervisor читает ответ при старте CT, wrapper — файл при старте Claude:
смена настроек доходит до актора со следующим стартом CT, restart и recycle
сессии её не перечитывают.

## Origin актора и серверный шлюз Git

Managed-актор хранит неизменяемый `origin` — HTTPS URL Git-репозитория,
который гость клонирует в пустой `/workspace/project`. Пустой origin — пустой
workspace, как раньше. Origin задаётся при создании: поле `origin` в
`POST /api/swarms/{id}/actors` (только managed; native-актор с этим полем
получает 400) или `add NAME --origin URL` у master. Без origin worker,
созданный master, наследует origin master; иначе берётся repository проекта;
иначе workspace пустой. JSON актора содержит `"origin"` и `"originMode"`:
`gateway`, `direct` или `""`.

Каноническая форма (пакет `gitorigin`): только `https://`, hostname DNS
(не IP и не числовая запись вроде `127.1`), порт отсутствует или 443,
непустой путь из сегментов `[A-Za-z0-9._~-]` без `.`/`..`, без userinfo,
query, fragment, percent-encoding и управляющих символов, не длиннее 1024
байт; host в нижнем регистре, без завершающего `/`. Хранится только
каноническая форма; отказ называет правило и не повторяет значение.

Режим вычисляется заново при чтении, на каждом start и на каждом запросе
шлюза:

- `gateway` — origin в точности равен repository проекта, и у сервера есть
  доступ к нему: активный проектный Git credential (ссылка декларации на
  credential, привязанный ровно к этому repository, [SECRETS.md](SECRETS.md))
  или remote `BROOD_GIT_REMOTES`;
- `direct` — host origin точно входит в публичный allowlist гостя
  (`github.com`, `gitlab.com` и т.д.), клон идёт через egress proxy гостя;
- иначе создание отказывает 422 до резервирования, а не создаёт пустой
  workspace молча.

На каждом старте гостя supervisor заново получает origin и режим через
авторизованный workspace endpoint. Если origin потерял режим (repository
проекта сменился, remote убран, проектный credential удалён или отвязан),
сервер возвращает оба поля пустыми: гость не клонирует, шлюз отказывает.
Bootstrap env не расширяется, учётные данные в гостя не попадают. Схема SQLite
10 добавляет `managed_actors.origin` и таблицу `project_repositories`
аддитивно: прежние акторы получают пустой origin. Схема 20 добавляет таблицы
`project_git_credentials` и `project_git_credential_refs`; миграции нет, база
прежней версии отвергается и создаётся заново.

### Remotes установки и repository проекта

`BROOD_GIT_REMOTES` — секрет установки в `.env`: JSON-объект, ключ —
канонический HTTPS URL репозитория, значение `{"username":"...","token":"..."}`
или `{}` (без учётных данных). Неканонический ключ, неизвестное или
регистровое имя поля, повтор, только одно из двух полей, двоеточие в
username, непечатаемые символы или более 256 remotes — отказ запуска с
именем настройки, без значений. Токен остаётся на сервере: его нет в JSON,
логах, ошибках, окружении гостя и форматировании конфигурации.

- `GET /api/git-remotes` (администратор):
  `{"items":[{"origin":"...","credentialConfigured":true}]}`;
- `GET /api/projects/{id}/repository` (участники проекта): `{"origin":""}`;
- `PUT /api/projects/{id}/repository` (администратор, same-origin, CSRF):
  совместимое тело ровно `{"origin":"..."}`; значение канонизируется,
  `""` очищает. Repository больше не обязан быть ключом BROOD_GIT_REMOTES.
  Неизвестные и регистровые варианты полей, повторы, `null`, другие типы и
  лишние документы — 400. Сессия и роль перепроверяются в транзакции записи.

Источник декларации проекта — Broodfile: `bro build` разрешает repository
из явного поля либо Git origin текущего checkout и идемпотентно
синхронизирует его через `/api/projects/sync` (`docs/BUILD.md`). Панель
показывает результат без второго редактора. Объявить URL можно независимо
от credentials, но это не даёт режима gateway: его точная проверка и
сетевые ограничения остаются прежними. BROOD_GIT_REMOTES хранит настройки
серверного доступа, а не список допустимых деклараций проекта.

Предпочтительный источник серверного доступа — проектный Git credential:
`bro secret --project P git add NAME --repository URL ...` и ссылка
`project.git_credential: NAME` в Broodfile ([SECRETS.md](SECRETS.md)).
Токен при этом не переносится в `BROOD_GIT_REMOTES` и меняется без
перезапуска сервера. Активный проектный credential имеет приоритет над
remote установки того же repository; legacy-remotes продолжают работать
как прежде.

### Шлюз

Гость не достаёт до частного Git установки: egress proxy гостя по-прежнему
отвергает private-адреса, и это не меняется. Сервер посредничает так же, как
шлюз моделей:

- `GET /api/proxmox/git/<uid>/<generation>/info/refs?service=git-upload-pack`
  или `?service=git-receive-pack` (query ровно такой);
- `POST /api/proxmox/git/<uid>/<generation>/git-upload-pack`;
- `POST /api/proxmox/git/<uid>/<generation>/git-receive-pack`.

Авторизация — ровно один `Authorization: Bearer <guest token>` той же проверки
UID, поколения, start intent, привязки роя и namespace, что у
`/api/proxmox/llm` и `/api/proxmox/secrets`; cookie панели не принимается.
Затем режим origin актора должен быть `gateway`. Upstream — `<origin>/<op>`
с Basic auth из активного проектного credential, иначе из remote. Вверх уходят только `Content-Type`, `Accept`,
`Content-Encoding`, `Git-Protocol` и фиксированный `User-Agent`; вниз —
`Content-Type`, `Content-Encoding`, `Cache-Control`. Cookies, `Set-Cookie`,
`WWW-Authenticate` и forwarded identity не проходят, redirect — 502, а не
переход. POST требует точный `application/x-git-*-request`. Тела потоковые:
upload-pack до 64 MiB, receive-pack до 1 GiB (413); весь запрос — 30 минут;
не более 4 одновременных запросов на актора (429). Stop, reset, смена
repository проекта или remote, ротация или удаление проектного credential,
снятие или смена ссылки декларации отменяют и открытый поток в течение
секунды. Тела и учётные данные не журналируются.

Транспорт шлюза не использует proxy окружения, проверяет TLS системными
корнями (не ниже 1.2) и не выполняет redirects. После разрешения DNS он не
подключается к loopback, link-local (включая metadata `169.254.169.254`),
unspecified, multicast, broadcast и reserved адресам, а также к IPv6 с
вложенным IPv4, который доставит шлюз трансляции или туннель: NAT64
(`64:ff9b::/96`, `64:ff9b:1::/48`), 6to4 (`2002::/16`), Teredo
(`2001::/32`), IPv4-compatible (`::/96`) и IPv4-translated
(`::ffff:0:0:0/96`) отвергаются целиком, каким бы ни был вложенный адрес.
Эту границу держит сам сервер, потому что проектный credential задаётся через
API, а не проверяется выкладкой. Частные адреса LAN допустимы, как и для
remotes установки; в сети только с IPv6 и DNS64 upstream нужен собственный
IPv6-адрес.

Модель доверия: **актор может читать и пушить с серверными учётными данными
ровно в repository своего проекта**, и только пока он выбран и настроен.
Любой код или модель внутри актора получает это право, включая force-push и
удаление веток, если их разрешает credential. Выдавайте remote отдельный
токен с минимальными правами одного репозитория; защита веток на Git-сервере
остаётся границей. Другой remote установки или repository другого проекта
через шлюз недоступен: upstream определяется только origin актора.

Выкладка сервера должна отдельно доставить `BROOD_GIT_REMOTES` в Secret
`brood-go-env` и разрешить egress сервера к host remotes на 443; это не
входит в серверный код. Сохранение проектного credential сетевую политику
не меняет, как и форма подключения Proxmox: egress сервера к его host на 443
должен быть разрешён отдельно. Штатная выкладка открывает egress только для
hosts ключей `BROOD_GIT_REMOTES` ([DEPLOY.md](DEPLOY.md), «Git remotes»);
ключ со значением `{}` открывает его без токена в `.env`. Без egress режим
остаётся `gateway`, но запрос шлюза завершается 502.

## Состояние, восстановление и освобождение ресурсов

SQLite хранит неизменяемые bindings, снимок одобренного шаблона, CTID,
случайный ownership nonce, поколение, desired state и журнал операций.
Резервирование коммитится **до** внешнего запроса. Provisioning, stopped,
error и неопределённые результаты продолжают занимать ёмкость; одна и та же
CTID уникальна в пределах идентичности PVE cluster, а не alias endpoint.

PVE create возвращает UPID. Потеря ответа не означает, что CT не создана:
нельзя выбрать другую CTID или повторить создание вслепую. Перезапуск сервера
принимает существующую CT только после полной проверки владельца,
unprivileged режима, storage/network/profile и членства в разрешённом пуле.
Само закрытие процесса сервера не останавливает CT.

Операция имеет отдельный durable stage/task slot. Stop task и delete task
не затирают UPID друг друга. До подтверждённого завершения текущей операции
нельзя начать другую, даже если диагностическая phase выглядит терминальной.
Reset сохраняет старую принадлежность до завершения удаления и подтверждения
отсутствия, после чего одним CAS меняет поколение/nonce и записывает новый
create intent. Ёмкость между этапами не освобождается.

Отсутствие CT в ACL-filtered inventory, HTTP 403 или HTTP 500 не доказывает,
что диск можно считать удалённым. После завершения удаления provider требует
положительную проверку глобального ID: `GET /cluster/nextid?vmid=<id>` должен
успешно вернуть именно этот свободный ID. Это наблюдение в момент проверки,
а не новая блокировка VMID на стороне PVE.

Pool drain не удаляет работающих акторов. Новые размещения и поддерживаемые
рестарты ограничиваются состоянием пула; администратор может явно включить
пул обратно. Удаление пула и роя отказывается продолжаться, пока остаются
managed allocations или неподтверждённая очистка. Увеличение доступа токена,
снятие host policy или остановка пользовательского актора не являются
автоматическим способом обойти отказ или нехватку ёмкости.
