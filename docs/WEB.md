# Web

Исходная React/TypeScript/Bun-панель сохранена в `web`: тот же frontend
CLIProxyAPI Management Center с существующими разделами, компонентами,
темами, hash-router и шестью локалями. Переезд backend на Go не заменяет
панель минимальным HTML. Соглашения frontend — `web/AGENTS.md`.

## Сборка

```sh
bin/brood dev web test
bin/brood dev web build
make -C go build
```

Обе dev-команды используют checksum-pinned Bun image из panel-стадии
`deploy/Dockerfile.go`, frozen `bun.lock` и `VERSION=v1.26.7+brood`.
Проверка включает Bun tests, ESLint, TypeScript и production Vite build.
Успешная сборка атомарно заменяет `go/brood/server/static/index.html`.
Это generated release bundle: вручную его не правят.

Bundle хранится вместе с Go-кодом и встраивается через `go:embed`, поэтому
обычные `go build`/`go test` не требуют Bun. Release/image сборка пересобирает
панель из исходников; frontend runtime/toolchain не попадает в scratch-образ.
Смена исходников панели требует новой сборки bundle до коммита.

## Зависимости

Список зависимостей `web/package.json` закрыт так же, как у Go-модуля:
новая библиотека — сначала запись здесь с причиной и ценой в bundle.

- **react-markdown 10.1.0, remark-gfm 4.0.1, rehype-sanitize 6.0.0 (#252)**
  — отчёты шагов, вопрос и материал запроса, текст ответа, задача прохода и
  инструкция узла пишутся моделями и операторами в markdown; панель его
  показывает, не исполняя. Компонент `web/src/components/ui/Markdown.tsx`
  рендерит GFM (таблицы в прокручиваемой полосе, код моноширинно с
  переносом, списки, чекбоксы задач) без `rehype-raw` и без
  `dangerouslySetInnerHTML`: HTML автора становится текстом ещё до
  `rehype-sanitize`, поэтому `<script>`, `<b>`, `<img onerror>` и
  закрывающий тег конверта `</cross-session-message>` видны буквально, а
  sanitize со схемой GitHub — вторая линия: он снимает `javascript:`-ссылки
  и атрибуты-обработчики, если они когда-нибудь дойдут до дерева. Ссылки
  открываются с `rel="noopener noreferrer" target="_blank"`; картинки не
  загружаются — вместо них подпись: отчёт не ходит во внешнюю сеть из
  панели. Заголовки понижены до `h4`..`h6`, чтобы отчёт не спорил с
  заголовками страницы. Проп `collapsible` сворачивает текст выше ~600 px с
  кнопкой «Показать полностью»; `collapsedHeight` задаёт другой порог
  (задача прохода на странице роя — две строки, #253): порог в несколько
  строк режется по строкам (`line-clamp`), без затухания и с текстовой
  кнопкой. Причина шага (`detail`) остаётся простым
  текстом, в ней моноширинно размечен только ID операции после
  `workspace operation`. Версии закреплены точно, `bun install
  --frozen-lockfile`; экосистема unified приносит 99 пакетов в lockfile.
  Bundle `go/brood/server/static/index.html`: 3 802 908 байт до,
  3 980 093 после (+177 185, 4,7 %; gzip 1 143 841 → 1 196 749,
  +52 908). Проверки — `web/tests/markdown.test.ts`.

## Дизайн-токены

Токены живут в `web/src/styles/themes.scss`: три блока (`:root` светлая,
`[data-theme='white']`, `[data-theme='dark']`) переопределяют цвета, шкала
типографики объявлена один раз в `:root`. Модули стилей берут токены, не
числа; новый размер шрифта или цвет -- сначала токен, потом применение.
Проверка -- `web/tests/themeTokens.test.ts`: чистая функция читает
`themes.scss`, раскрывает `var()` и считает контраст WCAG по парам, так что
падение контраста ловится до сборки bundle, а не Lighthouse на стенде.

- **Шкала** `--fs-12`…`--fs-28` и `--lh-12`…`--lh-28`: шесть размеров
  (12/13/14/16/20/28 px), у каждого одно межстрочное в пикселях. 12 --
  подписи, бейджи, заголовки колонок; 13 -- текст таблиц, форм и пояснений;
  14 -- заголовки секций и действия; 16 -- заголовки карточек и диалогов,
  имя карточки на телефоне; 20 -- заголовок страницы на телефоне; 28 --
  заголовок страницы. `--measure: 72ch` ограничивает ширину пояснений и
  текста в карточках. Темы шкалу не переопределяют.
- **Текст** `--text-primary`/`--text-secondary`/`--text-tertiary`: каждая
  ступень не ниже 4,5:1 на странице (`--bg-secondary`) и на карточке
  (`--bg-primary`) во всех трёх темах; `--text-quaternary` -- только для
  декора (точки, контуры), не для слов. `--primary-color` тоже пара текста:
  ссылка на странице и подложка кнопки под `--primary-contrast`; в тёмной
  теме текст кнопки тёмный, потому что кнопка светлеет при наведении.
  Заголовки групп меню -- 11 px и `--text-secondary` (`layout.scss`).
- **Карточки** двух уровней: `--card-bg`/`--card-border` -- карточка и
  таблица, `--card-inset-bg`/`--card-inset-border` -- блок внутри карточки
  (`.notice`, `.code`, группа необратимых действий). В светлой теме
  вложенный блок светлее карточки, как поле формы; в тёмной -- светлее,
  ближе к зрителю. Вложенность читается цветом, не количеством рамок.
- **Бейджи** -- четыре семантических тона, словарь в
  `web/src/features/access/state.ts` (`BADGE_TONES`, `swarmTone`,
  `executionTone`, `roleTone`, `requestTone`, `deliveryTone`,
  `substrateTone`): `attention` ждёт человека (waiting, open запрос, unbound
  роль, неподтверждённый исход), `progress` -- система работает (running,
  provisioning, доставка), `problem` -- встало (error, failed, crashed,
  сломанная привязка), `neutral` -- ничего не требует (active рой, ready роль,
  answered, stopped, succeeded). Тон отвечает «надо ли смотреть», а не
  называет состояние, поэтому здоровое состояние покоя не красится. Цвета --
  `--<тон>-badge-bg/-fg/-border`; текст на две ступени темнее оттенка, пара
  не ниже 4,5:1. Классы `.tone-<тон>` -- в `substrate.module.scss`,
  компонент -- `StatusBadge`/`StateBadge`.
- **Граф** (`features/pipelines/pipelines.module.scss`): состояния узлов и
  таймлайна -- переменные `--pip-*`, под svg одна легенда `.graph-legend`
  (`legend.ts`): виды узлов с особым контуром, когда их больше одного, и
  состояния, которые проход уже раздал; графу без состояний и с одним видом
  узлов легенда не рисуется.

## Новые сущности

Существующие страницы providers, auth files, OAuth, quota, logs, config,
plugins, actors, templates, workers, worker pools и policy сохранены.
В том же интерфейсе добавлены:

- **Пользователи:** список, создание, редактирование и удаление; роль,
  отображаемое имя и блокировка — свойства одной формы. Username существующей
  записи неизменяем. Сохранение атомарное; изменение роли/блокировки отзывает
  сессии. Сброс пароля — отдельное действие. Последнего активного администратора
  нельзя удалить или лишить прав. Владельца живых роёв нельзя удалить, пока
  рои не переданы или удалены.
- **Проекты:** создание/удаление и явная кнопка «Выбрать». Выбор задаёт
  единственный глобальный контекст панели; в переключателе только проекты,
  без ссылки на управление ими. «Сведения о проекте» (`/projects/:project`)
  показывает резервирование и пределы шарда, обязательные метки воркеров,
  репозиторий, каталог определений (#240) и состав проекта. Смена проекта из
  шапки обновляет URL деталей.
- **Состав проекта:** доступен для чтения участникам проекта. Администратор
  добавляет участника выбором из активных пользователей установки, исключает
  действием в строке. Свободного ввода принципалов нет. Старые `/policy` и
  `/permissions` ведут к деталям выбранного проекта; отдельного пункта меню нет.
- **Ёмкость:** пределы меняет только администратор. Пустое значение означает
  unlimited, `0` запрещает выделение; decimal int64 остаётся строкой без
  преобразования через JavaScript Number. Недоступная инвентаризация показывается
  как неизвестная, не нулевая. Резервирование включает suspended и pending golden,
  но не является метрикой текущего потребления. Сбой сохранения не теряет черновик.
- **Политика Substrate** (`/substrate-policy`): отдельный инфраструктурный
  раздел для native identity. Варианты берутся из `/api/identities` и уже
  прочитанных привязок; пользователь выбирает checkbox, а не вводит строку.
  Локальный username не выдаётся за native identity.
- **Рои:** все доступные рои выбранного проекта, создание/удаление, состояние
  и повтор операции по явному retry intent сервера. Передача основного владельца
  доступна owner/admin выбором из участников проекта; остальные grants сохраняются.
  «Доступ к рою» показывает роли owner/editor/viewer и позволяет владельцам выбирать
  участников проекта и менять роли. Последнего owner нельзя исключить или понизить;
  окончательную проверку выполняет Go API. Глобального выбора роя нет.
- **Список роёв (#255):** колонки «Состояние» (инфраструктура: provisioning,
  active, stopped, ...) и «Исполнение» (не запущен, идёт, ждёт ответа,
  завершён, встал, остановлен) — разные, рядом «Открытых вопросов». Ждущие
  ответа сверху (у кого вопросов больше — выше), затем вставшие, идущие,
  не запущенные, завершённые, остановленные; рои без сводки — в конце в
  порядке сервера (`swarmOrder`, `features/access/swarmActivity.ts`).
  Исполнение и число открытых вопросов несёт сама строка
  `GET /api/projects/{id}/swarms` (`execution`, `openRequests`, #234):
  сервер читает сводку одной выборкой на весь список, панель рои не
  опрашивает, N+1 и предела на число роёв со сводкой нет. Строка без
  сводки или с браком в ней (`swarmActivityOf`) — прочерк, не ноль
  вопросов и не «не запущен». Рядом с открытыми вопросами стоит признак
  недоставленных ответов актору тоном attention и словами счётчика шапки
  инбокса (#264), с подсказкой о повторе на странице роя: число несёт та же
  строка (`undeliveredAnswers`, #266, ответы с доставкой `failed` или
  `unconfirmed`), отдельного запроса на рой нет. Ноль и строка старого
  сервера без поля дают прежнюю ячейку; брак в поле теряет только признак,
  не сводку. Порядок списка признак не меняет. Та же строка несёт
  определение снимка, число участников и managed-акторов роя (#268:
  `definition`, `memberCount`, `managedActorCount`): колонки «Определение»
  (имя ссылкой на определение в каталоге проекта, #270, и версия снимка с
  подсказкой, что новая публикация рой не меняет), «Участники» и
  «Managed-акторы» с подсказкой, что native-акторы Substrate в число не
  входят: это не все акторы роя. Колонка есть, когда поле несёт хоть одна
  строка (`factColumns`, `features/access/swarmFacts.ts`): у старого
  сервера таблица прежняя; строка без поля -- прочерк, брак поля теряет
  только его. Щелчок по ссылке определения строку не открывает. Рядом с
  исполнением -- сколько прошло с его последней смены (`executionAt`, #268:
  запуск прохода, остановка или окончание), словами локали
  (`Intl.RelativeTimeFormat`): целые минуты, часы, дни без округления вверх,
  меньше минуты и момент впереди часов браузера -- «только что»; точный
  момент -- в подсказке. Считается от чтения списка (`useReadMoment`):
  своего таймера нет, у списка роёв опроса нет, момент сдвигает
  перечитывание. Строка без момента или с браком в нём (не RFC 3339 с
  зоной, `executionMoment`, `features/access/executionAt.ts`) -- прежняя
  ячейка исполнения; проверки -- `web/tests/executionAt.test.ts`,
  `swarmRowFacts.test.ts`. Список
  живёт в `useSwarmActivityStore`, один
  на панель: меню берёт из него имя проекта (группа ресурсов проекта
  названа его именем) и число роёв, ждущих оператора, у пункта «Swarms»:
  правило и слова -- те же, что у плитки «Ждут вас» обзора (#269); страница
  роёв отдаёт ему свой список. Подсказки о ролях роя — в пустом состоянии
  списка; подпись о повторе операции — только когда в списке есть рой не в
  `active`. Тоны бейджей исполнения — attention/progress/problem/neutral
  (#254) через локальный маппинг на нынешние success/warning/danger/muted в
  том же файле. Каталог проектов берёт число роёв из строки
  `GET /api/projects` (`swarmCount`, #234: длина списка роёв проекта у того
  же пользователя, одной выборкой на весь каталог) и отмечает выбранный
  проект в строке. Детали проекта: раздел «Ёмкость» свёрнут
  (`<details>`), когда инвентарь недоступен, причина — в его заголовке.
  Акторы и шаблоны: группа каждого роя сворачивается, отказ загрузки
  групп — одной плашкой на причину с именами роёв, а не под каждым роем.
  Страница настроек показывает `detail` отказа Go API (503 без LLM backend)
  текстом, а не сырым JSON; рекламного блока апстрима у поля прокси нет.
- **Страница роя (#215, переустройство #253):** `/swarms/:id`, строка
  списка роёв ведёт сюда. Заголовок — имя роя, не определения графа; под
  ним одна строка сведений: проект ссылкой, владелец и роль именами,
  полный ID с копированием, пространство в Substrate и состояние
  инфраструктуры бейджем (не `active` — ещё строка тревоги под ними); на
  телефоне сведения сложены под «Сведения». Первый экран отвечает «что
  сейчас и что от меня нужно», и при 1280×900 на нём помещаются открытый
  вопрос и начало графа. Строка состояния исполнения — бейдж, узел, на
  котором стоит проход (кнопкой, тем же выбором, что на графе), и слово
  шага, когда оно уточняет исполнение (фаза работы, отказ, неизвестный
  исход), а не повторяет его; рядом действие запуска или остановки
  (#218). Под строкой — совет застрявшему шагу (#238) или пояснение
  состояния, затем задача текущего прохода (#242) в две строки с
  развёртыванием. Остановленный рой и рой, ждущий ответа, различаются
  значком и пояснением. Дальше открытые запросы оператору (#216), затем
  граф и панель выбранного узла в две колонки от 1024 px (панель липкая,
  пока граф листается; на телефоне подряд); подпись в заголовке графа —
  личность снимка (#218). Ниже роли (#241), история шагов, доступ.
  Выбранный узел (по умолчанию текущий) показывает исход и актора
  последнего посещения, инструкцию из графа и моменты шагов — когда
  сервер их отдаёт, число заходов — только если их больше одного.
  История шагов идёт по проходам: прошлые проходы свёрнуты в заголовок с
  числом шагов (`details`), текущий раскрыт и своей задачи не повторяет —
  она в первом блоке; у шага длительность вместо двух моментов (полные —
  в подсказке), у идущего шага — начало; без записанных моментов нет и
  этого. Вопрос оператору открывается и у своего узла. Доступ, передача
  и удаление — в конце страницы по прежнему плану действий. Адрес роя
  делает его проект глобальным контекстом; смена проекта в шапке ведёт к
  списку роёв. Исполнение читается по старым маршрутам
  `/api/pipeline-runs/{id}`, где ID — это рой (#206); у роя без графа
  исполнение не начато. Чистая логика строки состояния и длительностей —
  `swarmState.ts` (`executionNow`, `stepDuration`, `durationParts`,
  `rolesUnfolded`), проверки — `web/tests/swarmPage*.test.ts`. Тексты для
  оператора без машинных слов: «пространство в Substrate», не atespace;
  «заходов», не visits.
- **Запросы оператору (#216):** инбокс на странице роя, под строкой
  состояния и выше графа: `GET /api/swarms/{id}/requests?all=1`,
  перечитывается, пока рой активен. Открытые сверху (дольше ждущий первым)
  и целиком; отвеченные и отменённые — историей, свёрнутой в счётчик
  («N отвеченных», #253). Материал (`context`) любого запроса свёрнут под
  своей подписью (#253): спрашивает вопрос, материал читают по желанию.
  Когда сам инбокс шире 720 px (container query, не ширина окна),
  открытый запрос встаёт в две колонки: вопрос и материал слева, форма
  ответа справа. У запроса — вопрос, материал, кто спрашивает (узел —
  кнопкой, она выбирает его на графе; актор — именем) и момент. Узловой
  запрос отвечается выбором варианта — радиогруппа, выбор виден состоянием
  поля, а не цветом — и необязательным комментарием; уходит исход варианта.
  У запроса актора исхода нет: текст, да/нет или подпись варианта уходят
  текстом ответа и граф не ведут. Форма ответа у запроса одна — в инбоксе
  (#259). Выбранный узел показывает свой запрос той же карточкой без формы,
  в одну колонку: вместо неё кнопка «Ответить выше», она переводит фокус к
  выбору варианта в форме инбокса; после ответа — подпись выбранного
  варианта. Узел, выбранный в момент ответа, остаётся выбранным, хотя граф
  пошёл дальше: куда — говорит строка состояния. Запрос, на который
  отвечали на странице, остаётся на своём месте в инбоксе до ухода с неё,
  а не уходит в свёрнутую историю: ответ принят — у него подтверждение,
  отклонён (например, другой управляющий ответил раньше) — отказ текстом
  сервера; фокус переходит к этому итогу. Карточку инбокса с фокусом
  внутри отмечает рамка: после перехода мышью кольца у радио нет. В
  истории — подпись нажатого варианта. Доставка ответа актору —
  состоянием (#260): при `failed` (ответ заведомо не ушёл) — причина и
  повтор (`.../deliver`) сразу; `unconfirmed` (ушёл без квитанции) — тоном
  внимания и словами «доставка не подтверждена: ответ мог дойти до актора»,
  с тем же повтором, но после подтверждения в диалоге «повтор может
  доставить ответ дважды» (#261). Причина (`deliveryError`) приходит только
  в ответе answer/deliver: после перезагрузки остаются состояние и слова.
  После повтора — новое состояние и причина, фокус — на доставке: кнопка на
  время повтора заблокирована и исчезает с доставкой. Ответ с доставкой
  `failed` или `unconfirmed` историей не становится (#264): такие запросы
  стоят группой «Доставка требует внимания» под открытыми, дольше ждущий
  актор первым, с повтором под рукой, пока доставка не удастся; карточку
  отмечает левая полоса, у неподтверждённой пунктирная. Повтор на странице
  оставляет карточку в группе и после доставки, до ухода со страницы:
  фокус на её новом состоянии, а причина прошлой неудачи рядом с
  доставленным ответом не показывается. Шапка инбокса считает рядом с открытыми
  все недоставленные, и отвеченный здесь, который стоит на своём месте.
  Правило размещения: `inboxSections` (`requestState.ts`). Счётчик
  открытых в списке роёв (`openRequests`, #234) их не учитывает: строка
  списка несёт их отдельным числом `undeliveredAnswers` (#266). Viewer
  читает без формы и без кнопки к ней. Ответ — `POST
  /api/swarms/{id}/requests/{request}/answer`; старым маршрутом ответа
  прогона панель не пользуется.
- **Запуск и остановка роя (#218):** одно действие исполнения на странице
  роя и только у owner/editor/администратора активного роя: «Запустить» у роя
  без снимка, «Запустить снова» у завершённого или остановленного,
  «Остановить» у идущего или ждущего. Зритель, неактивный рой и непрочитанное

  проекта (#228); отказ называет причину. Повторный запуск идёт на снимке роя: без выбора,
  без каталога и без commit. Оба несут задачу прохода (#242, ниже). Остановка подтверждается текстом о том, что
  акторы, их контейнеры и workspace остаются. Отказ — причиной сервера в
  диалоге; после действия страница перечитывает исполнение и граф. Кнопка
  действия стоит рядом со строкой состояния (#253): там же, где совет
  застрявшему шагу говорит остановить рой и запустить новый проход.
  Подпись в заголовке графа — личность снимка (`definition` чтения
  исполнения: имя, версия, ревизия) одной строкой, ревизия короткая на

- **Задача прохода (#242):** диалог запуска, первого и повторного, просит
  многострочную «Задачу прохода» и отправляет её `goal` как набрана, без
  обрезки: `{definition, goal, commit?}`. У повторного запуска поле пустое,
  над ним — задача прошлого прохода (`goal` чтения исполнения), если сервер
  её отдаёт. Счётчик под полем — в байтах UTF-8 до 4096, как предел
  сервера. Панель проверяет те же правила, что сервер, и в его порядке:
  пусто или одни пробелы (те, что снимает Go `strings.TrimSpace`), больше
  4096 байт, одиночная суррогатная половина (не UTF-8: при отправке она
  молча стала бы U+FFFD), управляющие символы кроме `\n` и `\t`, закрывающий
  тег конверта `</cross-session-message>`. Такая задача не уходит: причина —
  у поля (`aria-invalid`, описание поля), фокус — на нём; пустота
  называется только после попытки запуска. Решает всё равно сервер: его
  отказ (400 `invalid swarm start: ...`, 422 `invalid swarm goal: ...`) —
  его текстом в диалоге, набранная задача остаётся. Страница роя
  показывает задачу текущего прохода под строкой состояния (#253) как
  markdown без HTML (#252), в две строки с развёртыванием (`Markdown
  collapsible` с `collapsedHeight`): переводы строк внутри абзаца
  сохранены, теги автора остаются текстом. История шагов делится на
  проходы по `pass` шага: заголовок «Проход N, с шага #M» с числом шагов в
  summary и задача прохода (`goal` его первого шага) теми же двумя
  строками над его шагами; прошлые проходы свёрнуты, последний раскрыт и
  задачу не повторяет — она под строкой состояния (#253); шаги без
  `pass` — одним списком, как раньше.
- **Опрос страницы роя (#257):** один таймер на страницу

## Сессии и management proxy

Панель использует `/api/auth/session`, `/api/auth/login`, `/api/auth/logout`.
Login/logout возвращают 204; после входа клиент читает текущего пользователя
и `is_admin` из session endpoint. Cookie `session` — HttpOnly, cookie `csrf`
возвращается заголовком `X-CSRFToken`; изменяющие запросы проверяют Origin.
Пароли и management key не сохраняются в browser storage.

Вход не зависит от LLM-прокси: обычный пользователь и администратор могут
работать с проектами/роями, даже если backend провайдеров не настроен.
Существующие management-страницы используют Go BFF: явно настроенные
`CLIPROXY_URL` и `CLIPROXY_MANAGEMENT_KEY` остаются на сервере. Go проверяет
актуальную admin-сессию и CSRF/Origin, удаляет browser credentials и сам
добавляет upstream management key. Native LLM-клиенты используют свои bearer
keys, не browser sessions. Redirect из management backend не пропускается.

Без явной настройки LLM backend соответствующие запросы получают объяснимый
503; наличие страницы не означает настроенных провайдеров. Private Kubernetes
endpoint требует отдельно настроенных credentials и сетевого доступа к backend;
автоматического public cutover или возврата Django нет.

## Несохранённые правки

Hash-роутер отменяет Back/Forward, возвращаясь на разницу `idx` записей.
У записи, созданной мимо роутера (адресная строка, `location.hash`), индекса
нет, а у записей после неё он `NaN`: отмена там невозможна или перезагружает
страницу, поэтому `useUnsavedChangesGuard` её не просит. Защита из трёх
слоёв: blocker роутера — для его переходов и Back/Forward между его записями;
Navigation API — для Back/Forward браузера и набранного адреса, если браузер
разрешает отмену; `beforeunload` — для ухода со страницы. Переход, который не
отменить, не теряет данные: `useDraftRecovery` хранит черновик вне страницы,
и редактор при следующем открытии предлагает его вернуть. Черновики без
секретов (OAuth-алиасы и исключения моделей) лежат в `sessionStorage` и
переживают перезагрузку; черновик `config.yaml` с ключами — только в памяти
вкладки. Выход из сессии очищает оба. Регрессия — `bun run test:browser`.

## Терминалы и проверка

Поведенческий тест локальной адаптации входит в driftty build stage вместе
с upstream-тестами. Browser-регрессия запускается отдельно:

```sh
node deploy/driftty-direct-pty-browser.test.cjs go/brood/server/static/driftty.html /path/to/playwright
```

Второй аргумент — установленный модуль Playwright. Тест поднимает только
локальный HTTP/ttyd protocol fake и Chromium с phone emulation: проверяет
opaque origin, все три поверхности управления, Fit screen, сохранение явного
размера при resize, ввод, wheel/touch scrollback и native mouse reporting в
alternate screen. Это не проверка реального гостя или Safari на устройстве.

Ссылка terminal идёт через авторизованный Go endpoint и короткоживущий
actor-view ticket. Обязательный CSP sandbox без `allow-same-origin` не даёт
HTML актора полномочий панели. Ticket привязан к сессии, рою и актору;
его нельзя писать в access logs. Модель отзыва — `docs/GO.md`.

UI проверяется в браузере против настоящего Go API, включая обычного
пользователя. Отдельно отмечаются инфраструктурные fake и ненастроенные
backends. Статус ошибочного provision не подменяется успешным созданием роя.
