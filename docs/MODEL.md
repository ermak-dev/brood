# Model

Объектная модель установки: из чего она состоит, кто чем владеет и какой слой
является авторитетом прав. Остальные документы описывают подсистемы, этот —
сущности между ними. Код: `go/brood/store`, `go/brood/app`,
`go/brood/substrate`, `go/brood/server`.

## Три слоя

Прикладной слой brood проверяет права пользователей установки до вызова
ateapi. Substrate отдельно проверяет инфраструктурную identity сервера
по своим политикам: успешная проверка brood не отменяет отказ ateapi.
Сборка — третий слой, он доставляет образы и шаблоны в рой.

```
brood (SQLite)          авторитет прав
  user, project, membership, swarm, session
        |
        | рой 1:1 atespace, имя производное от ID роя
        v
Substrate (ateapi)      следствие
  atespace, actor, actor template, egress policy,
  worker, worker pool, access policy
        ^
        | образы и шаблоны
Broodfile / bro build / bro push
```

## Прикладной слой

Таблицы — `go/brood/store/schema.sql`, типы и правила — `go/brood/app`.

```
user(id, username, display_name, is_admin, disabled)
  |                                  |
  | M:N membership(project, user)    | 1:N swarm.owner
  |     без роли                     |
project(id, name)
  | 1:N
swarm(id, project, owner, name, atespace_name, atespace_uid, state, retry)
session(token_hash, user)
```

- **Пользователь** — локальная учётная запись установки. Единственная роль
  модели — глобальный `is_admin`; заблокированный отказан всегда, включая
  администратора.
- **Проект** — имя и состав участников, больше ничего: ни ёмкости, ни привязки
  к воркерам.
- **Членство** — пара «проект, пользователь», без роли. Даёт видеть проект и
  создавать в нём рои; чужие рои членство не открывает.
- **Рой** — один atespace Substrate внутри проекта, с одним владельцем.
  `atespace_name` производное от ID роя (`swarm-<id без дефисов>`), подменить
  область через payload нельзя.
- **Сессия** — вход пользователя; прикладному слою не видна.

Действия и правила — `go/brood/app/authz.go`. Ресурсов два: проект и рой.
Доступ к рою — `(владелец И участник проекта) ИЛИ активный администратор`;
передача владения — только администратор, только активному рою; удалённый рой
не существует ни для кого.

### Жизненный цикл роя

```
provisioning -> active | error
active       -> deleting | error
deleting     -> deleted | error
error        -> active | deleting | error | deleted
deleted      — терминальный, строка остаётся
```

Сбой Substrate возвращается вызывающему как ошибка и одновременно
сохраняется: строка получает `state=error` и `retry` (`create` или `delete`).
Повтор совместимой операции возобновляет её; успех зависит от доступности
Substrate. Создание идемпотентно по имени роя в проекте, удаление сверяет имя
области по сохранённому UID: чужая одноимённая область не удаляется и не
присваивается.

## Substrate

Клиент — `go/brood/substrate/client.go`, объекты — канонический protojson
ateapi.

```
atespace                   1:1 с роем
  |- actor          1:N    единица работы, suspend и resume
  |    |- egress policy 0..1
  |    `- -> actor template
  |- actor template 1:N    неизменяем, Update в ateapi нет
  `- access policy  0..1   синглтон default, роли owner, editor, viewer

установка, вне atespace
  |- worker         1:N    зеркало пода, пишет ate-controller
  |- worker pool    1:N    число подов и их ресурсы, объект Kubernetes
  `- access policy  0..1   синглтон default, роли owner, viewer
```

`access policy` — ACL самого Substrate, не прав brood: `members` принимает
только `user:<id>`, где id — identity кластера. У пользователей brood такой
identity нет. Сервер ходит в ateapi одной ServiceAccount
`system:serviceaccount:brood:django` (`docs/SUBSTRATE.md`), global owner, и
не синхронизирует bindings с пользователями brood. Администратор может
изменять политику через API и панель; она независимо регулирует доступ
инфраструктурных identity. Поэтому политика Substrate — инфраструктурный
объект кластера, а не состав участников проекта brood.

Воркеры и пулы принадлежат установке целиком. Актор попадает на воркер по
`workerSelector`; с проектом или роем этот выбор не связан.

## Сборка и публикация

`Broodfile` объявляет цели сборки; `bro build` складывает артефакты цели в
`.brood/build/<target>`; `bro push` отправляет их в рой через сессию
пользователя (`go/CONTRACT.md`). Репозиторий образов — `<atespace>/<environment>`,
шаблон создаётся в atespace роя. Акторы при публикации не создаются.

## Словарь

- **Рой** — запись brood и её atespace; в интерфейсе это одна сущность.
- **Шард** — проект как раздел установки с собственной ёмкостью. Решение
  эпика #45, в коде ещё нет.
- **Актор** — единица работы внутри роя.
- **Политика Substrate** — `access policy` ateapi, над identity кластера.
- **Права доступа** — состав доступа brood: членство и роли.

Слово «проект» в коде пока означает четыре разных объекта, и это расхождение,
а не договорённость: проект brood; atespace, который панель тоже зовёт
проектом, храня при этом ID роя (`web/src/stores/useProjectStore.ts` против
`web/src/features/substrate/components/ProjectSwitcher.tsx`); проект
`Broodfile`; назначение `bro push --project`, принимающее и проект, и рой
(`go/brood/clientapi/push.go`).

## Расхождения текущей модели

Зафиксированы эпиком #45; каждое — задача своего слоя.

- **У проекта нет инфраструктурного следа.** Ни ёмкости, ни пула, ни лимитов:
  участник создаёт рои до исчерпания общей ёмкости установки (#48).
- **У роя нет ACL.** Владелец — один столбец, таблицы ролей нет; совладельца
  или права «только смотреть» выдать нечем, передача владения — подмена
  столбца (#47).
- **Гранулярность прав несовместима между слоями.** Сверху ролей нет вовсе,
  у ateapi их три; спроецировать одно на другое нечем, пока brood не выдаёт
  пользователям identity (#47, #54).
- **Уникальность имени роя в проекте держится кодом, не схемой** (#47).
- **Наружу у роя нет человекочитаемого владельца:** API отдаёт внутренний id
  (#49).

## Целевая модель

Согласованное направление: проект — аналог шарда, рой — группа акторов
с ACL. Это не описание уже реализованного поведения. Привязка проекта
к отдельному пулу, состав квот, набор ролей и требование членства в проекте
для любой роли роя — предлагаемые детали реализации задач #47–#49;
их нужно проверить на сценариях совместной работы до изменения схемы.

В предлагаемом варианте проект — раздел установки с привязкой к пулу
воркеров и лимитами; членство — право расходовать его ёмкость и создавать
в нём рои.

Рой — группа акторов с ACL: участники роя с ролями `owner`, `editor`,
`viewer`; владелец — роль, а не столбец; передача владения — смена роли.
Членство в проекте остаётся предусловием любой роли в его роях.

Политика Substrate остаётся инфраструктурным объектом. Слить её с правами
brood в одну сущность можно только после того, как сервер начнёт выдавать
substrate identity на пользователя и сам писать bindings; до этого интерфейс
не делает вид, что это одно и то же.
