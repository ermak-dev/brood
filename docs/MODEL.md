# Model

Действующая объектная модель установки после #47–#49 и #53: проект — шард,
рой — группа акторов с локальным ACL. Источники контракта — `go/brood/store`,
`go/brood/app`, `go/brood/server` и `go/CONTRACT.md`. Подробности панели —
`docs/WEB.md`, сборки — `docs/BUILD.md`.

## Три слоя

Прикладной слой brood проверяет актуальные права пользователя до вызова
ateapi. Substrate независимо проверяет инфраструктурную identity сервера;
разрешение brood не отменяет отказ ateapi. Сборка доставляет образы и шаблоны,
но не выдаёт прав и не создаёт акторов.

```
brood (SQLite)                    авторитет прав и пределов
  user, session
  project, membership, project_capacity
  swarm, swarm_members
       |
       | рой 1:1 atespace, сохранённый native UID
       v
Substrate (ateapi)                авторитет native inventory
  atespace, actor, actor template, tags, egress policy
  worker, worker pool, access policy
       ^
       | образы и шаблоны
Broodfile / bro build / bro push
```

## Прикладные сущности

Схема версии 4: `schema.sql`, `swarm_members.sql`, `project_capacity.sql`,
`managed.sql` и stage управляемых операций в
`go/brood/store`. Известные старые схемы обновляются транзакционно;
повреждённая или неизвестная версия не восстанавливается догадками.

- **Пользователь** — локальная учётная запись. `is_admin` даёт полномочия
  администратора установки; `disabled` запрещает доступ независимо от ролей.
- **Сессия** — серверный вход пользователя. В базе хранится хэш токена;
  cookie/CSRF проверяет HTTP-слой. Сессия не заменяет актуальную проверку прав.
- **Проект, или шард** — логическая граница состава и резервирования ресурсов.
  Имеет имя, участников, обязательный worker selector и необязательные пределы.
- **Членство проекта** — пара «проект, пользователь», без отдельной роли.
  Позволяет читать проект, его состав и ёмкость, а также создавать рои.
  Само по себе не открывает чужой рой.
- **Рой** — группа акторов в проекте и ровно один atespace Substrate.
  Имя atespace выводится из ID роя; сохранённый UID защищает от присвоения
  или удаления чужой одноимённой области. Payload не подменяет эту связь.
- **Участник роя** — явная пара «рой, пользователь» с одной ролью `owner`,
  `editor` или `viewer`. Роль действует только вместе с членством проекта.
  Активный администратор имеет эффективные права owner без явного grant.

`swarm.owner_id` сохранён как совместимая проекция основного owner для старых
клиентов и отображения имени. Авторизация использует `swarm_members`, а не
равенство этому столбцу. Совладельцев может быть несколько. Смена роли или
исключение основного owner атомарно выбирает оставшегося owner для проекции;
последнего явного owner удалить или понизить нельзя.

Имя живого роя уникально внутри проекта: частичный уникальный индекс охватывает
все состояния, кроме `deleted`. Tombstone не занимает имя, но сохраняет старую
связь и не превращается в разрешение усыновить native namespace.

## Права роя

| Действие | Owner | Editor | Viewer |
|---|---|---|---|
| Читать рой, его ACL, акторов и шаблоны | Да | Да | Да |
| Создавать и менять нагрузку, suspend/resume | Да | Да | Нет |
| Получать writable actor-view/terminal ticket | Да | Да | Нет |
| Менять роли и исключать участников роя | Да | Нет | Нет |
| Передавать основное владение, удалять рой | Да | Нет | Нет |

Мутации нагрузки требуют активного роя. Повтор create/delete определяется
сохранённым намерением операции, а не одним состоянием `error`.

Owner/admin может передать основное владение активным роем активному участнику
проекта или администратору. Новый пользователь получает роль owner, grant
прежнего основного владельца снимается; остальные grants сохраняются. Это
отдельно от добавления совладельца через ACL. Последнего owner защищает
транзакция, включая конкурирующие изменения.

Удаление членства проекта лишает действительности доступ к его роям.
Заблокированному пользователю отказано всегда. HTTP не раскрывает закрытый
рой: недоступный объект выглядит как 404. Политики native identity и управление
инфраструктурой остаются admin-only, в том числе golden egress policy внутри
шаблона.

Actor-view ticket привязан к действующей сессии, рою и актору. Потеря права
manage-swarm, в том числе editor → viewer, отзывает writable доступ и закрывает
существующее соединение при повторной проверке. CSP actor-view изолирует HTML
актора от полномочий панели (`docs/GO.md`).

## Ёмкость шарда

`project_capacity` хранит обязательные метки воркера и пределы:

- числа неудалённых роёв;
- числа зарезервированных акторов;
- CPU в millicores;
- памяти в байтах.

Отсутствующий предел означает unlimited, явный ноль запрещает новое выделение.
HTTP передаёт nullable пределы и расход десятичными строками int64: значения
не проходят через JavaScript Number. Пределы и selector меняет только активный
администратор. Снижение предела не останавливает существующую нагрузку:
неизменное или уменьшающееся резервирование разрешено, рост сверх предела — нет.

Воркеры и пулы остаются инфраструктурой установки. Шард ограничивает размещение
через обязательный `workerSelector`, например метку выделенного пула.
Неуказанный selector нагрузки наследует метки шарда; явный обязан их сохранять.
Это не выделение отдельной физической машины и не автоматическое создание пула.
Пересекающиеся selectors могут использовать общие воркеры; квота не гарантирует
наличие физической ёмкости или поддержку runtime на выбранном воркере.

Расход вычисляется из строк роёв, native inventory и неудалённых managed
allocations, второго счётчика в БД нет. Учитываются все неудалённые состояния роя, suspended actors
и ожидающие golden actors. Pending golden и появившийся native golden не
считаются дважды. Публикация шаблона с golden disabled не занимает actor slot.
Неизвестные namespace UID, шаблоны или ресурсы не превращаются в нулевой расход:
детали проекта показывают unknown, ограниченное выделение отказывает.

Создание, замена и resume актора, публикация шаблона, build push и удаление
шаблона проходят согласованную проверку. Шаблон с обычными actor references
нельзя удалить и переиспользовать для обхода учёта; управляемый golden cleanup
разрешён. Отказ называет исчерпанный предел. Учёт защищён блокировкой проекта
в процессе и транзакциями записи; distributed quota между несколькими
независимыми server processes не заявляется.

## Жизненный цикл и восстановление

```
provisioning -> active | error
active       -> deleting | error
deleting     -> deleted | error
error        -> active | deleting | error | deleted
deleted      — терминальный, строка остаётся
```

Неопределённый сбой Substrate возвращается ошибкой и сохраняется как
`state=error`, `retry=create|delete`. Совместимый повтор продолжает операцию.
API сериализует сохранённый `retry`, включая пустое значение после успеха.
Создание идемпотентно по имени и владельцу; удаление сверяет прежний native UID.

Узкое исключение — типизированный атомарный отказ native удаления непустой
области. Повторная проверка того же UID позволяет откатить локальное намерение
удаления в active с пустым retry. Владелец сохраняет API для очистки детей,
после которой повторный DELETE завершается. Это не общий переход deleting →
active: транспортная неопределённость или чужой UID не разрешают rollback.
Удаление заново проверяет полномочия после ожидания блокировки проекта.

Удалить проект с любым неудалённым роем нельзя, даже администратору. SQL cascade
не используется как замена native cleanup. Tombstones не блокируют удаление
пустого проекта. При сбое очистки ребёнка родитель и его состав сохраняются.

Потерянную локальную связь может восстановить только активный администратор:
read-only inspection показывает native UID и безопасный inventory, затем
явный recover сверяет канонический ID и ожидаемый текущий UID. Неизвестный
candidate сам по себе не доказывает владение. Recover не создаёт, не удаляет
и не перезапускает native workloads, не переписывает существующую связь.
Подробный maintenance-контракт — `go/CONTRACT.md`.

## Substrate и сборка

Atespace содержит акторов, неизменяемые actor templates, tags и native access
policy. Worker — зеркало пода, worker pool — Kubernetes-объект установки.
Native `access policy` регулирует identity кластера, а не локальный ACL brood.
Сервер использует инфраструктурную ServiceAccount
`system:serviceaccount:brood:django` и не выдаёт пользователям substrate identity
или bindings. Сходство имён owner/editor/viewer не означает синхронизации
этих независимых слоёв.

`Broodfile` объявляет цели, `bro build` создаёт локальные артефакты,
`bro push` публикует их через ту же серверную сессию в доступный рой.
Публикация проверяет selector и пределы шарда, не создаёт акторов и не даёт
доступа к чужим template/tag references. Историческое имя флага `--project`
не означает raw atespace: API работает с ID роя brood, сервер определяет
native namespace сам. Декларация project в Broodfile — контекст сборки, не
идентификатор шарда или atespace.

## Управляемый провайдер Proxmox

`claude-proxmox` — отдельный ограниченный профиль brood, а не native Worker
Substrate. `managed_pools` и `managed_actors` хранят собственный inventory:
UID пула и актора, неизменяемый снимок шаблона и ресурсов, CTID, поколение,
nonce владения, желаемое состояние, намерение операции, его stage, UPID и
revision. Подробности жизненного цикла — [PROXMOX.md](PROXMOX.md).
Неудалённые stopped/error allocations продолжают занимать ёмкость. Общие
пределы проекта и обязательный selector применяются к обоим провайдерам;
резервирование физической ёмкости managed-пула атомарно между проектами.

Рой по-прежнему связан с native atespace сохранённым UID. Managed-провайдер
не заменяет эту связь, ACL, native API или существующие полные профили.
Виртуальный read-only шаблон `claude-proxmox-<pool>` появляется в списках
без записи в Substrate. Коллизия с native шаблоном или актором вызывает
отказ, а не выбор провайдера по пользовательской метке. Actor API сохраняет
`results`, camelCase и десятичные строки int64; managed-записи явно содержат
`provider`, `placement` (node/ctid/pool), `phase`, `desired`, поколение и
capabilities, без вымышленного `workerAssignment`.

Активация пула — явный admin-запрос, не побочный эффект GET. Установка
задаёт весь блок `template`, `templateDigest`, `capacity` в
`BROOD_PROXMOX_POOLS`, отдельные `BROOD_PUBLIC_ORIGIN` и
`BROOD_PROXMOX_RELAY_SECRET`. Ёмкость пула — общая; immutable профиль
резервирует равные доли, округлённые вниз до целого ядра, MiB и GiB.
Конфигурации соединений без runtime-блока остаются доступными для чтения.
API не выдаёт ключи, CA, credential references, guest tokens или nonce.
Draining запрещает новые размещения, сохраняя остановку и очистку;
удаление пула или роя отказывает при оставшихся managed allocations.

Контейнер непривилегированный, актор работает не от root; workspace
сохраняется при stop/resume. В образе доверенный root supervisor отвечает
за PTY и fail-closed контролируемую сеть. Docker, kind, произвольные OCI,
mount/env/publish и memory checkpoint этим профилем не поддерживаются.
Suspend возвращает 409 до эффектов; существующие native профили не урезаются.

До PVE-записи фиксируется durable intent. Неопределённый create сохраняет
исходный CTID и резервирование: новый CT вслепую не создаётся. Мутации
проверяют полный marker pool UID + actor UID + generation + nonce,
принадлежность ресурсному пулу и допустимую конфигурацию CT. PVE не даёт
атомарного ownership precondition для power/delete: оператор не должен
подменять активный CT между проверкой и запросом. Остановка сервера
закрывает транспорт, но не останавливает акторов; restart сверяет durable
inventory и не повторяет уже отправленное исполнение.

`running` требует успешной PVE task, аутентифицированного relay и HTTP-пробы
фиксированного ttyd. Guest WSS-маршрут вне cookie/CSRF middleware принимает
только scoped HMAC-токен текущего UID и поколения; installation relay key,
PVE/session credentials в CT не передаются. Relay разрешает только terminal
channel, не произвольный forwarding. Actor-view сохраняет session/ACL/CSP
и native UID-проверки, дополнительно связывая ticket с managed UID и
поколением; отзыв прав, stop/delete/reset закрывают браузерные потоки.

## Интерфейс и границы

Глобальный переключатель хранит только ID проекта brood. Рой глобально не
выбирается: администратор видит все рои проекта, участник — только рои со
своей действующей ролью. «Сведения о проекте» объединяют состав, selector,
пределы и резервирование. ACL редактируется у конкретного роя; участники и
новый основной владелец выбираются из списков.

Обычному пользователю доступны четыре раздела: проекты, рои, акторы, шаблоны.
Детали проекта и состав доступны для чтения, изменение состава и пределов —
только администратору. Кнопки workload скрыты для viewer; это удобство панели,
а не граница безопасности. Каждый Go API запрос проверяет актуальные права.

Пользователи, инфраструктурные политики, воркеры/пулы, CLIProxyAPI, dashboard,
config, logs, plugins и system остаются admin-only. Native policy находится в
инфраструктурной навигации, не дублирует пользовательские права проекта.
LDAP, OAuth issuer, универсальная RBAC-схема, автоматическое физическое
выделение шарда и синхронизация native identity не заявляются.
