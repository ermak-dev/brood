# Telegram

Подсистема управления разработкой из Telegram (эпик #278): профиль и
привязка чата, поллер ботов, зеркало запросов роя и границ прохода,
ответы кнопками и команды чата. Хранение — схема SQLite (`docs/MODEL.md`,
«Версия схемы 29» и далее); контракты HTTP API —
[CONTRACT](../go/CONTRACT.md), «Профиль Telegram». Раздел перенесён из
`docs/MODEL.md` (#286).

Профиль и поллер Telegram (#281, эпик #278); раздел переедет в
`docs/TELEGRAM.md` с задачей деплоя эпика (#286). Хранилище Telegram —
выше, «Версия схемы 29».

API профиля действует только для самого вызывающего, за сессией и CSRF, и
запись перепроверяет сессию в своей транзакции; формы ответов и отказов —
[CONTRACT](../go/CONTRACT.md), «Профиль Telegram».

 - `PUT /api/me/telegram` ровно `{"token"}`: `getMe` доказывает токен и даёт
   имя бота, имени от вызывающего нет. Бот установки своим ботом не
   становится и до ответа его `getMe`: сервер узнаёт его по id бота из
   токена. Токен не возвращает ни один ответ и ни один отказ. Токен
   отвергнут только по ответу о нём самом (401, 404); прочий отказ `getMe`,
   как 429, — «повторить позже», а не «токен неверен».
 - `GET` — бот привязки (свой или бот установки), задан ли свой токен,
   состояние и причина, подписки, привязанный чат и ждёт ли код; без
   привязки — пустое состояние `unlinked`, а не отказ.
 - `DELETE` снимает свой бот и привязку чата одной транзакцией; поллер своего
   бота остановлен до ответа.
 - `POST /api/me/telegram/link` выдаёт код из `crypto/rand`: 32 байта (256
   бит) в base64url без дополнения, 43 знака параметра deep link `t.me`, срок
   15 минут (`telegramLinkCodeTTL`). Энтропию хранилище проверить не может,
   её держит выдача; срок сверяет `ConfirmTelegramLink`. Ответ несёт код один
   раз, в базе только его хэш. Пользователю без своего бота код не выдаётся,
   пока бот установки остановлен: его никто не примет до перезапуска.
 - `PUT /api/me/telegram/events` (#295) заменяет подписки полным набором
   (`SetTelegramEvents`): виды сверяет хранилище по своему словарю. Повтор
   схлопывается, порядок — словаря; пустой набор — ни одной подписки, а не
   значение по умолчанию со всеми видами. Отказ неизвестного вида называет
   словарь, а не присланное значение: тело не попадает ни в отказ, ни в
   журнал. Поллеров подписки не касаются: сверки после записи нет.

Поллер — на бота, а не на пользователя: Telegram отдаёт очередь бота одному
`getUpdates`. Сервер держит поллер своего бота каждого включённого
пользователя, чья привязка не в `error`, и один поллер бота установки
(`BROOD_TELEGRAM_BOT_TOKEN`) для всех без своего бота. Набор поллеров
сверяется с базой на старте, после записи профиля, кроме подписок (до ответа
API), и раз в 15 секунд: блокировка, смена роли и пароля отзывают сессии мимо
поллера, и он останавливается со следующей сверкой. Сверку после записи уход
клиента не отменяет (запись уже зафиксирована), её срок — 10 секунд. Не
прошла (база не прочлась) — `PUT /api/me/telegram` и `POST /link` отвечают
внутренним сбоем, а не успехом без поллера; `DELETE` останавливает поллер
снятого бота и без неё, остаток набора сверит следующая сверка.
`Server.Close` ждёт поллеры до закрытия базы: ошибка привязки, которую пишет
останавливаемый поллер, дописывается.
Long poll `getUpdates` — 50 секунд.
Offset живёт в памяти по id бота: перезапуск поллера в процессе продолжает
очередь, перезапуск процесса берёт обновления, которые Telegram ещё не
считает подтверждёнными, и последняя порция до остановки может прийти снова.
Сбой — пауза от секунды, вдвое за сбой подряд, до минуты и не меньше
`retry_after`. 401 и 409 останавливают поллер: привязку своего бота они
переводят в `error` с причиной и текстом отказа клиента, если пользователь
всё ещё держит токен этого поллера (токен в тексте клиент маскирует, причину
с формой токена хранилище отвергает, и тогда остаётся постоянная часть).
Сверка не запускает остановленный так токен снова и тогда, когда ошибку
записать не удалось (база отказала): пометка в памяти держит его до нового
токена или нового кода. Бот установки стоит до перезапуска сервера,
причина — `bot_reason` профиля, действие оператора — [DEPLOY](DEPLOY.md).
Его имя из `getMe` берётся, только если это имя пользователя Telegram по
правилу своих ботов хранилища (`store.TelegramBotName`: латиница, цифры,
`_`), иначе бот безымянный и ссылки `t.me` нет. `getMe`, который ответил,
даже таким именем, снова не спрашивается; сбой опросу не мешает, а `getMe`
после него спрашивается снова не раньше паузы, как `getUpdates` после сбоя.
Свой бот, ставший ботом установки (тот же id бота),
второго поллера не получает: его привязка уходит в `error` с постоянной
причиной, и новый код через него не выдаётся, пока свой бот не снят или
не заменён. Ошибку привязки снимает новый токен или новый код. Порция больше
предела клиента (`ErrTooLarge`) спрашивается снова с того же offset по
одному обновлению, следующая — снова целиком.

Поллер только принимает обновления. Действует личный чат человека: id чата
равен id отправителя; группы, каналы, боты и сообщения от имени чата
игнорируются без ответа. `/start <код>` из непривязанного чата подтверждает
привязку (`ConfirmTelegramLink`, момент — часы сервера при обработке).
Неверный, истёкший, выданный для другого бота код и код отключённого
пользователя получают один и тот же отказ, который не называет аккаунт.
Свой бот, уже привязанный к чату, другим чатам не отвечает ничем.
Привязанный чат на `/answer`, reply на сообщение запроса и нажатие кнопки
ответа отвечает на запрос (ниже, «Ответы из Telegram»); прочие команды и
нажатия кнопок подтверждения исполняет адаптер команд (ниже, «Команды
чата»), на `/start` без роя — напоминание о привязке; на прочий текст чат
получает подсказку, как ответить. Права перепроверяет `TelegramChatSession`
на каждом обновлении: он же называет сессию привязки, под которой пришло
обновление. Ответы чату идут прямо `sendMessage` и `answerCallbackQuery`,
без outbox, записи исхода и повтора; уведомления идут через outbox (ниже).
Имя пользователя Telegram собеседника держит строка привязки (#294, выше,
«Версия схемы 31»): подтверждение кода пишет имя отправителя `/start`, а
каждое сообщение и нажатие кнопки привязанного чата — имя, которое оно несёт,
если собеседник его сменил или снял (`NoteTelegramUsername` под сессией
обновления). Имя, которое хранилище не примет, считается отсутствующим:
привязка и обновление из-за него не срываются. Профиль показывает имя из
хранилища, поэтому оно переживает перезапуск сервера.

### Зеркало роя (#282)

Запросы оператору и границы прохода зеркалятся в чат через `telegram_outbox`.
Уведомление ставит та же транзакция, что доменное изменение
(`queueTelegram`): откат изменения уносит и уведомление, а зафиксированное
изменение без уведомления не остаётся — отказ записи уведомления
откатывает и само изменение, метод возвращает отказ. События и их виды:

 - открыт узловой запрос (`request_opened`: запуск, переход графа в
   human-узел) и вопрос актора (`actor_question`);
 - ответ на запрос, откуда бы он ни пришёл — панель, CLI, Telegram
   (`request_answered`), в одной транзакции с ответом и раньше конца прохода
   или следующего запроса, которые открывает продвижение графа; повтор
   применённого ответа ничего не пишет;
 - смена состояния доставки ответа актору (`answer_delivery`: `delivered`,
   `failed`, `unconfirmed`); исход, который состояния не меняет (повтор
   `failed`, `failed` поверх `unconfirmed`), — без уведомления. `pending`
   пишет сам ответ;
 - начало прохода (`pass_started`, раньше запроса его первого шага) и его
   конец (`pass_finished`): шаг выхода или терминальный отказ
   (`succeeded`, `failed`) и остановка (`stopped`). Шаг, который остановка
   закрыла или оставила без исхода, отдельного уведомления не получает;
 - отказ шага (`step_failed`): шаг закрыт `refused` (инструкция заведомо не
   ушла) или стал `unconfirmed` (её исход неизвестен), в том числе
   восстановлением при запуске.

Получатель — каждый, кто в момент записи читает рой (включённый
администратор либо участник проекта с ролью в рое, правило просмотра роя),
с живой привязкой (`linked` и её сессия `telegram`) и подпиской на вид;
остальным строки нет. Строка несёт событие — рой и объект (`ref`
`swarm/<id>/request/<id>`, `/pass/<номер первого шага>` или
`/step/<номер>`, `payload` — `TelegramEvent`), а не текст: хранилище молчит,
текст собирает сервер при отправке. Строк — по одной на читателя, поэтому
неизменный после записи текст объекта в строку не копируется (ниже, о
тексте): задача прохода (до 4 КиБ) или причина отказа шага (до 1 КиБ)
умножили бы outbox на число читателей, а snapshot крупнее 32 MiB
`brood database verify` отвергает (выше).

Отправитель (`telegramSender`) после коммита держит работника на каждого
пользователя с очередью: очередь пользователя идёт строго по порядку `id`,
одна отправка за раз, очереди разных пользователей — независимо. Набор
работников сверяется с базой раз в 2 секунды. Каждое уведомление — одно
сообщение через бот привязки: свой бот пользователя, без него бот
установки. Перед отправкой отправитель отмечает попытку
(`BeginTelegramAttempt`) и в той же транзакции сверяет адресата заново: у
кого больше нет живой привязки, подписки, права читать рой или бота, тому
уведомление снимается синтетической попыткой `failed` без отправки. Так же
снимается голова, чьё событие не прочесть (`payload` не JSON или поле
другого типа: строка записана мимо хранилища или другой версией): ограждения
не дают её ни удалить, ни исправить, и оставленная она держала бы очередь
пользователя вечно. Исход пишет `SettleTelegramAttempt`, и его не отменяет
остановка сервера:

 - Telegram принял — `sent` с `telegram_message_id`: по нему ответ на
   запрос правит его кнопки (#283, ниже);
 - запрос заведомо не ушёл (`ErrNotSent`: нет соединения, контекст кончился
   до отправки) или 429 — `failed` и в той же транзакции снова в очередь
   головой: следующая попытка после паузы backoff поллеров (от секунды,
   вдвое, до минуты), не меньше `retry_after`. Число таких попыток не
   ограничено: повтор безопасен, а голова и так держит очередь пользователя
   ради порядка, пока Telegram снова не ответит. Предел — возраст:
   уведомление старше суток (`telegramSendMaxAge`, от `created_at`), которое
   снова заведомо не ушло, остаётся `failed`, и очередь идёт дальше; так
   сбой дольше суток не копит в очереди больше событий этих суток.
   `created_at`, который не прочесть, считается старше;
 - попытка без отправки, потому что база не прочла токен своего бота или
   объекты события, — `failed` и снова в очередь, пока у уведомления меньше
   восьми попыток (`telegramSendAttempts`, счёт — все его попытки), затем
   `failed`; чтение, которое оборвала остановка сервера, предел не тратит.
   Свой бот снят или объект события исчез — `failed` сразу;
 - явный отказ (4xx, локальный отказ клиента) — `failed`, очередь идёт
   дальше;
 - исход неизвестен (`ErrUncertain`: обрыв после соединения, 5xx, потерянный
   ответ) — `unconfirmed`. Сообщение могло дойти, и отправитель его не
   повторяет, ни сейчас, ни после перезапуска: повтор только явный, как у
   доставки ответа актору (#260). Попытку, оборванную падением процесса,
   при запуске записывает `unconfirmed` `RecoverTelegramOutbox`, до первой
   попытки нового отправителя.

Отправку в полёте остановка сервера обрывает не сразу: та получает до 5
секунд, и её исход записан до закрытия базы — успевшая отправка остаётся
`sent` со своим `telegram_message_id`, а не `unconfirmed` после
перезапуска. Новую отправку остановка не начинает: уведомление, которое она
застала до отправки, снова в очереди (`ErrNotSent`; старше суток — `failed`,
как при любом `ErrNotSent`).

Доставка at-least-once (эпик #278): `sendMessage` не идемпотентен, а
отметку попытки может откатить падение ОС или потеря питания
(`synchronous=NORMAL`), и тогда сообщение уйдёт ещё раз; повтор по
неизвестному исходу отправитель не делает. Не записался сам исход (база
отказала) — работник знает его и пишет снова после паузы backoff, пока
сервер жив, и ещё раз при остановке; сообщение при этом не повторяется, а
очередь идёт дальше после записи. Только если не удалась и последняя
запись при остановке, попытка остаётся в полёте до перезапуска, и
восстановление записывает ей `unconfirmed`.

Текст простой, без разметки, на английском: рой, узел и шаг узлового
запроса, спросивший актор и ожидаемый ответ (как ожидание актора, а не
призыв ответить: уведомление получает и viewer, которому ответ не
разрешён; как ответить, говорит только уведомление того, кто вправе,
ниже), автор и ответ, исход доставки (неудачная называет, кто вправе
повторить, — управляющий роем, — а не велит повторять каждому читателю),
проход с определением и задачей, исход прохода, отказанный шаг с причиной; у
запроса — вопрос, варианты и материал. Вопрос, материал и ответ запроса
после записи не меняются, задача прохода — тоже (у первого шага прохода,
`swarm_steps_pass_fence`), а шаг `refused` и `unconfirmed` с его причиной не
меняет больше ни одна запись; поэтому их читают при отправке
(`GetSwarmRequest`, `GetSwarmStep`), а не копируют в каждую строку очереди;
рой удалён или объект (запрос, шаг) исчез — `failed` без отправки. Ссылка ведёт на страницу
роя панели на origin `BROOD_PANEL_ORIGIN` ([DEPLOY](DEPLOY.md)): сервер
отдаёт панель только в корне, а панель выбирает страницу по фрагменту (hash
router), поэтому ссылка — `<origin>/#/swarms/<id>` (#194); без настройки
ссылки нет. Текст длиннее предела сообщения Bot API (4096 знаков) уходит
одним документом с полным текстом и подписью до 1024 знаков: первая
строка, указание на файл и ссылка. Уведомление с записанным исходом
хранится 30 дней (`PruneTelegramOutbox` раз в час). Кнопки ответа и команды
чата — ниже (#283, #284).

### Ответы из Telegram (#283)

Уведомление открытого запроса (`request_opened`, `actor_question`) несёт
средства ответа тому, кто в момент попытки вправе управлять роем: включённый
администратор или участник проекта с ролью owner или editor в активном рое
(`TelegramNotification.Manager`, правило ответа на запрос). Viewer получает
уведомление без кнопок и без подсказки, как ответить; запрос, закрытый к
моменту отправки, — тоже. Кнопки прав не дают: ответ перепроверяет их в
своей транзакции, и кнопки, отправленные редактору, которого потом
понизили, ответа не записывают.

 - `choice` — кнопка на вариант, по строке; `confirm` — Yes и No.
   `callback_data` — `a:<номер уведомления>:<индекс варианта>`, а не текст
   варианта: Bot API держит её в 64 байтах. Номер — `id` строки outbox
   получателя, и чат находит только свои уведомления
   (`UserTelegramNotification`). Данные кнопки может прислать и изменённый
   клиент: номер чужого или удалённого сроком хранения уведомления — «кнопка
   недействительна», право проверяет транзакция ответа. Граф и хранилище
   принимают подписи, которые Telegram кнопкой не покажет (`" "`), а узел —
   и больше 100 вариантов; клавиатуру с ними клиент Bot API отверг бы вместе
   с уведомлением. Такой выбор уходит без кнопок, и подсказка велит ответить
   в brood.
 - `text` — без кнопок: ответ — reply на сообщение запроса или команда
   `/answer <номер> <текст>`, которую называет уведомление. Текст ответа —
   текст reply или остаток команды после номера, со строками. Reply
   находит уведомление по номеру сообщения в чате нынешней привязки
   (`TelegramRequestOfMessage`); reply на иное сообщение и текст без
   команды получают подсказку, как ответить. Сам клиент Bot API (#280)
   `force_reply` не отправляет: поле ответа открывает пользователь, а не
   уведомление (#298, слой клиента).

Если текст уведомления длиннее сообщения и уходит документом, подсказка,
как ответить, стоит и в подписи, рядом со ссылкой: номер для `/answer` не
прячется в файле.

Нажатие, reply и `/answer` записываются тем же путём, что `POST
/api/swarms/{id}/requests/{request}/answer` (`answerRequest`):
`AnswerSwarmRequest` от имени пользователя привязки, где сессию панели
заменяет `TelegramSessionActive` чата, бота и собеседника, проверенная в
транзакции ответа, а права там же проверяет хранилище. После коммита граф
продвигается, как после ответа из панели. Доставка ответа актору идёт своей
горутиной одновременно с ответом чату, а не после него: она длится до 40
секунд (`requestDeliveryTimeout`), а поллер бота установки один на всех его
пользователей; её исход зеркалит `answer_delivery`, остановка сервера ждёт
её. Повтор нажатия, который шлёт Telegram (порция после перезапуска), — тот
же автор с тем же исходом: успех без второй записи. Чату отвечает короткий
текст (`answerCallbackQuery` на нажатие, сообщение на reply и `/answer`):
состояние запроса после ответа — кто и когда ответил и выбранный вариант, —
или причина отказа: нет права, актор запроса исчез (ответить на запрос
больше нельзя), запрос исчез, граф больше не ждёт ответа, кнопка
недействительна. Отвеченный другим или отменённый запрос отвечает своим
состоянием и ничего не пишет. `/answer` и reply без ждущего текстового
запроса — отказ с причиной: формат, нет такого запроса в этом чате, запрос
отвечают кнопками. Нажатие, reply и `/answer` из чата без живой привязки
(снята, сессия отозвана) игнорируются без ответа, как его сообщения.

После ответа — из панели, CLI или Telegram — и после нажатия на закрытый
запрос отправитель правит отправленные сообщения запроса (`requestClosed`):
кнопки ответа уступают одной кнопке состояния `s:<номер>`, чья надпись
называет, кто и когда ответил, а нажатие показывает состояние тому, кто ещё
читает рой, и ничего не пишет. Текст сообщения не меняется: клиент Bot API
правит только клавиатуру (`editMessageReplyMarkup`) через бот, которым
сообщение отправлено. Сообщения выбираются не по правам в момент правки:
кнопки получил тот, кто управлял роем при отправке, и редактор, которого
потом понизили или убрали из роя, держал бы их вечно. Правится сообщение
каждого получателя, но только в чате его нынешней привязки: уведомление,
поставленное до неё, могло уйти в другой чат или через другой бот, где его
номер сообщения называет чужое сообщение (`TelegramRequestMessages`). Кто
читает рой сейчас, получает кнопку состояния, и viewer тоже; у того, кто рой
больше не читает, кнопки ответа снимаются без состояния. Правка — лучшая
попытка без outbox и повтора: отказ Telegram (сообщение больше не правится,
сообщение без кнопок не изменено), сбой сети или базы её пропускают,
ответа она не задерживает.
Ответ, пришедший, пока уведомление запроса было в полёте, правка ещё не
видит отправленным, поэтому отправитель после записи `sent` сверяет запрос
и правит это сообщение сам. Отмена запроса и остановка графа сообщений не
правят: оставшуюся кнопку правит первое нажатие на неё.

### Команды чата (#284)

Привязанный личный чат управляет brood от имени пользователя своей
привязки, с его правами (`telegramCommands`, `telegram_commands.go`). Имя
команды — в любом регистре. `/answer`, reply и текст без команды поллер
отдаёт ответам (#283, выше), прочие команды — адаптеру:

 - `/swarms [page]` — рои пользователя по правилу списков панели (проекты
   членства и рои с ролью, администратору — все) с исполнением и числом
   открытых запросов из той же сводки (`SwarmSummaries`);
 - `/swarm [swarm]` — роль пользователя, исполнение, снимок, текущий шаг с
   причиной, задача прохода, открытые запросы и managed-акторы;
 - `/use <swarm>` — рой по умолчанию чата в строке привязки
   (`SetTelegramSwarm`, схема 30); `/use` без роя называет его;
 - `/requests [page]` — открытые запросы роя по умолчанию в виде списка
   запросов панели (`swarmRequestViews`) и ссылка на страницу роя;
 - `/actors [swarm] [page]` — managed-акторы командой каталога `agents`;
 - `/start <swarm> <goal>` — новый проход на закреплённом снимке роя,
   commit — HEAD repository проекта, как у запуска из панели без commit;
   задача — текст после роя как есть, с переносами строк;
 - `/stop <swarm>` — остановка прохода;
 - `/actor <swarm> <name> stop|start|update|reset` — команда каталога того же
   имени, `reset` с `confirm`;
 - `/help` — перечень вместе с `/answer` и тем, как ответить на запрос
   кнопкой и reply; неизвестная команда — короткий отказ с её именем.

`/swarm`, `/requests` и `/actors` без роя берут рой по умолчанию. Рой
называют именем, `<проект>/<имя>`, когда имя повторяется в разных проектах
(тогда отказ перечисляет варианты), или id; рой с пробелом в имени — только
по id. Рой, который пользователь не читает, не найден, как в API. Рой по
умолчанию — свойство привязки пользователя: перепривязка чата его не
снимает, право читать рой проверяет каждая команда, а не запись, и рой без
права — отказ «выберите другой», а не показ. Удаление строки роя снимает его
(`ON DELETE SET NULL`).

Исполнение — те же методы сервера, что у панели и `bro`, своей логики
решений у адаптера нет: запуск — `startSwarmPass`, остановка — `stopSwarm`
(видимость роя, затем `StartSwarm`/`StopSwarm`, которые в транзакции записи
проверяют сессию `telegram` чата и право управлять роем), команды каталога —
проверки маршрута `POST /api/commands/{tool}` (`commandPreflight`: право на
рой, живой рой, его namespace) и исполнитель каталога. Право управлять
адаптер проверяет и до подтверждения: viewer получает отказ с нужной ролью
(«needs the owner or editor role in it; you are a viewer»), а не кнопку.
Право, потерянное до нажатия, отвергает сама запись. Отказ несёт публичную
причину отказа под ним: у запуска и остановки — набор
`swarmExecutionRefusal`, общий с HTTP, у каталога — `reason` (#276); прочая
ошибка — общий отказ без её текста, причина — в журнале сервера.
Неизвестный исход команды каталога назван неизвестным: она могла
подействовать, повторять — после проверки.

Сессия чата — сессия привязки, под которой пришло обновление
(`TelegramChatSession`): чат, отвязанный и привязанный снова, получает
новую. Где её проверяет запись:

 - `/start`, `/stop` и `/use` — в своей транзакции записи (`authorize`
   `StartSwarm`, `StopSwarm`, `SetTelegramSwarm`): привязка, умершая или
   сделанная заново до записи, ничего не меняет;
 - `/actor` — нет. Сессию чата адаптер кладёт полномочием сессии команды
   каталога, но его читают только команды сессии гостя; запись намерения
   жизненного цикла (`managedWorkloadOperation`) проверяет право и
   namespace, а сессию не проверяет — ни чата, ни веб-сессии `POST
   /api/commands`. Поэтому адаптер проверяет привязку при нажатии, перед
   командой каталога, и после неё. Привязка, умершая до команды, ничего не
   запускает; умершая, пока команда шла, её не останавливает: чат получает
   «no longer linked … may have taken effect», а не итог и не молчание.
   Проверка после команды идёт без срока команды (свой срок — 5 секунд):
   команда, упёршаяся в свой срок, не принимает его за отвязку; проверку,
   которая не удалась, чат видит неизвестным исходом. Проверка сессии в
   самой записи жизненного цикла закрыла бы окно и для веб-сессии: это
   изменение слоя жизненного цикла, #299.

`/start`, `/stop` и `/actor` исполняются только после нажатия кнопки.
Подтверждение (`telegram_confirm.go`) принадлежит чату — пользователю, боту
и чату под сессией его привязки — и живёт в памяти процесса: id — 96
случайных бит, `callback_data` — `c:<id>:y` или `:n`, 20 байт из 64. Срок —
2 минуты: нажатие в этот момент и позже, отмена, чужой чат, неизвестный id,
нажатие после новой привязки чата и перезапуск сервера ведут к «ничего не
сделано», само по себе подтверждение не исполняется никогда. Первое
подтверждающее нажатие в срок забирает действие под блокировкой; каждое
следующее — и тот же callback, который Telegram прислал снова, и второе
нажатие — узнаёт только, что действие идёт или прошло. Нажатие получает
ответ `answerCallbackQuery`, клавиатура решённого подтверждения снимается,
итог действия уходит в чат сообщением. Действие начинается с проверки
привязки: умершая после проверки поллера, пока нажатие ждало ответов Bot
API, ничего не исполняет и ответа не получает. Срок ограничивает и начало
действия: оно начинается не позже 10 секунд после срока подтверждения
(`telegramConfirmGrace`). Нажатие, принятое в срок, ждёт до действия ответа
нажатию и снятия клавиатуры, каждый до 30 секунд; без предела нажатие за
секунду до срока начинало бы действие почти через минуту после него.
Действие, которое они задержали дольше, не исполняется: чат получает
«expired before its action could start», повтор нажатия — «expired». Начало
действия — не его запись: проверки самого действия (проход, поколение
актора, проверки маршрута каталога) и запись идут после него в срок
команды. Поллер отдаёт адаптеру команд только нажатия кнопок `c:`; кнопки
ответа и состояния запроса (`a:`, `s:`) и прочие данные разбирают ответы
(#283, выше). Сам адаптер кнопку другого вида за подтверждение не
принимает: отказ без правки её клавиатуры.

Подтверждение держит то, что подтверждали. `/stop` — проход, который шёл
при подтверждении (проход последнего шага): после чужой остановки и нового
прохода нажатие отвечает «started another pass since you confirmed» и
ничего не останавливает. `/actor` — актора и его поколение: после чужого
`reset` или пересоздания актора того же имени нажатие отвечает «was reset
or replaced since you confirmed». Обе проверки — при нажатии, перед
командой, а не в её записи: окно между ними — чтения той же команды.
Рой, который пользователь больше не видит, эти проверки не называют: его
скрывает сама команда.

Память подтверждений ограничена на чат: открытых не больше восьми, сверх —
истекает самое старое; всего в памяти не больше 32, сверх — забывается
самое старое, кроме идущего. Исход помнится 10 минут после срока, если
предел не вытеснил его раньше; нажатие забытого лишь недействительно.
Нажатие из непривязанного чата остаётся без ответа.

Ответ укладывается в предел сообщения Bot API: списки — по 20 строк на
странице до 180 знаков каждая, с номером страницы и ссылкой на следующую,
имена — до 100 знаков, задача — до 1000. Поллер разбирает обновления бота
по одному, поэтому команда задерживает следующие обновления того же бота.
Срок команды или нажатого действия — минута (`telegramCommandTimeout`), и к
нему добавляются вызовы Bot API, каждый до 30 секунд (срок клиента): у
команды — `sendMessage` ответа, у нажатия — `answerCallbackQuery`,
`editMessageReplyMarkup` и `sendMessage` итога, и проверка привязки после
команды до 5 секунд, которая идёт и после её срока. Команда держит поллер
до 1 минуты 35 секунд, нажатие — до 2 минут 35 секунд. У бота установки
поллер один на всех его пользователей: медленная команда одного задерживает
обновления всех, и нажатие, которое ждало в очереди дольше срока
подтверждения, лишь истекает, ничего не сделав. Свои боты пользователей
этой очереди не делят.


## Egress к Bot API и выкладка

Кластер установки (kind, CNI kindnet) умеет только IP-правила стандартного
NetworkPolicy: FQDN-правил нет, а замена CNI означала бы пересоздание
production-кластера. Поэтому egress к Bot API — разрешение имени при каждой
выкладке (`telegram_egress`, `brood/dev/deploy/go_server.py`, #286): адреса
`BROOD_TELEGRAM_API` (по умолчанию `https://api.telegram.org`) резолвятся
и превращаются в правила TCP 443, как у Git remotes и Proxmox endpoints;
выкладка без работающего разрешения — отказ с именем настройки.

Хрупкость оговорена сознательно: адрес Telegram меняется между выкладками,
и тогда уведомления оседают в очереди (`failed` после отказов, `unconfirmed`
после неоднозначных отправок) до следующей выкладки с новыми адресами.
Средство — повторная выкладка. HTTP origin на loopback правил не даёт:
локальный сервер Bot API установки достигается внутри кластера.

Выкладка передаёт `BROOD_TELEGRAM_BOT_TOKEN`, `BROOD_TELEGRAM_API` и
`BROOD_PANEL_ORIGIN` в Secret и env сервера; секреты — только `.env` и
защищённые переменные CI, не в логи, ответы API и guest env.
