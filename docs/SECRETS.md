# Проектные секреты

`bro secret` переносит механизм `mop secret` в серверное хранилище Brood.
Это данные проекта, а не credentials установки, Proxmox или CI.
Управление доступно администратору через обычную HTTPS-сессию `bro`.
Проект указывается явно по ID или однозначному имени.

Виды секретов различаются назначением. `var` и `file` — данные приложения:
их получает актор проекта (раздел «Доставка»). `git` — серверные Git
credentials (раздел «Серверные Git credentials»): их использует только
серверный шлюз Git, актору они не передаются никогда.

```sh
bro secret --project PROJECT var add APP_TOKEN --stdin
bro secret --project PROJECT var add APP_TOKEN --value-file /private/token
bro secret --project PROJECT var list
bro secret --project PROJECT var remove APP_TOKEN

bro secret --project PROJECT file add .env config/service.json
bro secret --project PROJECT file list
bro secret --project PROJECT file remove .env config/service.json
```

Значение переменной не принимается в argv. Ввод из stdin или файла удаляет
не более одного завершающего перевода строки. Остальное значение сохраняется
без изменения; переносы строк внутри переменной запрещены. Файлы передаются
как непрозрачные байты, с относительными путями от корня Git checkout.
Симлинки, устройства, FIFO и выход за корень не принимаются. Пакет добавления
проверяется целиком до записи. Мутации молчат; list показывает только имена,
размеры файлов и revision, никогда значения. Read/export API отсутствует.

Секреты не объявлены MCP tools и недоступны через `bro --guest secret`.
Обычное проектное членство само по себе не даёт права управлять ими.

## Доставка

Поддерживается управляемый Proxmox Claude Code runtime с новым guest image.
Изменения применяются при следующем старте приложения, restart, recycle
или новом аттестованном шаге, а не инъекцией в работающий процесс.
Для нового шага супервизор получает проекцию после проверки запроса, но
держит её в памяти до доказанной остановки предыдущей сессии. Публикация
предшествует checkout и запуску нового приложения. При отказе получения
старую сессию не останавливают. При отказе публикации супервизор завершает
runtime с явной ошибкой: нельзя гарантировать прежнюю проекцию, поэтому
checkout, запуск шага и доставку инструкции не начинают. Для ворот с человеческим
решением подготовьте секрет до подтверждения, которое запускает акторский шаг.
Обновление сервера не заменяет guest image и не перезапускает существующих
пользовательских акторов.

Root supervisor получает только секреты текущего проекта по scoped токену
актора: сервер проверяет UID, generation, актуальную привязку роя и namespace.
Пользовательская cookie не даёт доступа к этому endpoint. Проекция хранится
в `/run/brood/project-secrets.json`, владелец root, группа 1000, режим 0440.
Фиксированный UID 1000 wrapper применяет файлы и добавляет переменные только
в окружение конечного процесса Claude Code. В root supervisor, session helper,
аргументы tmux и образ значения не добавляются.

Переменные доступны и без checkout. Доставка файлов требует существующего Git
checkout в `/workspace/project`: до публикации байтов проверяются отсутствие
пути в индексе и фактическое действие ignore-правил. Пользовательский
`.gitignore` не переписывается. Отрицательные правила, раскрывающие секрет,
вызывают отказ. Служебные Git/Claude control paths, включая `.gitignore` на
любой глубине, не принимаются как имена секретов.

У актора с origin первый старт приложения клонирует его до применения
файлов ([PROXMOX.md](PROXMOX.md), «Origin и первый клон»), поэтому файловые
секреты работают и на новом акторе. Без checkout — origin не задан или клон
не удался — Claude запускается только с переменными, а терминал сообщает,
что файлы не доставлены; байты не публикуются. Они появятся на следующем
старте после успешного клона.

Файлы создаются с режимом 0600. Пользовательские файлы не перезаписываются:
для замены или удаления ранее доставленного файла его hash должен совпадать
с учтённым. Manifest и журнал восстановления находятся вне workspace, в
приватном каталоге `/workspace/home/.config/brood/`, содержат имена и hashes,
но не значения. Журнал позволяет повторить прерванное применение. Симлинки,
hard links и небезопасные компоненты пути вызывают отказ. Linux filesystem
должна поддерживать `O_TMPFILE`; небезопасного fallback нет.

Native Substrate runtime пока не имеет приватного канала доставки. Запуск,
обновление, resume актора или golden template с секретами проекта отказывает,
а не помещает их в публичный template env и не пропускает молча.

## Границы доверия

Это не vault, скрывающий данные от самого актора. Его приложение и модель
с Read/Bash работают от UID 1000 и намеренно получают доступ к файлам и
окружению. Не выдавайте проекту credentials, которые его код не должен знать.
Git-ignore защищает обычный workflow, но не мешает доверенному актору самому
прочитать файл или выполнить `git add -f`.

SQLite и её snapshots содержат значения в открытом виде внутри приватного
хранилища. Шифрование at rest не заявляется. База создаётся с режимом 0600;
каталог, WAL, резервные копии и PVC должны оставаться приватными. Удаление
секрета не стирает исторические резервные копии.

Не допускаются переменные, меняющие identity, executable search, загрузчики,
интерпретаторы, Git execution policy и фиксированный model/proxy route.
Лимиты: 128 файлов и переменных, 512 KiB на файл, 2 MiB файлов в проекте,
16 KiB на значение переменной и 64 KiB на суммарное окружение секретов.
Имена файлов ограничены 1024 байтами, каждый компонент — 255 байтами.
Гостевое применение дополнительно ограничивает encoded manifest и Git excludes
64 KiB, журнал восстановления — 256 KiB. Переполнение, включая объединение
старых и новых имён для recovery, вызывает отказ до публикации байтов.

Приёмка использует только синтетические значения и собственные временные
ресурсы. Успех локальных CLI/server tests не доказывает доставку в работающий
Proxmox guest; это отдельная проверка закреплённого образа.

## Серверные Git credentials

```sh
bro secret --project PROJECT git add NAME --repository URL --username USER --stdin
bro secret --project PROJECT git add NAME --repository URL --username USER --value-file /private/token
bro secret --project PROJECT git list
bro secret --project PROJECT git remove NAME...
```

Git credential — имя, точный repository, к которому он привязан, и пара
HTTP Basic `username`/`token`. Им пользуется только сервер: шлюз Git
([PROXMOX.md](PROXMOX.md), «Origin актора и серверный шлюз Git») и
разрешение ветки проекта при первом запуске роя без commit
([MODEL.md](MODEL.md), «Запуск и остановка роя»). Сервер подставляет его в
upstream-запрос к этому repository. Актору, его окружению,
проекции секретов, bundle, образу, workspace endpoint, публичным DTO и логам
значение не передаётся. Это не `var`/`file`: credentials хранятся в отдельных
таблицах, не меняют revision доставляемых секретов и не включают отказ native
runtime из-за секретов проекта.

Имя — lowercase DNS label до 63 байт. Repository принимается как HTTPS или
SSH Git URL и привязывается в канонической HTTPS-форме (правила — пакет
`gitorigin`); userinfo, query и IP-адреса отвергаются. Username — видимый
ASCII без двоеточия до 256 байт, token — видимый ASCII до 4096 байт. Token не
принимается в argv: только stdin или обычный файл без симлинка с правами
только владельца (без доступа группы и остальных); снимается не более одного
завершающего перевода строки. Не более 16 credentials в проекте. `add` с
существующим именем — ротация: заменяет token, username и привязку целиком.
Мутации молчат; `list` печатает `NAME`, `REPOSITORY` и `active` или
`inactive`, никогда username или token. Отказ называет правило, а не
значение. Проверка ввода выполняется до сети.

Credential сам по себе доступа не даёт. Он **активен**, когда декларация
проекта ссылается на него (`project.git_credential` в Broodfile, см.
[BUILD.md](BUILD.md)) и repository проекта в точности равен его привязке.
Смена repository в декларации не переносит credential: старый token не уходит
другому серверу, пока администратор не привяжет credential к новому URL.
Ссылка может указывать на отсутствующее имя: удаление credential отзывает
доступ, а не ломает декларацию.

Ротация, удаление credential, снятие или смена ссылки и смена repository
действуют сразу, без перезапуска сервера: следующий запрос шлюза использует
новое состояние, открытый поток со старым credential отменяется в течение
секунды. Активный credential проекта имеет приоритет над записью того же
repository в `BROOD_GIT_REMOTES`.

Удаление проектного credential отзывает только его, а не legacy-доступ. Если
для того же repository в `BROOD_GIT_REMOTES` задан remote с учётными данными,
Git-доступ проекта остаётся: открытый поток со старым credential отменяется,
режим origin актора остаётся `gateway`, и следующий запрос шлюза уходит с
legacy token. Так же после снятия ссылки декларации. Запись `{}` тоже
оставляет режим `gateway`, но шлюз идёт к repository без учётных данных.
Чтобы закрыть доступ, уберите запись repository из `BROOD_GIT_REMOTES`
повторной выкладкой ([DEPLOY.md](DEPLOY.md), «Git remotes»).

API — только для администратора через cookie-сессию, same-origin и CSRF;
сессия и роль перепроверяются в транзакции записи:

- `GET /api/projects/{id}/secrets/git` —
  `{"items":[{"name":"...","repository":"...","active":true}]}`;
- `PUT /api/projects/{id}/secrets/git` — ровно
  `{"name":"...","repository":"...","username":"...","token":"..."}`;
  repository — HTTPS URL, сервер канонизирует его (SSH-формы переводит в HTTPS
  только `bro`);
- `DELETE /api/projects/{id}/secrets/git` — ровно `{"names":["..."]}`, 1..16 имён;
  отсутствующие имена безвредны.

Мутации отвечают тем же списком метаданных. Неизвестные и регистровые
варианты полей, повторы, `null`, другие типы и лишние документы — 400,
нарушение правил значения или лимита — 422, без повторения тела. Чтения
значения нет. Как и остальные секреты, credentials не объявлены MCP tools и
недоступны через `bro --guest secret`.

Credential хранится в открытом виде в той же приватной SQLite (0600), что и
остальные секреты; к базе, WAL, резервным копиям и PVC применяются те же
требования. Выдавайте отдельный token с минимальными правами одного
репозитория: любой код актора с режимом gateway может читать и пушить через
шлюз с этим token (модель доверия — [PROXMOX.md](PROXMOX.md), «Шлюз»).
