# Секреты проекта и доступ к Git

Переменные и файлы проекта доставляются агентам. SSH-ключ Git принадлежит
рою и настраивается отдельно.

Секретами проекта управляет только администратор.

## Переменные и файлы

**Переменная** — пара «имя и значение» в окружении сессии Claude Code
и всего, что она запускает.

**Файл** — содержимое по относительному пути внутри рабочей копии агента
`/workspace/project`. Файл `secrets/gh-token` появится у агента как
`/workspace/project/secrets/gh-token`.

### Пределы и правила имён

| Что | Предел |
| --- | --- |
| Переменных в проекте | 128 |
| Значение одной переменной | 16 КиБ, одна строка, без NUL |
| Все переменные вместе | 64 КиБ |
| Файлов в проекте | 128 |
| Один файл | 512 КиБ |
| Все файлы вместе | 2 МиБ |

Имя переменной — латинские буквы, цифры и `_`, не с цифры. Зарезервированы
и отвергаются:

- имена с префиксами `BROOD_`, `CLAUDE_`, `ANTHROPIC_`, `LD_`, `DYLD_`,
  `PYTHON`, `BASH_FUNC_`, `GIT_CONFIG_`;
- имена, которые меняют поведение оболочки, загрузчика, прокси и проверки
  сертификатов, среди них `HOME`, `PATH`, `USER`, `SHELL`, `ENV`, `BASH_ENV`,
  `IFS`, `NODE_OPTIONS`, `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`,
  `SSL_CERT_FILE`, `GIT_SSH_COMMAND`, `GIT_SSL_NO_VERIFY`.

Сравнение идёт без учёта регистра. Полный список — в
`go/brood/projectsecret/project_secret.go`.

Путь файла — относительный, до 1024 байт, без `..`, обратной косой черты
и двоеточия. Ни один компонент пути не может называться `.git`, `.gitignore`,
`.claude`, `.mcp.json` или `CLAUDE.md` (в любом регистре). Один секрет не
может быть каталогом для другого: `a` и `a/b` вместе — отказ.

## Объявление в brood.yaml

Секреты можно объявить в `brood.yaml` рядом с проектом. В файле записаны
только имена и локальные пути, значений в нём нет:

```yaml
vars:
  brood:
    project: my-project
    secrets:
      env: .env
      files:
        - path: secrets/gh-token
          source: secrets/gh-token
        - path: config/local.json
          source: deploy/agent-local.json
```

- `env` — локальный dotenv-файл. Каждая его переменная становится переменной
  проекта.
- `files[].source` — локальный файл, `files[].path` — путь, по которому он
  окажется в рабочей копии агента.

Пути `env` и `source` заданы относительно корня репозитория и должны
оставаться внутри него. Значения читаются из рабочего каталога, а не из
коммита, поэтому сами файлы с секретами обычно держат в `.gitignore`.

Формат dotenv: строки `KEY=VALUE`, пустые строки и комментарии с `#`.
Допускаются префикс `export ` и значение в одинарных или двойных кавычках;
в двойных кавычках `\"` и `\\` раскрываются. У значения без кавычек `#` после
пробела начинает комментарий. Ошибки называют файл и номер строки, но не её
содержимое.

### Что отправляет и удаляет bro build

Блок `secrets` объявляет набор секретов целиком. `bro build` приводит секреты
на сервере к этому набору:

1. читает значения и проверяет пределы до первого запроса к серверу;
2. запрашивает у сервера имена существующих секретов;
3. печатает в stderr, какие имена будут удалены и записаны. Значения не
   печатаются никогда;
4. удаляет переменные и файлы, которых нет в блоке, включая добавленные
   вручную;
5. записывает все объявленные заново: сервер не отдаёт значения, сравнить их
   нельзя.

```text
project secrets: remove variables: OLD_TOKEN
project secrets: set variables: GH_TOKEN, NPM_TOKEN
project secrets: set files: secrets/gh-token
```

| В `brood.yaml` | Что делает `bro build` |
| --- | --- |
| блока `secrets` нет | секреты на сервере не трогает |
| `secrets: {}` | удаляет все переменные и файлы проекта |
| блок с `env` и `files` | оставляет на сервере ровно объявленное |
| опция `--no-secrets` | не читает и не синхронизирует секреты |

`bro build --plan` показывает объявление без обращения к серверу: пути и имена
переменных из dotenv-файла, без значений.

## Управление вручную: bro secret

Проект в `bro secret` всегда называется явно, опцией `--project`. Значения не
принимаются аргументами и не печатаются. Успешное изменение ничего не выводит.

```text
usage: bro secret --project ID_OR_NAME file add|list|remove [PATH...]
       bro secret --project ID_OR_NAME var add NAME --stdin
       bro secret --project ID_OR_NAME var add NAME --value-file FILE
       bro secret --project ID_OR_NAME var list|remove [NAME...]
```

Переменные:

```sh
bro secret --project my-project var add GH_TOKEN --stdin < token.txt
bro secret --project my-project var add NPM_TOKEN --value-file ~/.secrets/npm
bro secret --project my-project var list
bro secret --project my-project var remove NPM_TOKEN
```

Значение читается со стандартного ввода или из файла; один завершающий перевод
строки отбрасывается. `var list` печатает только имена.

Файлы:

```sh
bro secret --project my-project file add secrets/gh-token config/local.json
bro secret --project my-project file list
bro secret --project my-project file remove config/local.json
```

`file add` запускается внутри рабочей копии Git. Источник — обычный файл, не
символическая ссылка, внутри этой рабочей копии. Имя секрета — путь файла
относительно её корня, и по тому же пути файл появится у агента. `file list`
печатает имена и размеры.

`add` с существующим именем заменяет значение. Если в `brood.yaml` есть блок
`secrets`, следующий `bro build` удалит всё добавленное вручную и не
объявленное в блоке.

## Как агент получает секреты

Секреты не входят в образ и не записываются в конфигурацию контейнера
в Proxmox. Агент забирает их с сервера сам:

1. Служба `brood-guest` от имени root запрашивает набор секретов проекта
   по адресу `/api/proxmox/secrets/{uid}/{generation}` с токеном агента.
   Сервер отдаёт секреты того проекта, которому принадлежит рой агента.
2. Набор кладётся в `/run/brood/project-secrets.json`: владелец root, чтение
   для группы пользователя `actor`. `/run` — файловая система в памяти.
3. При запуске сессии обёртка от имени `actor` добавляет переменные
   в окружение Claude Code и раскладывает файлы в `/workspace/project`.

Запрос выполняется при старте службы агента, то есть при создании и запуске
контейнера, и при перезапуске сессии. Чтобы работающий агент получил
изменённые секреты, перезапустите его сессию: `bro restart NAME`. Идущая
сессия новых значений не видит.

Особенности доставки файлов:

- Файлам нужна рабочая копия Git в `/workspace/project`. Если её нет,
  например клонирование не удалось или у проекта нет репозитория, сессия
  запускается без файлов-секретов, с предупреждением в терминале. Переменные
  доставляются в любом случае.
- Пути секретов добавляются в `.git/info/exclude`, чтобы файлы не попали
  в коммит. Файл `.gitignore` репозитория не меняется.
- Файл, удалённый из секретов проекта, удаляется из рабочей копии при
  следующем запуске сессии.
- Доставка не перезаписывает чужое. Если по пути секрета в репозитории лежит
  отслеживаемый файл или доставленный файл изменили в рабочей копии руками,
  доставка отказывает и сессия не запускается, пока конфликт не устранён.

Токен агента привязан к его поколению ([MODEL.md](MODEL.md)): после `reset`,
остановки или удаления агента старый токен секретов не получит.

## SSH-ключ роя для Git

При создании роя Brood генерирует отдельную пару Ed25519. Владелец роя и
администратор видят только публичный ключ: **Рои → нужный рой → Git SSH key**.
Чтобы дать рою доступ к закрытому репозиторию:

1. Добавьте публичный ключ в настройки репозитория на Git-хостинге как
   deploy key. Разрешайте запись только если агентам нужен `git push`.
2. Укажите SSH-адрес репозитория проекта, например `git@git.example.com:team/app.git`.
   Агент сохраняет SSH-адрес в `origin`; `clone`, `fetch` и `push` идут
   напрямую из контейнера. Из контейнера должен быть доступен SSH-порт Git.

Закрытый ключ хранится в базе сервера и доставляется по защищённому соединению
при старте только агентам этого роя. Все они используют один ключ. Он доступен
процессам пользователя `actor`, поэтому давайте ключу доступ только к нужным
репозиториям. Ключ не входит в образ и не сохраняется в рабочую копию.
OpenSSH при первом соединении запоминает ключ Git-хоста и отклоняет его
изменение. Для проверки до первого соединения заранее добавьте сверенный ключ
Git-хоста в `~/.ssh/known_hosts` или в системный `known_hosts` образа.

Удаление роя или пересоздание базы не отзывают уже выданный доступ на
Git-хостинге. Удалите там deploy key. После пересоздания роя добавьте его
новый публичный ключ. Системный SSH-ключ установки для подключения сервера
к контейнеру к Git-ключам роёв не относится.

## Что где хранится и что не печатается

- Значения переменных, файлов и закрытые ключи роёв хранятся в базе SQLite сервера без
  шифрования. Защищайте файл базы и её резервные копии как секрет.
- API не возвращает значения: по запросу отдаются только имена, размеры
  файлов. Для Git API панели возвращает только публичный ключ роя.
- `bro` не принимает значения аргументами командной строки, не печатает их
  и не включает в сообщения об ошибках. `bro build` печатает только имена.
- В `brood.yaml` и в Git значений нет: только имена и пути.
- В образ агента и в конфигурацию контейнера в Proxmox секреты не попадают.
- У агента переменные и файлы доступны пользователю `actor` и всему, что он
  запускает. Агент может прочитать и вывести их: давайте проекту токены
  с минимальными правами.
