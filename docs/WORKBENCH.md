# WORKBENCH

Окружение актора для сборки Brood, его проверок и тестовой выкладки в собственный
Substrate. Команды -- `brood workbench`, код -- `brood/dev/workbench`.

Корневой Broodfile использует доверенную LXC-нагрузку с общим ядром VM.
Для вложенных Docker и kind нужен отдельный пул с явным opt-in профилем
`ate.dev/lxc-nesting=enabled`. Он добавляет только FSETID, KILL, AUDIT_WRITE и
SYSLOG к базовому набору LXC-воркера; сам worker pod не становится privileged.
Профиль допускает чтение общего kernel log и не предназначен для враждебных
нагрузок. В этом классе OCI allowlist актора не является дополнительной
изоляцией: верхнюю границу задаёт профиль воркера. Docker socket, kubeconfig
и credentials машины установки внутрь актора не передаются.

Изменение nesting-метки вызывает rollout воркеров и может вытеснить акторы.
Создавайте отдельный пустой пул; не включайте профиль на занятом пользовательском
пуле. Обычные LXC-пулы и остальные классы без opt-in сохраняют прежние права.

## Состояние проверки

Перенос полного development/coding workbench в LXC отслеживается в #96.
Описанные ниже прогоны microVM — исторические результаты, не доказательство
успешного полного цикла в LXC. Для LXC итогом остаётся собственный
`status.json=passed` после HTTPS-проверки вложенного Go endpoint; состояние
Actor `RUNNING`, доступный PTY или успешный rollout этого не заменяют.

Исторический прогон до Go-переезда: на 2026-10-26 внутри microVM прошли
239 Python-тестов, ruff, 1676 тестов старой панели,
lint, проверка типов и production-сборка панели. В том же акторе поднят
вложенный kind, из исходников установлен отдельный Substrate, собраны образы
Brood и завершена выкладка. Штатная HTTPS-проверка тестового сервера прошла;
`status.json` вернул `passed` через mTLS маршрутизатора. Чтение результатов через mTLS
маршрутизатора и сохранение диагностики при отказе старта Docker проверены.

Для вложенного Kubernetes нужны подготовка cgroup v2, настоящий `/dev/kmsg`
и блочная ФС для Docker. У kind-ноды отсутствовал `/dev/kmsg`,
из-за чего kubelet не запускался. Прямая проверка создания и чтения настоящего
устройства `c 1:11` внутри гостя успешна: отсутствие node в `/dev` не означало
запрет доступа. Загрузчик создаёт этот node перед Docker, проверяет тип,
major/minor и возможность открытия. Симлинк, обычный файл или другое устройство
не принимаются. Runtime, его разрешения и устройства физического хоста не
меняются. Проверенный исходный commit приложения -- `1eab4e4`, с отдельным
исправлением локализованного frontend-теста из #17. Полный цикл окружения
и его ограничения отслеживаются в #16.
Холодная сборка всего Substrate на 4 CPU занимает десятки минут. Тихий
интервал сам по себе не доказывает ни зависание, ни компиляцию: установщик
разрешает и собирает `ko` до появления подробного вывода. Проверяйте реальные
подпроцессы, загрузки и ошибки, а не только последнее сообщение стадии.

Этот результат не доказывал новый Go-only guest pipeline. На этапе удаления
legacy его полный прогон требовал отдельной свободной microVM; действующий
пользовательский coding-актор не использовался для проверки. На локальном
стенде 2026-10-27 отсутствовали `/dev/kvm`, WorkerPool и зарегистрированные
воркеры. Native Go API/CLI e2e и suspended-actor проверки прошли отдельно
(`docs/GO.md`). Новая публикация использует уникальный tag и digest metadata
конкретного buildx-вызова, не общий изменяемый tag.

Повторная приёмка #26 на 2026-10-29 использует отдельный проверочный пул на
VM с 24 CPU, примерно 38Gi RAM и `/dev/kvm`. Оба корневых target собраны из
чистого commit `4f57f2c9b5f6899e9fbefe4e95cb5f70e2bc8b85`; общий digest образа —
`sha256:5430095184f1b0c4efcc94f88a7bef91e7df371971f116b7b04b75f1275ca18b`.
Ресурсы шаблонов сохранены: 4000m CPU и 8Gi RAM. Полные OCI layers и
артефакты проверены на согласованность digest и отсутствие секретов оператора.

В двух development-прогонах прошли 274 Python-теста, ruff, 1742 проверки
панели, lint, типы, embedded bundle, Go-тесты и сборка обоих бинарников.
Вложенный kind был создан, но установка native Substrate завершилась
`connection reset by peer` при загрузке Go-зависимостей. Поэтому полного
Go-only `status=passed` эти прогоны не доказывают. Наличие готового kind
или сообщение стадии сборки native-образов не заменяет итоговую HTTPS-проверку.

Coding target проверен в настоящем браузере через Go BFF и mTLS router:
CLI `2.1.310` показывает welcome/theme без входа, ArrowDown меняет выбор темы,
переподключение сохраняет PID CLI и время создания tmux-сессии. Без сессии BFF
возвращает 401; capability-view отвергает чужой Origin с 403. Native router
без клиентского сертификата завершает TLS с `certificate required`.
Политика coding применяется отдельно к актору до использования CLI: шаблон
не передаёт ему EgressPolicy автоматически. Credentials оператора не
передавались, модельные запросы и платные вызовы не выполнялись.

Итоговая приёмка #26 на 2026-10-30 завершена на чистом корневом Broodfile
из commit `026963f1bab045168afd33e8029cd831b8442011`, без наложенных исправлений.
Оба target собраны настоящим `bro build`; общий digest —
`sha256:6c9266e8ec89ae598a43b43920ded847a18bb890989b040637acf77b22ee301d`.
Сохранены корневые command/args, 4000m CPU, 8Gi RAM и политика каждого профиля;
OCI descriptors/layers проверены по digest и на отсутствие секретов оператора.

В отдельной development-microVM прошли 296 Python-тестов, ruff, 1742 теста
панели, lint, типы, bundle, Go-тесты и сборка обоих бинарников. В её собственном
Docker/kind установлен закреплённый fork `f5d03ca0`, подготовлен gVisor и
выложен приватный Go endpoint. Реальная HTTPS-проверка с проверкой CA и имени
успешна; итоговый `status.json=passed` независимо прочитан через mTLS.
Отдельный coding-актор из того же digest прошёл browser welcome, ArrowDown,
переподключение с прежним PID и tmux session time, отказы 401/403 и TLS-отказ
без клиентского сертификата. Enter, вход и модельные запросы не отправлялись.

После сохранения результата development-VM удалена штатным native DeleteActor
с precondition по UID: её полностью вложенные Docker/kind удалены вместе с VM.
Это не доказательство исполнения `substrate uninstall` внутри этого гостя.
Подтверждены отсутствие VM sockets и нулевые allocations перед следующим
актором. Затем удалены coding-актор, оба шаблона и только собственные
проверочные рой, проект и пул. UID и состояние пользовательского актора,
а также UID/spec исходного пула остались прежними. Пользовательский актор
оставался в ранее возникшем `CRASHED`; Revert и восстановление не выполнялись.
Свежая LXC/gVisor-приёмка и граница несовместимой production-базы — `docs/LXC.md`.

## Состав

- Python той же версии и по тому же digest, что `.ci/test.sh`;
- Go по версии и SHA-256 из общего `brood/dev/pins.json`;
- закреплённые Docker Engine, CLI и buildx;
- исходный commit Brood и закреплённый в установщике commit Substrate;
- локальные wheels зависимостей extra `dev` из `pyproject.toml`;
- Go-клиент `bro` для единой сборки из Broodfile; отдельного Python compiler нет.

Образ сейчас собирается для amd64. Локальные Broodfile, Dockerfile, загрузчик
и сценарий берутся из текущих рабочих файлов, включая изменения без commit.
Запрошенная Git metadata реконструируется shallow, без локальных `.env`,
`secrets/`, credential helper или истории до HEAD. Внешний Substrate закреплён commit.

## Сборка и шаблон

Из каталога с Broodfile, без требования локальной установки Substrate:

```sh
bro build --help
bro build --plan                    # проверенный план development без Docker
bro build                           # локальный OCI-образ и комплект development
bro build coding                    # тот же environment, интерактивный шаблон
bro build --export PATH             # текущий переносимый контекст без Docker
bro push coding --project WORKSPACE # публикация через текущую bro login сессию
```

`--export` требует новый каталог и не публикует образ. Внешние источники
читаются по закреплённому commit. Контракт — `docs/BUILD.md`.

Результаты лежат в `.brood/build/development/` и `.brood/build/coding/`:
`actor-template.json`, `egress-policy.json`, `build.json`, `image.oci.tar`.
`bro push` загружает OCI chunks через авторизованный API и регистрирует шаблон
в выбранном личном рое; atespace назначается сервером после проверки прав. Новый
образ или runtime spec получает новое имя шаблона по hash. Golden snapshot
выключен. Сама сборка ничего в Substrate не регистрирует и не запускает.

`bin/brood workbench build` — тонкая dev-обёртка над внешним Go `bro build`;
`bro` должен быть в PATH. Она не содержит второго compiler/schema и использует
`BUILD_PROJECT` как необязательное имя назначения. `workbench template` остаётся инструментом
явного формирования runtime/pool/policy. Для обычной сборки используйте
`bro build`: он сохраняет весь согласованный комплект артефактов.

## Пул и ресурсы

Оба шаблона требуют три метки в `WorkerPool.metadata.labels`:
`brood.dev/purpose=development`, `brood.dev/sandbox=lxc` и
`ate.dev/lxc-nesting=enabled`. Меток в `spec.template.labels` для планировщика
недостаточно; зарезервированную `ate.dev/lxc-nesting` туда помещать нельзя.
Рабочий пул установки не меняется. Манифест отдельного пула:

```sh
brood workbench template --kind pool --image LXC_WORKER_AT_DIGEST
```

Пул `brood-development`, namespace `brood`, класс lxc, SandboxConfig
`lxc-image`, amd64. Requests -- 2 CPU / 8Gi, limits -- 6 CPU / 10Gi. Актор
запрашивает 4 CPU / 8Gi. LXC-воркер имеет один actor slot: для одновременных
development и coding нужны как минимум два воркера. Образ воркера берётся
из разрешённых образов установки, не из образа задания.

Нужен дисковый запас под Docker, исходники и kind. В LXC `durableDir` должен
находиться на настоящем ext4: `/workspace/docker` используется напрямую, без
loop-устройств общего ядра и без sparse-образа. Старый `docker.ext4` в workspace
вызывает отказ: переносите данные явно или используйте свежий актор.
`vfs` копирует слои целиком и расходует больше места, чем overlay2; квоты на
весь workspace нет, поэтому контролируйте свободное место машины установки.

Историческая microVM-подготовка использовала приватный sparse-образ ext4 32Gi.
В приёмке 2026-10-30 на диске около 100GB свободное место уменьшилось с 41GB
до примерно 9GB, хотя само задание уже завершилось успешно. При падении ниже
порога запаса 12GiB была приостановлена только собственная VM; после чтения
результатов она была кратко возобновлена и удалена. Перед coding-прогоном
освободилось около 46GB. Дополнительно удалялись только неиспользуемые private
BuildKit cache records, привязанные к конкретным CI-сборкам этого проекта;
общего prune, удаления чужих образов, томов или данных не было. Размер sparse
образа не заменяет контроль свободного места хоста и резерв для других работ.

## Запуск

После создания проекта, пула и шаблона на машине установки:

```sh
brood workbench run --atespace brood-development \
  --template brood-build-test-deploy --name build-001
```

Команда проверяет владение установкой и development-селектор шаблона, создаёт
новый актор, затем его `default` EgressPolicy, и только после этого возобновляет
актор. Уже существующий актор не перезаписывается. Если политика не создалась,
новый актор остаётся приостановленным, без запущенной нагрузки.

Политика -- отдельный объект каждого актора, а не поле, наследуемое от
ActorTemplate. Если актор создаётся другим клиентом, сначала создайте ему
политику из:

```sh
brood workbench template --kind policy --atespace brood-development --actor build-001
```

Разрешены конкретные публичные хосты сборки: PyPI, npm, GitHub, Go proxy,
реестры и источники артефактов. TLS идёт без MITM на 443; HTTP -- только к
пакетным репозиториям Debian на 80. Остальное запрещено. Дополнительный точный
хост задаётся `--allow-host HOST` при запуске или генерации политики. Wildcard,
URL, IP и локальные имена не принимаются. GitLab-токен и ключи оператора в
образ не попадают; доступ к приватному origin этим шаблоном не выдаётся.

## Что выполняется внутри

Начальный код копируется в `/workspace/brood` и `/workspace/substrate` только
один раз. Уже существующая работа на томе не заменяется. Новый тестовый `.env`
и TLS создаются на месте; секреты случайные, файлы имеют режим 0600.

Docker слушает только собственный unix socket. Native LXC выставляет
`container=lxc`; загрузчик выбирает LXC-подготовку по этому маркеру. Сначала
проверяются ext4 workspace и отсутствие подмен путей. Затем mount propagation
корня отделяется через `--make-rprivate /`, чтобы будущие mount-операции Docker
не распространялись обратно в namespace воркера. Создаётся private devpts с
`newinstance`, `/dev/ptmx` указывает на его `pts/ptmx`. Чужие файлы и симлинки
не перезаписываются. Проверяется настоящее устройство `/dev/kmsg` c 1:11;
файл, `/dev/null` или отсутствие разрешения чтения не принимаются.

При старом microVM-запуске без LXC-маркера сохранена подготовка отдельного
`docker.ext4` и loop-устройства приватного ядра гостя. Неизвестный runtime
вызывает отказ, а не fallback на loop-устройства общего ядра.

Блочная ФС нужна cAdvisor в kubelet: Docker root непосредственно на virtio-fs
виден как `device=none`. В LXC durable workspace уже является ext4 и не требует
дополнительного форматирования.

Затем запускается `dind` из закреплённого образа Docker: он подготавливает
cgroup v2 для вложенных контейнеров. Одного монтирования cgroup2 недостаточно
для systemd в kind-ноде. Временные файлы и Go cache также находятся на рабочем
томе, не в RAM-backed rootfs гостя.

`.ci/workbench.sh` последовательно выполняет:

1. `bin/brood dev setup`, `bin/brood dev test -v`, `venv/bin/ruff check .`;
2. `bin/brood dev web test` — проверки исходной React-панели и пересборку bundle;
3. настоящие `go test ./...` и сборку двух Go-бинарников;
4. `bin/brood substrate install` и `bin/brood substrate start` в собственном Docker;
5. `bin/brood workbench prepare`: только в госте с локальным socket и своим
   checkout/кластером, проверяет владение, создаёт namespace/SA/RBAC без
   перезаписи существующих объектов, собирает pinned gvisor worker image и
   дописывает разрешённый digest в приватный `.env`;
6. `bin/brood deploy go`: отдельный Go Deployment/PVC и приватный HTTPS
   Service, без public cutover и без переноса production-пользователей;
7. `.ci/workbench-https.sh`: ограниченная по времени HTTPS-проверка `/healthz`
   с guest CA, проверкой имени, ответом 200 и телом `ok`. Собственный port-forward
   слушает только loopback, получает свободный порт от ОС и удаляется по EXIT.

`passed` этого сценария означает успешные проверки, сборку, rollout и проверенный
HTTPS-ответ приватного endpoint. Это не проверка публичного ingress или доступа
к реальному актору через новый Go Deployment; такие e2e-доказательства
фиксируются отдельно.

Вложенный тестовый Substrate использует gvisor: `/dev/kvm` внутрь актора не
передан, второй уровень аппаратной виртуализации не нужен и не заявляется.
Имена kind-кластера и registry совпадают с обычной установкой, но относятся к
другому Docker daemon внутри гостя. Управление рабочим кластером исключено
отсутствием его socket, credentials и kubeconfig.

## Актор с Claude Code

Тот же образ содержит native CLI Claude Code `2.1.310`, ttyd и tmux.
В Debian 13 пакета ttyd нет: версия `1.7.7` собирается из исходного архива
upstream, закреплённого SHA-256, со штатными библиотеками Debian и libuv backend.
Linux x64 binary закреплён SHA-256 из официального `manifest.json`; при
выборе pin подпись manifest проверена ключом с fingerprint
`31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`. Сборка проверяет checksum binary.
Установщик с незакреплённым `curl | bash` не используется.

```sh
brood workbench template --profile claude-code --image IMAGE_AT_DIGEST \
  --atespace brood-development
brood workbench run --atespace brood-development \
  --template brood-claude-code --name claude-code
```

Профиль не запускает CI автоматически. Он готовит workspace и Docker,
печатает версию CLI и обслуживает терминал ttyd на порту 80. При подключении
открывается Claude Code в tmux-сессии `claude`, из каталога проекта.
Отключение браузера не завершает tmux-сессию; это не гарантия cold restart
или suspend/resume VM. Сервер результатов этого профиля слушает 8081.
`ready` означает готовность workspace/Docker, а не авторизацию CLI.

Терминал даёт управление доверенным LXC-контейнером с общим ядром VM. Он доступен только
через аутентифицированный Substrate Router; не публикуйте его отдельным
открытым портом. В ttyd включены ввод и проверка WebSocket Origin. Прокси
должен сохранять исходные Host/Origin и подставлять фиксированный
`ate-target-actor`, а не принимать цель от браузера.

Launcher выбирает egress из маркера профиля в самом шаблоне. Только coding-
профиль дополнительно разрешает точные хосты Anthropic API, входа и документации.
Обновления CLI, необязательная телеметрия, автоматические claude.ai MCP
connectors и Artifact отключены; wildcard-хостов нет. Build-профиль сохраняет
прежний список хостов.

API-ключи, OAuth-сессия и SSH-ключи оператора не копируются. Авторизация
выполняется пользователем внутри CLI со своей учётной записью; состояние
остаётся в HOME данного актора. Задача модели при создании актора не
отправляется. Без отдельной авторизации CLI не сможет выполнять модельные
запросы. См. официальные инструкции:
https://code.claude.com/docs/en/setup и
https://code.claude.com/docs/en/network-config.

Сборка требует Git-рабочее дерево или дерево из `--export`; релиз, полученный
только через `git archive`, не содержит Git metadata для снимка исходников.

## Результаты и доступ

Основной HTTP-порт актора -- 80. Он обслуживает только `/workspace/results`:

- `/status.json` -- состояние `starting`, `ready`, `testing`, `deploying`, `passed` или `failed`;
- `/workbench.log` -- вывод задания.

Из кластера эти пути доступны через HTTPS-сервис
`atenet-router.ate-system.svc:443` с заголовком
`ate-target-actor: brood-development/build-001`. Нужны доверенный клиентский
сертификат Substrate Pod Identity и CA Service DNS, не kubeconfig или TLS
самого Brood. Чтение `/status.json` через mTLS проверено на живом акторе.
Сервис router не предоставляет HTTP-порт 80; старые примеры port-forward
`8000:80` здесь не работают. Сам сервер результатов не требует пароля:
доступ к нему ограничивает маршрутизатор Substrate.

Статус Actor `RUNNING` означает, что окружение запущено, а не что тесты уже
завершились. Итог задания -- `status.json`. После успеха или ошибки актор
остаётся доступен для разбора; автоматического удаления рабочего тома нет.

Go endpoint слушает HTTPS Service:8443 во вложенном кластере; публичный
NodePort не создаётся. Проверка через loopback port-forward использует
сгенерированный guest-сертификат. Подготовка сама не создаёт пользователей:
для login-проверки нужен отдельный `brood bootstrap-admin`. Файлы настроек
и TLS не отдаются сервером результатов.

LXC не поддерживает memory checkpoint или автоматическое восстановление
процессов. В шаблоне указано предпочтение VOLUMES: холодная загрузка с томами,
не сохранение RAM. Оно не добавляет неподдерживаемые backend-операции snapshot
или suspend/resume. Для нового прогона используйте новый актор; durable workspace
не заменяет Git или резервную копию.
