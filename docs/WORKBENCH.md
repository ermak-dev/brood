# WORKBENCH

Окружение актора для сборки Brood, его проверок и тестовой выкладки в собственный
Substrate. Команды -- `brood workbench`, код -- `brood/dev/workbench`.

Это доверенная development-нагрузка: контейнер получает полный набор capabilities
внутри отдельного ядра microVM, чтобы запускать Docker и privileged kind-ноду.
Устройства, Docker socket и kubeconfig машины установки ему не передаются.
Для враждебных нагрузок такое окружение не предназначено.

## Состояние проверки

Исторический прогон до Go-переезда: на 2026-10-26 внутри microVM прошли
239 Python-тестов, ruff, 1676 тестов старой панели,
lint, проверка типов и production-сборка панели. В том же акторе поднят
вложенный kind, из исходников установлен отдельный Substrate, собраны образы
Brood и завершена выкладка. Штатная HTTPS-проверка тестового сервера прошла;
`status.json` вернул `passed` через mTLS маршрутизатора. Чтение результатов через mTLS
маршрутизатора и сохранение диагностики при отказе старта Docker проверены.

Для вложенного Kubernetes нужны подготовка cgroup v2, настоящий `/dev/kmsg`
и блочная ФС для Docker. У kind-ноды отсутствовал `/dev/kmsg`,
из-за чего kubelet не запускался. Прямая проверка создания и чтения настоящего
устройства `c 1:11` внутри гостя успешна: отсутствие node в `/dev` не означало
запрет доступа. Загрузчик создаёт этот node перед Docker, проверяет тип,
major/minor и возможность открытия. Симлинк, обычный файл или другое устройство
не принимаются. Runtime, его разрешения и устройства физического хоста не
меняются. Проверенный исходный commit приложения -- `1eab4e4`, с отдельным
исправлением локализованного frontend-теста из #17. Полный цикл окружения
и его ограничения отслеживаются в #16.
Холодная сборка всего Substrate на 4 CPU занимает десятки минут; тихий
интервал компиляции сам по себе не означает зависание.

Этот результат не доказывает новый Go-only guest pipeline. После удаления
legacy его полный прогон требует отдельной свободной microVM; действующий
пользовательский coding-актор не используется для проверки. На локальном
стенде 2026-10-27 отсутствовали `/dev/kvm`, WorkerPool и зарегистрированные
воркеры. Native Go API/CLI e2e и suspended-actor проверки прошли отдельно
(`docs/GO.md`). Новая публикация использует уникальный tag и digest metadata
конкретного buildx-вызова, не общий изменяемый tag.

## Состав

- Python той же версии и по тому же digest, что `.ci/test.sh`;
- Go по версии и SHA-256 из общего `brood/dev/pins.json`;
- закреплённые Docker Engine, CLI и buildx;
- исходный commit Brood и закреплённый в установщике commit Substrate;
- локальные wheels зависимостей extra `dev` из `pyproject.toml`;
- Go-клиент `bro` для единой сборки из Broodfile; отдельного Python compiler нет.

Образ сейчас собирается для amd64. Снимки Git shallow: в них нет локального
`.env`, `secrets/`, credential helper или истории до выбранного commit.
Загрузчик workbench, Dockerfile и сценарий задания берутся из того же commit,
что корневой `Broodfile`. Незакоммиченные изменения в снимок не накладываются;
команда сообщает об их исключении.

## Сборка и шаблон

На машине установки с принадлежащим ей Substrate:

Экспортируйте `BUILD_REGISTRY` и `BUILD_ATESPACE` из доверенного `.env` либо передайте
`--registry` и `--atespace`. Команды читают только выбранный Git commit:

```sh
bro build --plan                    # проверенный план development без Docker
bro build                           # образ и комплект development
bro build coding                    # тот же environment, интерактивный шаблон
bro build --ref COMMIT --export PATH # чистый переносимый контекст без Docker
```

`--export` требует новый каталог и не публикует образ. Внешние источники
читаются по закреплённому commit. Контракт — `docs/BUILD.md`.

Результаты лежат в `.brood/build/development/` и `.brood/build/coding/`:
`actor-template.json`, `egress-policy.json`, `build.json`. Шаблон регистрируется
через авторизованный API или инструменты Substrate; редактора JSON в минимальной
Go-панели нет. Atespace берётся из контекста сборки. Новый
образ или runtime spec получает новое имя шаблона по hash. Golden snapshot
выключен. Сама сборка ничего в Substrate не регистрирует и не запускает.

`bin/brood workbench build` — тонкая dev-обёртка над внешним Go `bro build`;
`bro` должен быть в PATH. Она не содержит второго compiler/schema и использует
`BUILD_REGISTRY`/`BUILD_ATESPACE`. `workbench template` остаётся инструментом
явного формирования runtime/pool/policy. Для обычной сборки используйте
`bro build`: он сохраняет весь согласованный комплект артефактов.

## Пул и ресурсы

Шаблон выбирает только воркеры с меткой `brood.dev/purpose=development` в
`WorkerPool.metadata.labels`: меток в `spec.template.labels` для планировщика
недостаточно, они относятся к подам.
Рабочий пул установки не меняется. Манифест отдельного пула:

```sh
brood workbench template --kind pool --image MICROVM_WORKER_AT_DIGEST
```

Пул `brood-development`, namespace `brood`, класс microvm, SandboxConfig
`microvm`, amd64. Requests -- 2 CPU / 8Gi, limits -- 6 CPU / 10Gi. Актор
запрашивает 4 CPU / 8Gi; два таких актора на один воркер не помещаются.
Образ воркера берётся из разрешённых образов установки, не из образа задания.

Нужен дисковый запас под Docker, исходники и kind. Внутри `durableDir` Docker
получает sparse-образ ext4 логическим размером 32Gi; физически файл растёт по
мере записи. Это ограничивает его файловую систему, но не остальные файлы
workspace: общей квоты у `durableDir` нет. `vfs` копирует слои целиком и
расходует больше места, чем обычный overlay2; за свободным местом машины
установки нужно следить. При копировании образа сохраняйте разрежённость.

## Запуск

После создания проекта, пула и шаблона на машине установки:

```sh
brood workbench run --atespace brood-development \
  --template brood-build-test-deploy --name build-001
```

Команда проверяет владение установкой и development-селектор шаблона, создаёт
новый актор, затем его `default` EgressPolicy, и только после этого возобновляет
актор. Уже существующий актор не перезаписывается. Если политика не создалась,
новый актор остаётся приостановленным, без запущенной нагрузки.

Политика -- отдельный объект каждого актора, а не поле, наследуемое от
ActorTemplate. Если актор создаётся другим клиентом, сначала создайте ему
политику из:

```sh
brood workbench template --kind policy --atespace brood-development --actor build-001
```

Разрешены конкретные публичные хосты сборки: PyPI, npm, GitHub, Go proxy,
реестры и источники артефактов. TLS идёт без MITM на 443; HTTP -- только к
пакетным репозиториям Debian на 80. Остальное запрещено. Дополнительный точный
хост задаётся `--allow-host HOST` при запуске или генерации политики. Wildcard,
URL, IP и локальные имена не принимаются. GitLab-токен и ключи оператора в
образ не попадают; доступ к приватному origin этим шаблоном не выдаётся.

## Что выполняется внутри

Начальный код копируется в `/workspace/brood` и `/workspace/substrate` только
один раз. Уже существующая работа на томе не заменяется. Новый тестовый `.env`
и TLS создаются на месте; секреты случайные, файлы имеют режим 0600.

Docker слушает только собственный unix socket. Перед daemon создаётся и
проверяется настоящий гостевой `/dev/kmsg`, а `/workspace/docker.ext4`
подключается к loop-устройству гостя и монтируется в `/workspace/docker`.
Чужое монтирование, симлинк, неверная ФС и старые немонтированные Docker-файлы
не заменяются и не скрываются. Уже существующий образ не форматируется.
При неудачном монтировании loop-ассоциация остаётся для разбора: она могла
существовать до этого запуска. Это не loop-устройство физического хоста.

Блочная ФС нужна cAdvisor в kubelet: Docker root непосредственно на virtio-fs
виден как `device=none` и не позволяет запустить kind-ноду. Форматирование,
монтирование ext4 и запись внутри отдельного гостя проверены реально.

Затем запускается `dind` из закреплённого образа Docker: он подготавливает
cgroup v2 для вложенных контейнеров. Одного монтирования cgroup2 недостаточно
для systemd в kind-ноде. Временные файлы и Go cache также находятся на рабочем
томе, не в RAM-backed rootfs гостя.

`.ci/workbench.sh` последовательно выполняет:

1. `bin/brood dev setup`, `bin/brood dev test -v`, `venv/bin/ruff check .`;
2. настоящие `go test ./...` и сборку трёх Go-бинарников;
3. `bin/brood substrate install` и `bin/brood substrate start` в собственном Docker;
4. `bin/brood workbench prepare`: только в госте с локальным socket и своим
   checkout/кластером, проверяет владение, создаёт namespace/SA/RBAC без
   перезаписи существующих объектов, собирает pinned gvisor worker image и
   дописывает разрешённый digest в приватный `.env`;
5. `bin/brood deploy go`: отдельный Go Deployment/PVC и приватный HTTPS
   Service, без public cutover и без переноса production-пользователей.

`passed` этого сценария означает успешные проверки, сборку и rollout приватного
endpoint. Это не проверка публичного ingress или доступа к реальному актору
через новый Go Deployment; такие e2e-доказательства фиксируются отдельно.

Вложенный тестовый Substrate использует gvisor: `/dev/kvm` внутрь актора не
передан, второй уровень аппаратной виртуализации не нужен и не заявляется.
Имена kind-кластера и registry совпадают с обычной установкой, но относятся к
другому Docker daemon внутри гостя. Управление рабочим кластером исключено
отсутствием его socket, credentials и kubeconfig.

## Актор с Claude Code

Тот же образ содержит native CLI Claude Code `2.1.310`, ttyd и tmux.
В Debian 13 пакета ttyd нет: версия `1.7.7` собирается из исходного архива
upstream, закреплённого SHA-256, со штатными библиотеками Debian и libuv backend.
Linux x64 binary закреплён SHA-256 из официального `manifest.json`; при
выборе pin подпись manifest проверена ключом с fingerprint
`31DDDE24DDFAB679F42D7BD2BAA929FF1A7ECACE`. Сборка проверяет checksum binary.
Установщик с незакреплённым `curl | bash` не используется.

```sh
brood workbench template --profile claude-code --image IMAGE_AT_DIGEST \
  --atespace brood-development
brood workbench run --atespace brood-development \
  --template brood-claude-code --name claude-code
```

Профиль не запускает CI автоматически. Он готовит workspace и Docker,
печатает версию CLI и обслуживает терминал ttyd на порту 80. При подключении
открывается Claude Code в tmux-сессии `claude`, из каталога проекта.
Отключение браузера не завершает tmux-сессию; это не гарантия cold restart
или suspend/resume VM. Сервер результатов этого профиля слушает 8081.
`ready` означает готовность workspace/Docker, а не авторизацию CLI.

Терминал даёт управление доверенной development-VM. Он доступен только
через аутентифицированный Substrate Router; не публикуйте его отдельным
открытым портом. В ttyd включены ввод и проверка WebSocket Origin. Прокси
должен сохранять исходные Host/Origin и подставлять фиксированный
`ate-target-actor`, а не принимать цель от браузера.

Launcher выбирает egress из маркера профиля в самом шаблоне. Только coding-
профиль дополнительно разрешает точные хосты Anthropic API, входа и документации.
Обновления CLI, необязательная телеметрия, автоматические claude.ai MCP
connectors и Artifact отключены; wildcard-хостов нет. Build-профиль сохраняет
прежний список хостов.

API-ключи, OAuth-сессия и SSH-ключи оператора не копируются. Авторизация
выполняется пользователем внутри CLI со своей учётной записью; состояние
остаётся в HOME данного актора. Задача модели при создании актора не
отправляется. Без отдельной авторизации CLI не сможет выполнять модельные
запросы. См. официальные инструкции:
https://code.claude.com/docs/en/setup и
https://code.claude.com/docs/en/network-config.

Сборка требует Git-рабочее дерево или дерево из `--export`; релиз, полученный
только через `git archive`, не содержит Git metadata для снимка исходников.

## Результаты и доступ

Основной HTTP-порт актора -- 80. Он обслуживает только `/workspace/results`:

- `/status.json` -- состояние `starting`, `ready`, `testing`, `deploying`, `passed` или `failed`;
- `/workbench.log` -- вывод задания.

Из кластера эти пути доступны через HTTPS-сервис
`atenet-router.ate-system.svc:443` с заголовком
`ate-target-actor: brood-development/build-001`. Нужны доверенный клиентский
сертификат Substrate Pod Identity и CA Service DNS, не kubeconfig или TLS
самого Brood. Чтение `/status.json` через mTLS проверено на живом акторе.
Сервис router не предоставляет HTTP-порт 80; старые примеры port-forward
`8000:80` здесь не работают. Сам сервер результатов не требует пароля:
доступ к нему ограничивает маршрутизатор Substrate.

Статус Actor `RUNNING` означает, что окружение запущено, а не что тесты уже
завершились. Итог задания -- `status.json`. После успеха или ошибки актор
остаётся доступен для разбора; автоматического удаления рабочего тома нет.

Go endpoint слушает HTTPS Service:8443 во вложенном кластере; публичный
NodePort не создаётся. Проверка через loopback port-forward использует
сгенерированный guest-сертификат. Подготовка сама не создаёт пользователей:
для login-проверки нужен отдельный `brood bootstrap-admin`. Файлы настроек
и TLS не отдаются сервером результатов.

Suspend/resume всей среды с Docker и kind отдельно не подтверждён. Для нового
прогона используйте новый актор; предпочтение MEMORY в шаблоне не является
гарантией сохранения процессов и не заменяет Git или резервную копию.
