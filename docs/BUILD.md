# Образ агента и brood.yaml

Агенту для работы над репозиторием нужны инструменты: компилятор, пакеты,
утилиты. Их описывает файл `brood.yaml` в корне репозитория — обычный плейбук
Ansible. Команда `bro build` объявляет по нему проект на сервере и просит
сервер собрать образ: шаблон контейнера Proxmox, клонами которого создаются
агенты проекта.

## Почему объявление живёт в плейбуке

`brood.yaml` решает две задачи одним файлом. Задачи плейбука готовят образ,
а зарезервированная переменная `vars.brood` одной из его пьес объявляет
проект: имя, репозиторий, лимиты, секреты. Так окружение агента и проект
описаны рядом, хранятся в Git вместе с кодом и меняются одним коммитом.

`bro` читает из файла только `vars.brood` как обычный YAML и не исполняет
Ansible. Остальной плейбук он не проверяет: его исполняет сервер при сборке.

## Пример

`brood.yaml` самого brood ставит инструменты разработчика и Go закреплённой
версии:

```yaml
- name: brood worker image
  hosts: localhost
  connection: local
  become: false
  gather_facts: false

  vars:
    brood:
      project: brood
      description: Agent pool on Proxmox
    pins: "{{ lookup('ansible.builtin.file', playbook_dir + '/brood/dev/pins.json') | from_json }}"
    go_archive: "go{{ pins.GO_VERSION }}.linux-amd64.tar.gz"

  tasks:
    - name: Developer packages
      ansible.builtin.apt:
        name: [build-essential, curl, git, jq, make, python3, python3-venv, ripgrep, unzip]
        state: present
        install_recommends: false
        update_cache: true

    # ... загрузка и распаковка Go из pins.json ...

    - name: Go on the PATH of every login shell
      ansible.builtin.copy:
        dest: /etc/profile.d/brood-go.sh
        mode: "0644"
        content: |
          export PATH=/usr/local/go/bin:$PATH
```

Здесь шаблоны `{{ }}` есть в соседних переменных `pins` и `go_archive`, но не
внутри `brood`: это разрешено. Блока `secrets` нет, поэтому секреты проекта
ведутся вручную ([SECRETS.md](SECRETS.md)).

## Схема vars.brood

Ровно одна пьеса плейбука должна определять `vars.brood`. Неизвестные ключи —
отказ.

| Ключ | Тип | По умолчанию | Действие |
| --- | --- | --- | --- |
| `project` | строка | обязателен | Имя проекта: строчные латинские буквы, цифры и дефисы внутри, до 63 символов |
| `description` | строка до 4096 символов | не меняется | Описание проекта |
| `repository` | строка | Git origin рабочего каталога | Репозиторий проекта. Адрес SSH вида `git@host:path` переводится в HTTPS. Пустая строка `""` отключает клонирование |
| `limits` | отображение или `null` | не меняются | Лимиты проекта |
| `limits.swarms` | целое или `null` | без предела | Число роёв |
| `limits.agents` | целое или `null` | без предела | Число агентов |
| `limits.cpu_millicores` | целое или `null` | без предела | Процессор, в тысячных ядра |
| `limits.memory_bytes` | целое или `null` | без предела | Память, в байтах |
| `secrets` | отображение | секреты не трогаются | Полный набор секретов проекта |
| `secrets.env` | строка | переменных нет | Путь к локальному dotenv-файлу |
| `secrets.files` | список | файлов нет | Файлы-секреты, не больше 128 |
| `secrets.files[].path` | строка | обязателен | Путь назначения у агента |
| `secrets.files[].source` | строка | обязателен | Локальный файл с содержимым |

Правила, которые легко упустить:

- Отсутствующий ключ `description`, `limits` или `secrets`
  оставляет на сервере прежнее значение. Репозиторий записывается всегда.
- Блок `limits`, если он есть, задаёт все четыре лимита разом: пропущенный
  в нём ключ и `null` означают «без предела», `0` запрещает резервирование.
  Как лимиты считаются — в [MODEL.md](MODEL.md).
- Блок `secrets`, если он есть, объявляет секреты целиком: `bro build` удалит
  с сервера всё, чего в блоке нет. Пустой блок `secrets: {}` удаляет все
  секреты. `secrets: null` — отказ.
- Пути в `secrets` — относительные, внутри репозитория, без `..`.
- Если Git origin у каталога нет и `repository` не задан, `bro build`
  отказывает: задайте `repository` явно.

### Только литералы

Всё под `brood` должно быть буквальным: строки, целые числа, `null`,
отображения и списки из них. `bro` не вычисляет шаблоны, поэтому под `brood`
запрещены `{{ }}` и `{% %}`, теги YAML, якоря и ссылки, ключи слияния `<<`
и повторяющиеся ключи. Отказ называет поле и строку файла:

```text
brood.yaml: brood.project (line 12): templates are forbidden; project metadata must be literal: bro does not evaluate templates
```

## Что делает bro build

```text
usage: bro build [--pool NAME] [--no-wait] [--no-secrets]
       bro build --plan
```

Команда запускается из корня репозитория и выполняет шаги по порядку:

1. Читает и проверяет `./brood.yaml`.
2. Готовит снимок рабочей копии и, если нужно, читает значения секретов до
   первого запроса к серверу.
3. Синхронизирует проект: описание, репозиторий для работающих агентов и
   лимиты. Отдельно синхронизирует объявленные секреты, если не задан
   `--no-secrets` ([SECRETS.md](SECRETS.md)).
4. Передаёт снимок серверу и печатает журнал сборки по мере поступления.

Снимок включает текущие версии отслеживаемых файлов и новые файлы,
которые Git не игнорирует. Удалённые файлы и пути с симлинками пропускаются.
Из снимка исключаются `.git`, `.env` и `.env.*` на любой глубине, корневой
`secrets/` и источники секретов из `brood.yaml`, даже с `--no-secrets`.
Предел — 64 МиБ вместе с заголовками архива и 20 000 файлов. Подмодули не
поддерживаются. Коммитить, пушить или настраивать Git-токен не требуется.

Создавать проект, менять его объявление и синхронизировать секреты может
только администратор. Участник проекта может собрать образ, если объявление
в `brood.yaml` не отличается от записанного на сервере.

Если ни в одной пьесе нет `tasks`, `roles`, `pre_tasks`, `post_tasks`,
`handlers` или `import_playbook`, снимок не создаётся и образ не собирается:
синхронизируются только проект и секреты.

| Опция | Действие |
| --- | --- |
| `--pool NAME` | Собрать в этом пуле. Без опции сервер берёт единственный включённый пул; если их несколько, пул нужно назвать |
| `--no-wait` | Напечатать идентификатор образа и вернуться, не дожидаясь сборки |
| `--no-secrets` | Не читать и не синхронизировать объявленные секреты |
| `--plan` | Напечатать разобранное объявление в JSON; от секретов — только имена. Сервер не нужен |

Ctrl-C прекращает ожидание, но не отменяет сборку: она продолжается на
сервере. Статус выхода 0 — только для готового образа.

## Что делает сервер

Сборку запускает `POST /api/projects/{id}/images`, тело — снимок USTAR
(`Content-Type: application/x-tar`), необязательный параметр запроса `pool`.
Сервер проверяет архив и сохраняет его контрольную сумму SHA-256 в записи
образа. Для одного проекта в одном пуле идёт одна сборка. Сервер:

1. Создаёт и запускает свежий контейнер из базового шаблона пула.
2. Подключается по SSH, устанавливает бинарник `brood-guest` и передаёт
   снимок в `/opt/brood-build/src`. К Git-серверу за исходниками не обращается.
3. Ставит Ansible и создаёт пользователя `actor` (UID/GID 1000), домашний
   каталог `/workspace/home` и рабочий каталог `/workspace/project`.
4. Запускает `ansible-playbook -i localhost, -c local brood.yaml` от root
   из `/opt/brood-build/src`.
5. Удаляет `/opt/brood-build`, чистит кэш apt и сбрасывает `machine-id`,
   затем выключает контейнер и превращает его в шаблон Proxmox.

На сборку отводится 60 минут. Сервер хранит последние 64 КиБ журнала сборки.

## Что есть в образе и чего нет

Плейбук исполняется от root в Debian и видит уже созданного пользователя
`actor` и каталоги `/workspace`, поэтому может класть файлы в домашний каталог
агента `/workspace/home`.

В плейбук не нужно включать то, что сервер ставит сам:

- агент `brood-guest` и его служба `brood-agent.service` — сервер ставит
  и обновляет их при каждом запуске контейнера;
- `ttyd`, сервер терминала, — ставится при запуске контейнера;
- `bro` и Claude Code — агент скачивает их с сервера при старте.

В образ не попадают:

- секреты проекта: они доставляются агенту при запуске сессии, а не в сборку;
- исходный код проекта: каталог сборки удаляется, рабочую копию агент
  клонирует сам при первом запуске.

## Состояния и срок жизни образа

| Состояние | Что значит |
| --- | --- |
| `building` | Сборка идёт |
| `ready` | Шаблон готов; новые агенты могут быть его клонами |
| `failed` | Сборка не удалась; причина записана в образе, сборочный контейнер удалён |

Сборка, которую прервала остановка сервера, при следующем старте помечается
`failed`.

Новый агент проекта в пуле — связанный клон самого нового образа в состоянии
`ready` для этого проекта и пула. Если такого образа нет, агент создаётся из
базового шаблона пула. Уже созданные агенты на новый образ не переходят:
`bro reset` пересоздаёт контейнер из того образа, из которого агент был создан.
Чтобы получить агента на новом образе, удалите старого и создайте нового.

Образы сервер сам не удаляет. Старые образы и записи неудачных сборок убирают
вручную:

```sh
bro image list
bro image rm IMAGE
```

```text
usage: bro image list [--project NAME] [--json]
       bro image rm IMAGE [--project NAME]
```

`bro image list` печатает столбцы `ID`, `STATE`, `REF`, `POOL`, `PLAYBOOK`
и `AGE`, новые образы сверху. Проект берётся из `--project`, иначе из
`brood.project` в `./brood.yaml`. Удалить нельзя образ, который ещё собирается,
и образ, у которого остались агенты-клоны.

## Ограничения

- Сборка всегда чистая: каждый раз новый контейнер из базового шаблона, без
  кэша слоёв и без результатов прошлой сборки. Время сборки — это время
  полного прогона плейбука.
- Сборочный контейнер не учитывается ни в бюджете пула, ни в лимитах проекта:
  на время сборки пул занят сверх своего бюджета на долю одного агента.
- SSH-ключи хоста создаются в сборочном контейнере и попадают в шаблон,
  поэтому у всех клонов одного образа они общие.
- Диск клона имеет размер диска сборочного контейнера, то есть долю агента
  в пуле на момент сборки; процессор и память клону выставляются заново.
- Образ принадлежит пулу, в котором собран. Для агентов в другом пуле его
  нужно собрать там отдельно.
- Плейбук может сам скопировать файлы из снимка в другие каталоги.
  Удаление временного каталога не удаляет такие копии.
