# Запуск сервера

Сервер brood — один исполняемый файл `brood` с базой SQLite, встроенной
веб-панелью и SDK шлюза моделей CLIProxyAPI. Первая часть документа описывает то, что верно для любой
установки: настройки, данные, команды. Вторая — эталонную установку
проекта, какой она сейчас устроена.

Проект в разработке и релизов не имеет: настройки и команды меняются без
обратной совместимости.

## Часть 1. Любая установка

### Сборка

Нужен Go версии из `go/go.mod`. Собранная панель лежит в репозитории
(`go/brood/server/static/index.html`) и встраивается в сервер, поэтому Bun
для сборки сервера не нужен.

```sh
make -C go build
(cd go && CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w" -o bin/brood-guest ./cmd/brood-guest)
```

Первая команда кладёт сервер `brood` и клиент `bro` в `go/bin/`, вторая
собирает туда же программу агента `brood-guest`. Устройство модуля описано
в [GO.md](GO.md), пересборка панели — в [WEB.md](WEB.md).

### Настройки

Сервер читает настройки только из переменных окружения. Значение в
одинарных или двойных кавычках принимается без кавычек. Ни одна настройка
не обязательна для запуска; без части из них недоступны отдельные
возможности, это указано в таблице.

Основные:

| Настройка | Значение | Пример |
| --- | --- | --- |
| `BROOD_ADDR` | адрес слушателя; по умолчанию `127.0.0.1:8080` | `:8443` |
| `BROOD_DB_PATH` | файл базы SQLite; по умолчанию `./brood.db` | `/var/lib/brood/brood.db` |
| `BROOD_TLS_CERT`, `BROOD_TLS_KEY` | файлы сертификата и ключа; задаются вместе, без них сервер отвечает по HTTP | `/etc/brood/tls.crt` |
| `BROOD_SESSION_SECRET` | секрет сессий; при HTTP не короче 32 байт. Пустой заменяется случайным на время жизни процесса | случайная строка |
| `BROOD_SECURE_COOKIES` | `true` ставит cookie сессии атрибут `Secure` и без TLS на самом сервере: нужно, когда TLS завершает прокси перед ним | `true` |

Агенты и Proxmox (подробности в [PROXMOX.md](PROXMOX.md)):

| Настройка | Значение | Пример |
| --- | --- | --- |
| `BROOD_PUBLIC_ORIGIN` | HTTPS-адрес сервера, каким его видят контейнеры агентов. Без него и без секрета relay пулы не активируются | `https://brood.example.com` |
| `BROOD_PROXMOX_RELAY_SECRET` | секрет соединений агентов, не короче 32 байт | случайная строка |
| `BROOD_ARTIFACTS_DIR` | абсолютный путь каталога с программами агента. Без него агент не устанавливается | `/var/lib/brood/artifacts` |
| `BROOD_PROXMOX_POOLS`, `BROOD_PROXMOX_TOKENS` | подключения Proxmox, заданные в окружении вместо формы панели; задаются вместе, см. ниже | JSON |
| `BROOD_ACTOR_GIT_DOMAIN` | домен адреса, под которым агенты подписывают коммиты (`<агент>@<домен>`). Без него сервер имя автора агентам не задаёт | `agents.example.com` |
| `BROOD_ACTOR_MODEL`, `BROOD_ACTOR_SMALL_MODEL` | модель Claude Code агентов: основная и для быстрых задач. Без них модель выбирает Claude Code | имя модели шлюза |

Шлюз моделей — [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI).
Его можно встроить в процесс `brood` или подключить по существующим
настройкам `CLIPROXY_*`.

| Настройка | Значение | Пример |
| --- | --- | --- |
| `BROOD_CLIPROXY_CONFIG` | абсолютный путь к постоянному YAML, включающий встроенный CLIProxyAPI | `/var/lib/brood/gateway/config.yaml` |
| `CLIPROXY_URL` | адрес шлюза, `http` или `https` без пути | `http://127.0.0.1:8317` |
| `CLIPROXY_API_KEY` | ключ, с которым сервер пересылает шлюзу запросы агентов. Без адреса и ключа агенты не получают доступа к модели | ключ шлюза |
| `CLIPROXY_MANAGEMENT_KEY` | ключ управления шлюзом; нужен страницам управления панели | ключ шлюза |
| `CLIPROXY_CA_PEM_B64` | доверенные сертификаты шлюза, PEM в base64, если он отвечает по HTTPS с частным CA | base64 |
| `BROOD_ACTOR_LLM_URL`, `BROOD_ACTOR_LLM_API_KEY`, `BROOD_ACTOR_LLM_CA_PEM_B64` | отдельный HTTPS-шлюз только для запросов агентов; адрес и ключ задаются вместе. Страницы панели остаются на `CLIPROXY_URL` | `https://llm.example.com` |

Telegram:

| Настройка | Значение | Пример |
| --- | --- | --- |
| `BROOD_TELEGRAM_BOT_TOKEN` | токен бота установки. Без него общего бота нет ([TELEGRAM.md](TELEGRAM.md)) | токен BotFather |
| `BROOD_TELEGRAM_API` | адрес Bot API: HTTPS или HTTP на loopback; по умолчанию `https://api.telegram.org` | `http://127.0.0.1:8081` |

Формы JSON-настроек:

```sh
BROOD_PROXMOX_TOKENS='{"main": "<секрет токена>"}'
BROOD_PROXMOX_POOLS='{"pve1": {"endpoint": "https://pve.example.com:8006", "tokenID": "brood@pve!brood", "credentialRef": "main", "caPEM": "-----BEGIN CERTIFICATE-----\n...", "node": "pve", "resourcePool": "brood", "storage": "local-lvm", "network": "vmbr0", "template": "local:vztmpl/debian-12-standard_12.7-1_amd64.tar.zst", "templateDigest": "sha256:<64 знака>", "capacity": {"actors": 4, "cpuMillicores": "8000", "memoryBytes": "17179869184", "diskGiB": 80}}}'
```

Поля те же, что в форме подключения панели; `credentialRef` называет ключ в
`BROOD_PROXMOX_TOKENS`. Подключение из окружения в панели не удаляется, а
имя подключения из панели не может совпасть с именем из окружения.

Неверное значение останавливает запуск сообщением вида
`BROOD_ADDR: <что не так>` с именем настройки, без самого значения.

### TLS

С `BROOD_TLS_CERT` и `BROOD_TLS_KEY` сервер слушает HTTPS сам и передаёт
свой сертификат агентам как доверенный корень. Без них он отвечает по HTTP
и должен стоять за прокси, который завершает TLS; тогда задайте
`BROOD_SECURE_COOKIES=true`, а сертификату прокси контейнеры агентов должны
доверять сами, через корневые сертификаты Debian.

Агентам сервер нужен именно по HTTPS: `BROOD_PUBLIC_ORIGIN` с другой схемой
не принимается.

### Каталог данных

Всё состояние сервера лежит рядом с файлом базы:

| Файл | Что это |
| --- | --- |
| `brood.db` и файлы `-wal`, `-shm` | база SQLite: пользователи, проекты, рои, агенты, пулы, секреты, подключения Proxmox с секретами токенов |
| `ssh_identity` | SSH-ключ установки (ed25519, режим 0600), которым сервер входит в контейнеры агентов. Создаётся при первом запуске |

Каталог должен быть доступен только пользователю сервера: в базе лежат
секреты. Резервная копия — оба файла вместе; ключ без базы тоже нужно
сохранять, иначе собранные образы проектов станут недоступны
([PROXMOX.md](PROXMOX.md)).

### Программы агента

Агент в контейнере скачивает свои программы с сервера. Сервер отдаёт их из
каталога `BROOD_ARTIFACTS_DIR`, в котором лежат ровно четыре файла:

| Файл | Что это |
| --- | --- |
| `brood-guest` | программа агента, Linux amd64 |
| `bro` | клиент, которым агент выполняет команды |
| `claude` | Claude Code; версия и сумма закреплены в `brood/dev/pins.json` |
| `manifest.json` | размеры и суммы SHA-256 трёх файлов |

```json
{"artifacts": [{"name": "bro", "size": 12345678, "sha256": "<64 знака>"},
               {"name": "brood-guest", "size": 23456789, "sha256": "<64 знака>"},
               {"name": "claude", "size": 234567890, "sha256": "<64 знака>"}]}
```

Манифест можно собрать в самом каталоге:

```sh
for f in bro brood-guest claude; do
  printf '{"name":"%s","size":%s,"sha256":"%s"}\n' "$f" "$(stat -c %s "$f")" "$(sha256sum "$f" | cut -d' ' -f1)"
done | paste -sd, | sed 's/^/{"artifacts":[/; s/$/]}/' > manifest.json
```

Сервер перечитывает манифест на каждый запрос, перезапуск после обновления
не нужен. Он сверяет имена и размеры файлов с манифестом, а суммы не
пересчитывает: их проверяет агент после скачивания. Каждый файл не больше
512 МиБ. Чтобы обновление не было видно наполовину, готовьте новый каталог
рядом и подменяйте его переименованием; команда `brood artifacts` делает
это сама.

### Команды `brood`

| Команда | Что делает |
| --- | --- |
| `brood serve` | запускает сервер; останавливается по SIGTERM или SIGINT, дождавшись идущих запросов |
| `brood bootstrap-admin` | создаёт администратора: спрашивает имя и пароль (пароль без эха). Если пользователь с таким именем есть, ничего не меняет |
| `brood database inspect --path FILE` | печатает сведения о файле базы, не открывая его как базу сервера |
| `brood database snapshot --path FILE --output NEW` | делает согласованную копию работающей базы в новый файл |
| `brood database verify --path FILE --sha256 SUM` | проверяет, что копия с такой суммой имеет схему этой версии сервера |
| `brood database prune --current FILE --keep N` | удаляет старые копии рядом с `FILE`, оставляя `N` самых новых вместе с ней |
| `brood fixture export [--swarm PROJECT/SWARM]` | печатает фикстуру установки; с `--swarm` сохраняет рой, его ключи, проект, адрес репозитория и готовые образы |
| `brood fixture apply` | читает такой JSON со стандартного ввода и вставляет в базу |
| `brood artifacts --dir DIR` | принимает программы агента потоком со стандартного ввода и заменяет ими каталог `DIR`; печатает манифест |
| `brood version` | печатает версию |

Команды `database` печатают результат одним JSON-объектом и принимают
`--timeout` (по умолчанию 10 секунд, не больше минуты). `bootstrap-admin` и
`fixture` работают с базой из `BROOD_DB_PATH`. Код выхода 0 — успех, 1 —
ошибка.

### Первый запуск

```sh
export BROOD_DB_PATH=/var/lib/brood/brood.db
export BROOD_ADDR=:8443
export BROOD_TLS_CERT=/etc/brood/tls.crt BROOD_TLS_KEY=/etc/brood/tls.key
export BROOD_PUBLIC_ORIGIN=https://brood.example.com
export BROOD_PROXMOX_RELAY_SECRET="$(openssl rand -hex 32)"
export BROOD_ARTIFACTS_DIR=/var/lib/brood/artifacts

brood bootstrap-admin
brood serve
```

Секреты из примера нужно сохранить и передавать при каждом запуске: со
сменой `BROOD_PROXMOX_RELAY_SECRET` работающие агенты теряют соединение,
пока сервер не установит их заново. Готовность проверяет
`GET /healthz`: ответ `ok`, когда сервер достаёт до своей базы.

Дальше администратор входит в панель и подключает Proxmox
([PROXMOX.md](PROXMOX.md)); клиент `bro` описан в [CLI.md](CLI.md).

### Версии базы

Миграций нет. Сервер создаёт схему в пустом файле и записывает её номер.
Файл с другим номером или с отличающимися таблицами сервер открывать
отказывается:

```
incompatible database schema: found version 103, want 104; there are no migrations, recreate the database
```

Обновление сервера, которое меняет схему, означает новую базу: остановите
сервер, уберите файл базы вместе с `-wal` и `-shm`, запустите сервер и
создайте администратора заново. Пользователи, проекты, рои и записи об
агентах при этом теряются; контейнеры прежних агентов остаются в Proxmox,
и удалять их приходится вручную. Файл `ssh_identity` оставьте на месте.
Перенести администраторов, Telegram и пулы Proxmox помогает пара
`brood fixture export` (до обновления) и `brood fixture apply` (после).

## Часть 2. Эталонная установка

На машине деплоя под Debian amd64 сервер работает как системная служба
`brood.service` от пользователя `brood`. Go и панель собираются на builder;
на машине деплоя не нужны Go, Docker, Kubernetes и отдельный TLS-прокси.

Служба запускает `/var/lib/brood/brood serve` напрямую и читает настройки
из `/var/lib/brood/.env`. В `/var/lib/brood` находятся:

| Путь | Назначение |
| --- | --- |
| `brood`, `.env`, `tls.crt`, `tls.key` | установленный сервер, настройки сервера и файлы TLS |
| `artifacts/` | программы агента и манифест |
| `fixture.json` | фикстура установки; только в режиме `fixture` |
| `brood.db`, `ssh_identity` | база SQLite и SSH-ключ сервера |
| `gateway/` | постоянные настройки и авторизации шлюза, если он включён |

Каталог принадлежит `brood:brood` и закрыт для других пользователей.
Установленные файлы заменяются на месте; каталоги версий не создаются.

### Подготовка машины

Оператор от root запускает `deploy/provision.sh KEY FROM`. `KEY` — файл с
открытым ключом выкладки, `FROM` — адрес или CIDR builder. Скрипт ставит
unit в `/etc/systemd/system` и принадлежащую root принудительную команду
в `/usr/local/bin`; первый запуск службы происходит при первой выкладке.
Ключ записан в `authorized_keys` с
`restrict,from="<адрес builder>",command="/usr/local/bin/brood-deploy"`.
Пользователь `brood` не может менять это правило; единственное разрешение
sudo — `systemctl restart brood.service`. Новая возможность для ключа —
правка принудительной команды, а не другой ключ или shell.

Служба завершает TLS сама. До выкладки настройте DNS и вход на
`BROOD_HTTPS_PORT`; при внешней переадресации обновите её на этот порт.
Сетевые ограничения задаёт оператор на хосте. Для работы агентов
серверу нужно достигать API Proxmox и SSH контейнеров; в зависимости от
настроек ему также нужны доступ к Git, Telegram и поставщикам моделей.

При переносе с прежней установки сначала остановите старый сервер. Из
его тома `/data` перенесите `ssh_identity` и, если база нужна, `brood.db`
с её `-wal` и `-shm` либо согласованный снимок SQLite. В новом каталоге
`/var/lib/brood` файлы должны принадлежать `brood:brood` и быть закрыты для
других пользователей. Даже в режиме `fixture` перенесите `ssh_identity`:
иначе сервер создаст новый ключ, и старые образы проектов потребуют
пересборки. Сохраните прежние `BROOD_PUBLIC_ORIGIN` и `BROOD_PROXMOX_RELAY_SECRET`,
чтобы агенты смогли переподключиться. Если переносите шлюз, скопируйте его
YAML и файлы авторизации по инструкции в [GATEWAY.md](GATEWAY.md).
Для переезда с сохранением базы используйте `BROOD_DEPLOY_MODE=existing`
и совместимую версию схемы. Старую инфраструктуру убирайте после проверки
панели, терминала агента и запроса к модели. Останов, перенос данных и
демонтаж делает оператор; ключ CI к этому доступа не получает.

Если на хосте уже стояла systemd-версия с каталогами релизов, повторно
запустите `provision.sh` перед первой плоской выкладкой. Когда новая служба
пройдёт проверку готовности, оператор удаляет прежний каталог
`/var/lib/brood/releases` вместе с копиями настроек и ключей. Переносить
базу, SSH-ключ и каталог шлюза в этом случае не нужно.

### Выкладка и готовность

1. Задание `deploy` запускается на push в основную ветку. Ручные проверки
   не задерживают выкладку. На builder `.ci/deploy.sh` из дерева коммита
   собирает панель и программы `brood`, `bro`, `brood-guest`; отдельно
   скачивает закреплённый Claude Code и сверяет SHA-256.
2. Builder передаёт полный sha как SSH-команду, а на stdin — tar только
   с готовыми программами, `.env`, TLS-сертификатом и ключом и, если
   задана, фикстурой. Секреты не входят в контекст сборки и не публикуются
   как артефакты GitLab.
3. Принудительная команда берёт блокировку и принимает только ожидаемые
   файлы в закрытый временный каталог. Она проверяет TLS и (в режиме
   `fixture`) применение фикстуры в пробной базе. Из переданного `.env`
   она оставляет только настройки `BROOD_*` и
   `CLIPROXY_*`; пути установки задаёт сама. `brood artifacts` готовит
   `bro`, `brood-guest`, `claude` и их манифест.
4. Команда ставит готовые файлы переименованием, подменяет каталог
   артефактов целиком и перезапускает `brood.service`. Проверка ждёт `ok`
   от `/healthz` по HTTPS, обращаясь к локальному слушателю под публичным
   DNS-именем и проверяя сертификат. Она не проверяет внешнюю маршрутизацию.

Ошибка подготовки не меняет установленный сервер. Ошибка во время замены
файлов может оставить установку частично обновлённой; повторите выкладку
после устранения причины. Если служба не стала готова, выкладка завершается
с ошибкой без отката: новая версия уже могла пересоздать базу. Оператор
смотрит `journalctl -u brood.service` и исправляет настройки или
восстанавливает базу вручную. Выкладка файлов не заменяет SQLite, SSH-ключ
или каталог шлюза.

### Режимы выкладки

| `BROOD_DEPLOY_MODE` | Что происходит с базой |
| --- | --- |
| `existing` (по умолчанию) | Открывает текущую базу либо создаёт пустую. Несовместимую схему не меняет. На пустой установке оператор создаёт администратора командой `brood bootstrap-admin`. |
| `fixture` | Пересоздаёт базу, если sha релиза отличается от метки последнего сброса, и загружает фикстуру: администраторы, их привязки Telegram, подключения и пулы Proxmox. Перезапуск службы и повтор выкладки того же sha базу не трогают. |

Режим `fixture` используется на стенде разработки как временная мера, пока
схема меняется без миграций. Новый релиз восстанавливает только записи из
фикстуры. Агенты не сохраняются, их контейнеры Proxmox служба при сбросе не
удаляет. Свежая база получает стартовые роли «Мастер» и «Агент». Предыдущая
база остаётся в аварийной копии `brood.db.before-<sha>` до следующего сброса;
это не резервное копирование.

В production-фикстуре сохранён тестовый рой `brood/brood`. Чтобы обновить
фикстуру без смены Git-ключа, экспортируйте **тот же** рой. Публичный и
закрытый ключи сохраняются вместе; новая пара при восстановлении не
генерируется. Образ остаётся шаблоном в Proxmox: в фикстуре только его запись,
поэтому пул и метка владения на шаблоне должны ей соответствовать.

Передайте JSON защищённой файловой переменной `BROOD_DEPLOY_FIXTURE`.
В нём хеши паролей, секреты Proxmox и закрытый ключ роя. Не выводите файл в
терминал или логи и не добавляйте в git:

```sh
umask 077
sudo -u brood env BROOD_DB_PATH=/var/lib/brood/brood.db \
  /var/lib/brood/brood fixture export --swarm brood/brood > fixture.json
```

Создание первого администратора в `existing` (пароль запрашивается
интерактивно):

```sh
sudo -u brood env BROOD_DB_PATH=/var/lib/brood/brood.db \
  /var/lib/brood/brood bootstrap-admin
```

### Настройки установки

В `.env` задаются `BROOD_PUBLIC_HOST` (DNS-имя для проверки HTTPS и ссылок на примеры),
`BROOD_HTTPS_PORT` (порт слушателя), режим и нужные настройки сервера
из части 1. Формат — `KEY=VALUE`, по одной настройке на строку; внешние
кавычки разрешены, shell-подстановок нет. Выкладка задаёт пути к базе,
TLS-файлам и артефактам сама, как и `BROOD_ADDR`. В `fixture` выкладка
сама передаёт `BROOD_DB_RESET` (sha релиза) и `BROOD_FIXTURE_FILE` (абсолютный путь к JSON).

При включении встроенного CLIProxyAPI укажите абсолютный путь к YAML
через `BROOD_CLIPROXY_CONFIG`. Сам файл и каталог авторизаций храните
в `/var/lib/brood/gateway` с правами пользователя `brood`. YAML и
авторизации не входят в архив CI и переживают выкладки. Ключи шлюза
передаются из `.env`; `CLIPROXY_URL` и `CLIPROXY_CA_PEM_B64` для
встроенного шлюза не задаются. Пример YAML см. в [GATEWAY.md](GATEWAY.md).

### Защищённые переменные CI

Переменные видны только конвейерам защищённых веток; в репозитории нет ни
адреса машины, ни ключей. Их заводит `brood dev ci set`.

| Переменная | Тип | Назначение |
| --- | --- | --- |
| `BROOD_DEPLOY_HOST` | значение | `пользователь@адрес` машины деплоя |
| `BROOD_DEPLOY_SSH_KEY` | файл | закрытый ключ выкладки |
| `BROOD_DEPLOY_KNOWN_HOSTS` | файл | ключ хоста машины деплоя |
| `BROOD_DEPLOY_ENV` | файл | `.env` установки |
| `BROOD_DEPLOY_TLS_CERT` | файл | TLS-сертификат установки |
| `BROOD_DEPLOY_TLS_KEY` | файл | ключ TLS-сертификата |
| `BROOD_DEPLOY_FIXTURE` | файл | фикстура режима `fixture`; необязательна в других режимах |
