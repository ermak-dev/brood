# Сообщения и инструменты агента

Этот документ описывает, как люди и агенты brood обмениваются сообщениями
и как агент пользуется brood изнутри своего контейнера. Объекты системы
(проект, рой, агент, пул) описаны в [MODEL.md](MODEL.md); здесь нужны три
из них:

 - **рой** — группа агентов одного проекта с одним владельцем;
 - **агент** — контейнер, в котором работает сессия Claude Code;
 - **оператор** — человек: владелец роя или администратор.

Одни и те же команды доступны агенту как инструменты MCP (Model Context
Protocol, протокол, по которому Claude Code вызывает внешние инструменты)
и человеку как команды клиента `bro`. Список команд один на всех и лежит
в `go/brood/command`.

## Шина сообщений

Шина сообщений — способ доставить текст в сессию агента или человеку.
Команда одна: `send`. Область шины — рой: агент видит и адресует только
агентов своего роя, сообщение в чужой рой отправить нельзя.

### Кто кому пишет

| Отправитель | Получатель | Как |
|---|---|---|
| оператор | агент роя | `bro send NAME MESSAGE...` или сообщение в Telegram ([TELEGRAM.md](TELEGRAM.md)) |
| агент | другой агент того же роя | инструмент `send` с `to` = имя агента |
| агент | владелец роя | инструмент `send` с `to="operator"` |

Оператором может быть владелец роя или администратор. Агент не может
написать самому себе, удалённому агенту или агенту другого роя.

Имя `operator` зарезервировано за владельцем роя: агента с таким именем
создать нельзя, сервер отвечает
`The name operator is reserved for the human owner of the swarm. Choose another name.`
Сообщение на имя `operator` приходит в личный чат Telegram, привязанный
владельцем роя. Если чат не привязан или бота нет, отправитель получает
отказ с причиной, например
`not delivered to the operator: the swarm owner has no linked Telegram chat`.

### Что обещает `send`

`send` возвращает результат доставки, а не ответ. Ответ получателя, если
он будет, придёт позже отдельным сообщением.

 - Доставка разовая. Очереди нет, повторов нет: если получатель сейчас
   недоступен, сообщение не сохраняется, а отправитель получает отказ.
 - Сообщение уходит агенту только пока его контейнер держит соединение
   с сервером. Иначе ответ — `not connected`
   (`not sent: the agent is not connected; check its state with agents`).
   В этом случае сообщение заведомо не отправлено, повторять безопасно.
 - Агент внутри контейнера подтверждает, что сессия Claude Code приняла
   сообщение. Без аргумента ожидания сервер ждёт это подтверждение до 15
   секунд. Результат `delivered` означает, что сессия сообщение приняла.
 - Если подтверждение не пришло, результат — «доставка не подтверждена»
   (`the agent did not confirm the delivery; the message may have arrived,
   check with tail before sending again`, исход `unconfirmed`). Сообщение
   могло дойти, а могло и нет. Перед повтором нужно посмотреть вывод
   агента командой `tail`, иначе он получит его дважды.
 - Если в контейнере сейчас нет работающей сессии (например, сразу после
   перезапуска), агент отвечает, что сообщение не отправлено:
   `no unique live Claude session for this project`. Повтор безопасен.

Аргумент `wait_seconds` (от 0 до 300, по умолчанию 0; у `bro send` это
`--wait SECONDS`) просит дождаться, пока получатель закончит текущую
работу и станет свободен. Результат тогда дополняется словами
`idle confirmed` или `idle not confirmed`. Ответа получателя `send` не
возвращает и в этом случае.

Текст сообщения вместе со служебной обёрткой ограничен 128 КиБ.

### Как сообщение выглядит в сессии агента

Сервер дописывает к тексту строку о том, от кого сообщение и как на него
ответить, и передаёт его в сессию Claude Code как сообщение из другой
сессии. Сообщение оператора:

```
<cross-session-message from="uds:..." from-name="operator:alice" from-mode="bypass">
Запусти тесты и напиши, что упало.

[brood] This message is from the human operator of your swarm. To answer, use send with to="operator".
</cross-session-message>
```

Сообщение агента `agent-1`:

```
<cross-session-message from="uds:..." from-name="agent-1" from-mode="bypass">
Ветка готова к проверке.

[brood] This message is from agent "agent-1" of your swarm. To answer, use send with to="agent-1". The agents command lists the agents of the swarm.
</cross-session-message>
```

`from-name` у оператора — `operator:` и имя учётной записи. Отвечать на
адрес из `from` не нужно: он одноразовый. Ответ идёт инструментом `send`.

## Сервер MCP в агенте

Служба агента запускает Claude Code так:

```
claude --dangerously-skip-permissions --mcp-config '{"mcpServers":{"brood":{"command":"/opt/brood/bin/bro","args":["--guest","mcp"]}}}'
```

Сервер MCP с именем `brood` — это клиент `bro` в режиме агента
(`bro --guest mcp`). Он говорит с Claude Code по stdio и передаёт каждый
вызов службе агента через локальный сокет `/run/brood/swarm.sock`, а та —
серверу brood по своему исходящему соединению. У `bro` в этом режиме нет
ни пароля, ни токена: сервер узнаёт агента по соединению его контейнера,
поэтому агент действует только от своего имени и только в своём рое.
Собственные серверы MCP и настройки агента при этом сохраняются: `brood`
добавляется к ним.

Те же команды доступны агенту из оболочки контейнера без MCP:
`bro --guest agents`, `bro --guest send agent-1 "..."`; список — `bro
--guest help`.

При подключении сервер MCP передаёт Claude Code инструкцию:

Она называет `agents` для знакомства с роем и `send` для ответа.
Набор доступных инструментов зависит от роли. Если ответ на операцию
не подтверждён, проверьте её исход до повтора.

### Инструменты

Таблица повторяет каталог `go/brood/command`. «Меняет» — меняет ли вызов
что-нибудь; у `rm` и `reset` в описании MCP стоит признак разрушающего
действия.

| Инструмент | Аргументы | Что делает | Меняет |
|---|---|---|---|
| `agents` | — | Список агентов роя: имя, роль, состояние; поле `self` — имя вызвавшего | нет |
| `send` | `to`, `message`, `wait_seconds` (0–300, по умолчанию 0) | Сообщение агенту роя или владельцу (`to="operator"`) | да |
| `tail` | `name`, `lines` (1–10000, по умолчанию 40), `grep` | Последний вывод агента, при `grep` — только строки с этим текстом | нет |
| `slash` | `name`, `command` | Слэш-команда в сессию агента, например `/clear` | да |
| `add` | `name`, `origin` | Новый агент в рое; `origin` — HTTPS-адрес Git-репозитория для его рабочего каталога | да |
| `rm` | `name`, `confirm` | Удаляет агента вместе с контейнером | да, необратимо |
| `start` | `name` | Запускает остановленного агента в его контейнере | да |
| `stop` | `name` | Останавливает агента; контейнер и рабочий каталог остаются | да |
| `restart` | `name` | Перезапускает сессию агента в том же контейнере | да |
| `reset` | `name`, `confirm` | Заменяет контейнер новым; рабочий каталог уничтожается | да, необратимо |
| `diagnose` | — | Показывает, под каким именем и ролью вызов дошёл до сервера | нет |

`rm` и `reset` без `confirm=true` ничего не делают и отвечают отказом
с просьбой повторить вызов с подтверждением. Имя агента — строчные
латинские буквы, цифры и дефисы, не длиннее 63 символов.

Если `origin` у `add` не задан, новый агент получает тот же репозиторий,
что и создающий его мастер, а если у мастера его нет — репозиторий
проекта.

### Разрешения роли

Гостевой MCP показывает инструменты, разрешённые роли агента. Сервер
применяет текущую роль при вызове, в том числе при прямом `bro --guest`
или вызове из клиента, который помнит старый список инструментов.

 - `agents` и `diagnose` включаются независимо.
 - `send` отдельно разрешается для агентов своего роя и для оператора.
 - `tail` может быть выключен, разрешён для своего терминала или для всего роя.
 - `add` создаёт агента с ролью проекта по умолчанию, в пуле вызывающего.
 - `slash`, `restart`, `start`, `stop`, `rm`, `reset` разрешаются независимо
   и только для агентов, созданных вызывающим через `add`.

Чтение чужих терминалов, создание и управление требуют действующей
делегации администратора. Роль по умолчанию не может получать эти права.
Две начальные роли и жизненный цикл промпта описаны в [MODEL.md](MODEL.md).

### Результат и исходы

Ответ на вызов инструмента содержит текст для модели (`content`), признак
ошибки `isError` и поле `structuredContent`:

```json
{"text": "...", "data": {...}, "outcome": "accepted"}
```

`data` и `outcome` есть не у каждого ответа. Что делать агенту:

| Что пришло | Что это значит | Что делать |
|---|---|---|
| `completed` (у `tail` — `complete`) | Команда выполнена, результат в тексте | Пользоваться результатом |
| `accepted` | Сервер принял `add`, `rm`, `start`, `stop` или `reset` и выполняет в фоне; агент ещё не готов | Проверить состояние через `agents` |
| текст `delivered` без `outcome` | `send`: сессия получателя приняла сообщение | Ждать ответного сообщения, если оно нужно |
| `unconfirmed`, `isError` | Неизвестно, выполнилась ли команда | Посмотреть `tail` или `agents`; повторять только убедившись, что действия не было |
| `unknown`, `isError` | Команда жизненного цикла могла быть принята, но Proxmox её не подтвердил | Проверить `agents` перед повтором |
| `isError` с причиной, без `outcome` | Отказ: нет прав, нет такого агента, агент не подключён, нет места в пуле | Читать причину: в ней сказано, изменилось ли что-нибудь и что делать |

Отказ всегда приходит строкой с причиной, написанной для вызывающего.
Слова `nothing changed` или `not sent` в ней означают, что повтор
безопасен.

Время одного вызова ограничено: 30 секунд, а для `send` с `wait_seconds`
— это число секунд и ещё 15.

## Те же команды для человека

Оператор вызывает те же команды клиентом `bro`: `bro agents`,
`bro send`, `bro tail`, `bro slash`, `bro start`, `bro stop`,
`bro restart`, `bro rm`, `bro reset`. Они работают в текущем рое,
требуют входа (`bro login`) и права управлять роем. У человека есть и то,
чего нет у агента: подключение к консоли (`bro attach`), работа с пулами
и проектами. `bro mcp` отдаёт каталог как сервер MCP от имени вошедшего
пользователя, чтобы подключить его к своей модели:
`claude mcp add brood -- bro mcp`. Все команды с аргументами и примерами
— в [CLI.md](CLI.md).
