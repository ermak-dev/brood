# MCP

## Один каталог команд

Каждый инструмент — команда пользовательского Go-клиента `bro`, а не отдельная
реализация внутри MCP. Пакет `go/brood/command` содержит декларации команд:
путь CLI, имя инструмента, описание, аргументы, значения по умолчанию,
ограничения и annotations. Например, `bro session history` соответствует
`session_history`, `bro project limit` — `project_limit`.

`ParseCLI` и `ParseTool` возвращают один `Invocation`. CLI вызывает executor
непосредственно; `bro mcp` строит `tools/list` из тех же деклараций и вызывает
тот же executor. MCP не запускает командлеты подпроцессами, не разбирает
терминальный вывод и не имеет собственной реализации операций.

```text
bro <command> ───────┐
                    ├─ command.Invocation ─ executor ─ авторизованный сервис
bro mcp ─ metadata ─┘
```

Схемы отвергают неизвестные и повторяющиеся поля, null, неправильные типы и
выход за границы. Каноническое представление тоже ограничено по размеру.
Metadata описывает возможности, но не выдаёт полномочий: сервер проверяет их
при каждом вызове и повторно перед выдачей приватных результатов.

## Проектные интеграции

Трекер, MR и CI обслуживаются инструментами самого проекта: например,
`bin/brood dev` для Brood или скриптами другого проекта. Credentials этих
инструментов задаются через `bro secret var/file` и намеренно доступны процессу
актора (`docs/SECRETS.md`). Git transport credentials остаются отдельным
server-only механизмом. Ограничения окружения и сети задаются в Substrate.

Каталог платформы не содержит `gitlab_*` инструментов и не принимает их вызовы
от старых клиентов. Отдельных платформенных GitLab grants и merge approvers нет:
merge — обычная операция проектного инструмента, с подтверждением человека либо
автоматическая согласно процессу и внешним правам. Обычный `ask_operator`
позволяет процессу запросить решение, но не подменяет права внешнего сервиса.

## Два режима исполнения

Оператор использует сохранённую HTTPS-сессию `bro login`; TLS, Origin и CSRF
обслуживает существующий `clientapi`. Рой выбирается глобальным `--swarm ID`
или `BROOD_SWARM`. Команды установки — проекты, пулы, диагностика — работают
также без выбранного роя. `bro diagnose` читает только локальные метаданные,
не создаёт каталог состояния и не обращается к серверу.

```sh
bro --swarm SWARM_ID agents
bro --swarm SWARM_ID tail worker --lines 40
bro models
bro node
bro project limit --name brood --actors 3
bro mcp
```

Гость выбирает режим явно: `bro --guest ...` или
`BROOD_EXECUTION_MODE=guest`. При ошибке broker нет отката на операторскую
сессию. В гостевом режиме login/logout/whoami, проекты и push не используют
операторский транспорт.

Профиль `claude-proxmox` добавляет следующий сервер к Claude Code:

```json
{"mcpServers":{"brood":{"command":"/opt/brood/bin/bro","args":["--guest","mcp"]}}}
```

Это дополнительный `--mcp-config`, не `--strict-mcp-config`. Пользовательские
MCP-настройки сохраняются. Namespace инструментов — `mcp__brood__*`, имя
сервера — `brood`. Python и NATS в госте не нужны. `brood-guest` остаётся
доверенным supervisor, а гостевой образ дополнительно содержит `bro`.

`project_*`, `node*` и `server_diagnose` не объявляются в гостевом MCP.
Просмотр своих сессий доступен worker; просмотр соседей и управляющие
действия требуют действующей master-делегации. Изменяющие команды
(`stop`, `delete`, `start`, `reset`, `update`, `restart`, `wipe`,
`recycle`, `slash` и запись в `session_terminal`) и `dispatch` master
выполняет только для своих workers, добавленных им через `add` (#152,
#267, #133). Аренда `dispatch`
без срока закрывает актору жизненный цикл, управление сессией и шаги роя,
поэтому тоже считается изменением. Себя, другого master, worker другого
master и worker, созданного оператором, он не трогает: отказ называет, чей
это актор. Себя master не останавливает: в mop master не папет, а `stop`
остаётся командой оператора; остановленного master поднимает только
оператор. Worker оператора получает шаги от диспетчера шагов и сообщения
master через `send`. `send` и чтение (`tail`, `session_history`,
`stat`, просмотр терминала) правило владения не ограничивает. `landing`
держит токен проекта, а не аренду актора: имя в нём допустимо только своё.
Оператору нужно право управлять роем; владение не ограничивает ни его, ни
панель, ни диспетчер шагов. Наличие инструмента в `tools/list` не является
разрешением его выполнить.

Name-only `add` наследует одобренный пул именно от managed master, а origin —
от master или, если у master он пуст, repository проекта. `--origin`
канонизируется сервером: допустим только repository проекта с серверным
Git-доступом (активный проектный Git credential или `BROOD_GIT_REMOTES`,
через серверный шлюз Git) или публичный host allowlist гостя; иное — отказ
без резервирования. Оператор
не может неявно выбрать пул через эту команду: создание с явным шаблоном
остаётся в существующем API/панели. Native-акторы не изображаются managed
акторами в этом канале. Шаблон профиля существующего актора не меняет ни
одна команда: смена шаблона — новый пул и пересоздание акторов
([PROXMOX.md](PROXMOX.md), «Новый шаблон гостя и переход пула»); `update`
меняет только гостевой набор.

`restart` не меняет CTID, образ, PVE ownership и relay generation. Новая
сессия запускается тем же launch, что и автостарт при загрузке гостя:
`claude --dangerously-skip-permissions` с сервером `brood`, без диалогов
onboarding, trust и bypass ([PROXMOX.md](PROXMOX.md), «Автономный запуск
Claude»). Модель новой сессии выполняет инструменты без запросов
разрешений; то же относится к `recycle`. Для `wipe` и `recycle` нужен
проверенный Git-клон строго в `/workspace/project`: неизвестный Git state,
неподходящая конфигурация, symlink/gitdir вне корня дают отказ до остановки
сессии и очистки. `restart` workspace не чистит и Git-клона не требует (#158):
актору без origin хватает каталога `/workspace/project` без symlink.
Проверенный клон, найденный до остановки, `restart` проверяет снова перед
запуском, и потеря клона или каталога за время остановки даёт unknown.
Несовпадающая PTY identity даёт отказ до остановки сессии; живые процессы в
workspace дают отказ `wipe`, а у `restart` и `recycle` после остановки дают
unknown. Эти команды не загружают произвольный origin, bootstrap или shell из
аргументов.
`restart` и `recycle` ждут освобождения workspace до 4 секунд и нового session
proof до 8 секунд в общем бюджете helper 15 секунд; timeout или отмена после
эффекта дают unknown без автоматического освобождения reservation.
`wipe` требует остановленной Claude-сессии, а не выключенного CT.
Выключенный CT возобновляет `start`.

`start` и `reset` — те же durable intents, что действия resume и reset
API/панели: принятие — записанное намерение, а не готовность гостя.
`start` сохраняет CTID, диск, owner nonce и поколение; для работающего
актора это no-op без нового намерения и эффекта провайдера. Актор, чья CT
наблюдается работающей, а фаза `error`, `provisioning` (истекло ожидание
готовности, упала задача stop) или `stopped` (CT запустили мимо brood),
получает новое намерение start, согласованное наблюдением, без записи в PVE:
bootstrap env пишется только остановленной CT, а второй Start не нужен
(#275). Проверяется только владение CT (`InspectOwned`: owner nonce в
описании, unprivileged, корневой том этого CTID, сеть, никаких посторонних
mount, устройств и hook, членство в пуле ресурсов, один digest у обоих видов
конфигурации) и то, что она работает. Env CT не переписывается: гость
работает с тем bootstrap env, с которым CT запустили, и это проверяется лишь
косвенно — relay принимает только HMAC guest token текущего UID и поколения,
а `running` публикует только проверка готовности ttyd, со свежим окном
ожидания. Start остановленной CT идёт тем
же путём, что start update (ниже): пока Start не запрошен, сбой до него
оставляет start ждать, а не делает исход неизвестным. `reset`
останавливает и удаляет прежний CT, отзывает guest token старого поколения
с первого шага и только после подтверждённого отсутствия создаёт CT с тем
же CTID, новым owner nonce и поколением +1. Workspace не переносится: при
заданном origin актора гость клонирует его заново (#146, #147), иначе
workspace пуст. Координация с участием актора и workspace reservation
дают отказ обоим до любого эффекта провайдера.

`update` (#133) — тот же durable intent: операция start того же поколения,
первая стадия которой stop. После подтверждённой остановки та же операция
запускает CT; bootstrap #184 ставит набор, который сервер раздаёт сейчас
(`releases/<id>`), `/workspace/home` и `/workspace/project` сохраняются.
CTID, диск, owner nonce, поколение, шаблон и ресурсы не меняются, ёмкость
не освобождается; reset не участвует. Права те же, что у `stop`/`start`:
master — только свои workers, оператор с правом управлять роем — любой
актор. Порядок проверок до любого эффекта:

1. Актор работает и согласован. Остановленного `update` не поднимает:
   намерение stopped меняет только `start`, и тот сам ставит текущий набор;
   отказ называет `start`.
2. Проход роя, аренда `dispatch` (своя тоже, как у stop/start), landing и
   workspace reservation дают отказ с причиной (#272), без вызова гостя.
   Пока рой актора идёт проходом (running или waiting), `update` любого его
   актора — отказ: шаг, который станет pending для роли актора во время
   перезапуска (ответ оператора на human-узел, переход графа), диспетчер
   закрыл бы отказом «role has no live bound actor», а перезапуск с
   загрузкой набора и ожиданием readiness идёт минуты. Шаг в работе у
   самого актора отказ называет: pending узла, чья роль привязана к этому
   поколению, или attesting, delivering, inflight и unconfirmed этого
   поколения — номер шага, узел и состояние; иначе отказ называет рой.
   Завершённый проход и остановленный рой актора не держат: освободить
   актора — дождаться конца прохода или остановить рой (`bro swarm stop`).
3. У сервера есть проверенный манифест артефактов (`BROOD_ARTIFACTS_DIR`):
   без него bootstrap #184 откажет при старте, и CT останется
   остановленной.
4. Root гостя по session RPC `guest_release` читает только ссылку
   `/opt/brood/bin` и называет `releases/<id>`. Набор, о котором гость не
   сообщил, — отказ с причиной, без догадки и без перезапуска: runtime до
   #133 отвечает unsupported и не отличает CT с bootstrap #184 от CT
   прежнего шаблона, а та после выкладки с другими артефактами не
   стартует. Тот же отказ дают недоступный relay, отказ чтения и ответ не
   по форме. Runtime, который сообщает набор, приносит разовый `stop` и
   `start`, но только CT из шаблона с bootstrap #184; CT прежнего шаблона
   после выкладки, изменившей артефакты, останавливать нельзя
   ([PROXMOX.md](PROXMOX.md), «Обновление гостевых бинарей»). Плоский
   `bin` bootstrap до #184 — тоже отказ: перезапуск такой CT набор не
   поставит.
5. Тот же id, что у сервера, — no-op: CT не перезапускается, повтор
   `update` безопасен. Намеренный перезапуск CT на том же наборе — `stop`
   и `start`.

Принятие (`accepted`) — записанное намерение с UPID остановки, а не
готовность гостя; ответ называет id до и после и говорит, что шаблон и
ресурсы профиля не меняются. Stop, отказавший до записи (чтение владения,
явный 403), PVE не получал: это тоже принятие, ответ называет остановку
ещё не запрошенной и последний отказ, и reconcile запрашивает её каждым
проходом (#275). Без UPID после возможной записи (5xx, разорванное
соединение) или если UPID принятой остановки не удалось записать, исход
`unknown` (оператору — 409 с `X-Brood-Command-Outcome: unconfirmed`, гостю
— `OK=false`): намерение сохраняется, не повторяется само и запрещает
другие изменения жизненного цикла до сверки. Пока идёт остановка, второй
`update`, `stop`, `start` и `reset` получают отказ.

После подтверждённой остановки актор в фазе `stopped` ждёт запроса Start:
его отправляет следующий проход reconcile со своим сроком, а не остаток
срока ожидания stop-задачи. Сбой до Start (чтение владения, digest или
статуса, недоступная конфигурация, явный отказ Start: 403 после отзыва
`VM.PowerMgmt`, расхождение владения) оставляет start ждать с причиной в
диагностике, и следующий проход повторяет его; сервер, остановленный между
подтверждением остановки и запросом Start, продолжает тот же start после
запуска. Запись bootstrap env — не Start: её неоднозначный исход (5xx,
разорванное соединение, остановка сервера посреди записи) тоже оставляет
start ждать, и следующий проход снова проверяет владение, digest и
остановленную CT и пишет то же содержимое через digest CAS. Подтверждённую
запись повтор не переписывает, пока digest конфигурации тот же, что после
неё. Перед отправкой Start фаза становится `provisioning`: потерянный ответ
Start или незаписанный UPID — неизвестный исход, и CT второй раз не
запускается.

Пока Start не запрошен, задачи update в PVE нет, и CT остановлена:
`stop` отменяет update (актор остаётся остановленным, desired stopped, без
vzstop), `delete` удаляет CT как остановленную, `reset` заменяет её без
vzstop. `start` и `update` получают отказ, называющий ожидание и последний
отказ Start. После отметки `provisioning` или неоднозначного Start `stop`,
`delete` и `reset` получают отказ, как при неизвестном исходе. Так же ждёт
обычный start остановленной CT (#275); отказ называет ожидание start, не
update: по записи их не различить. CT ждущего start, запущенную мимо brood,
reconcile принимает без записи в PVE (#277): Start не отправлялся, владение
проверено наблюдением, и `running` публикует только проверка готовности,
как у `start` работающей CT.

Stop-стадия (`stop`, `delete`, `reset`, `update`) так же отличает отказ до
записи от неоднозначной (#275). Stop, отказавший на чтении владения или
явным 403, оставляет стадию ждать в фазе `running` с причиной, и следующий
проход снова наблюдает CT: работающая получает Stop, перед отправкой фаза
снова становится `stopping` (`deleting` у delete), и потерянный ответ Stop
остаётся неизвестным исходом. Пока Stop ждёт, no-op — только повтор того же
намерения: `stop` при ждущем stop, `delete` при ждущем delete. Остальные
изменения получают отказ, называющий ожидание, в том числе `stop` при ждущей
остановке `update` или `reset`: остановку уже ведёт другое намерение, и
следующее изменение ждёт саму остановку. Такой актор для роя не работает
(`docs/MODEL.md`, «Привязка ролей»): роль ему не привязывается и не
разрешается, запуск роя отказывает, а `status.state` API — остановка
(`ACTOR_STATE_SUSPENDING`, у delete `ACTOR_STATE_DELETING`), хотя `phase`
остаётся наблюдённой `running`. CT, найденную
остановленной, stop-стадия не останавливает: vzstop остановленной CT PVE
отвергает HTTP 500 «CT not running», который клиент считает неоднозначным;
остановка подтверждена наблюдением, `stop` сразу завершён, `delete` и
`reset` переходят к удалению.

Намерение stop-стадии записывается как «Stop не запрошен» (#277): сервер,
остановленный между записью и отправкой Stop, следующим проходом
отправляет его, а не оставляет исход неизвестным. CT такой стадии проход
ещё не наблюдал, и отказ называет ожидание остановки, не утверждая, что CT
работает: она могла остановиться или исчезнуть мимо brood. Delete-стадия
`delete` и `reset` устроена так же. Delete, отказавший до записи, ждёт в
фазе наблюдённой `stopped` с причиной, следующий проход снова наблюдает CT
и отправляет Delete один раз; перед отправкой отметка снимается, и
потерянный ответ Delete или незаписанный UPID остаются неизвестным
исходом. Пока Delete ждёт, no-op — только повтор того же намерения:
`delete` при ждущем delete. Остальные изменения получают отказ, называющий
ожидание удаления: `stop`, `start`, `reset` и `update`, а при ждущем
удалении `reset` и `delete`, ведь удаление уже ведёт другое намерение.
`status.state` — удаление (`ACTOR_STATE_DELETING`) у delete. CT, которую
запустили мимо brood, пока Delete ждёт, не удаляется работающей: стадия
возвращается к ждущей остановке той же операции, проход шлёт ей один Stop
и потом Delete. Если CT запустили уже после наблюдения прохода, PVE
отвергает Delete ответом HTTP 500, и исход, как у любого неоднозначного
ответа, неизвестен. CT, найденная отсутствующей, кончает очистку без
Delete, а закрытие стадии и освобождение аллокации фиксируются одной
транзакцией.
Delete-стадия без отметки, в том числе записанная сервером до #277, не
повторяется: её Delete мог уйти. Отметка — состояние, а не ошибка: в
`status.errorMessage` и отказах её нет, только причина последнего отказа.

## Доставка и координация

`send(to, message, wait_seconds=0)` адресует другого managed-актора того же
роя. Отправителя задаёт сервер. Максимальное ожидание — 300 секунд; это
ожидание квитанции/idle, а не текста ответа. Без ожидания простоя гость
адресата ждёт квитанцию доставки до 15 секунд ([PROXMOX.md](PROXMOX.md),
«Приём сообщений в госте»). Ответ актора — новый `send`.

Только совпавшая квитанция подтверждает доставку. `submitted; delivery
unconfirmed` не означает ни успех, ни гарантированную потерю. Повтор может
создать дубликат. Idle не доказывает доставку или выполнение задания.
Операторское сообщение помечается `operator:<username>` и не выдаётся за
адрес актора; обратного операторского inbox в этой реализации нет.

`dispatch` требует `to`, сообщение и `request_id`; `to` называет worker,
добавленного вызывающим master (#267). Сервер сначала атомарно
занимает allocation, затем отправляет задачу. Request ID связан с исходным
текстом; повтор не отправляет его заново и не оживляет освобождённую аренду.
Неизвестная доставка сохраняет аренду. Она не доказывает чистоту клона и не
передаёт Git credentials человека.

```sh
bro --guest dispatch worker "Run the project tests" --request-id task-1
bro --guest dispatch worker --request-id task-1 --action show
bro --guest dispatch worker --request-id task-1 --action release
bro --guest landing --action take --request-id integration-1
bro --guest landing --action give --request-id integration-1
```

Аренды и landing хранятся в SQLite, связаны с UID/поколением, человеком и
проектом/роем. У них нет автоматического force-steal или expiry. Перед
остановкой, запуском, удалением, reset, update и очисткой workspace активную
координацию нужно явно освободить. Администратор может выполнить точное
восстановительное release/give по request ID; это не impersonation master
и не новая отправка.
Отказ жизненного цикла или управления сессией из-за координации называет
request ID, держателя и цель аренды именами акторов роя и команду
освобождения (`dispatch --action release` или `landing --action give`,
#272). Держатель другого поколения или роя и удалённый актор названы
unknown, и освободить такую аренду отказ предлагает администратору; claim
другого роя не описывается. Человека и хеша задачи в отказе нет.
Аренду на чужого актора, взятую до #267, правило владения не снимает: ни
одна задача в работе не обрывается молча. Держатель по-прежнему видит и
отпускает свой точный request ID, повтор `send` к чужому актору получает
отказ владения без новой отправки. Без держателя аренду отпускает
оператор: `dispatch --action show` показывает request ID, затем
`--action release` с ним. Владелец worker чужую аренду не отпускает:
задачу держателя с актора снимает человек.
Human-оператор не может выполнять dispatch send или landing take без
managed actor identity.

Workspace mutations атомарно занимают отдельную reservation в том же SQLite
journal. Она исключает новый dispatch, landing и конфликтующий lifecycle на
всё время RPC. Подтверждённое завершение освобождает reservation; неизвестный
исход сохраняет её и сообщает operation ID. После exclusive restart сервера
незаконченные reservation становятся unconfirmed, но не освобождаются.
Администратор сначала проверяет workspace и затем может выполнить явный
`dispatch --action release` с точным operation ID. Inflight reservation
освобождать нельзя. Это восстановление разрешения на последующую работу,
не доказательство того, что предыдущий эффект не произошёл.

Landing — advisory-токен всего проекта, не разрешение GitLab merge/push.
Проверка SQLite и внешнее RPC не являются одной распределённой транзакцией.
Неизвестные исходы требуют сверки, а не автоматического повторения.

### Дочерние задачи

`child_*` исполняются только гостевым путём; оператор не выдаёт себя за actor.
Parent identity берётся из relay. `parent_sequence` и `parent_request_id`
выбирают только точную попытку этого вызывающего актора в его рое и проходе;
`request_id` ребёнка — 1–128 ASCII букв, цифр, `_` или `-`. Task — непустой текст
до 4096 байт, report — до 16384 байт по прежним правилам actor report. Родитель
создаёт ровно объявленный `total` (1–64), одинаковый во всех create. Mode/quorum
задаёт actor-узел снимка графа прохода: `childJoin: {mode: any}` или
`childJoin: {mode: quorum, quorum: 2}`. Без policy/mode действует all. Quorum должен
быть от 1 до total. Прежние аргументы create `mode` и `quorum` принимаются ради
совместимости, но игнорируются: гость не переопределяет policy узла. Оставшиеся
обязательства всегда retain; аргумента автоматической отмены нет.

```sh
bro --guest child create --parent-sequence 5 --parent-request-id PARENT --request-id tests --role tests --task "Run the project tests" --total 2
bro --guest child create --parent-sequence 5 --parent-request-id PARENT --request-id review --role review --task "Review the change" --total 2
bro --guest child get --child-id CHILD
bro --guest child join --parent-sequence 5 --parent-request-id PARENT --wait-seconds 15
bro --guest child complete --child-id CHILD --request-id tests --outcome success --report "Tests passed; result is on the task branch"
```

Первые create идут от родителя, complete — от адресованного worker. Роль
планирования — явная привязка человека плюс действующая admin-делегация master;
просто role binding полномочий не даёт. Это dispatcher roles path: допускается
worker оператора, привязанный им к роли. У raw `dispatch` остаётся ограничение
на workers, добавленных вызывающим master; child task не выдаёт родителю
lifecycle/session-control прав на worker оператора.

Разные роли на одном worker не означают параллельную ёмкость: FIFO держит на нём
не больше одной running child task, остальные ждут. Lifecycle, workspace control,
новая конфликтующая автоматическая координация отказывают, пока есть обязательства.
Явный owner/admin Stop или session control разрешены с журналом вмешательства и
сохранением uncertain эффектов; parent нельзя завершить generic
`pipeline_visit_complete` в обход join.
Readiness `ready_success` при any/quorum — не разрешение продвинуть parent при
`open>0`. `joined=true` означает подтверждённое продвижение этим вызовом; pending
ответ — bounded snapshot, а не обещание об отсутствии будущего результата.
Полные отчёты не собираются в ответ join: его frame остаётся bounded; оригиналы
читаются отдельно через get, агрегат хранится в отчёте graph step с явными
пометками сокращённых частей.

`child_create` принимает намерение (`accepted`), не обещает доставки. Фиксация
`sending` предшествует relay; квитанция даёт `delivered`, `notSent` — `not_sent`,
потерянный ответ — `unconfirmed`. Startup переводит незавершённый sending в
unconfirmed и не повторяет сеть. Точный create retry никогда не resend и не
восстанавливает cancelled задачу; при неопределённой доставке его `OK=false`,
outcome unconfirmed, и модель видит причину и сохранённое состояние. Нет надежды
на будущую дедупликацию #291. Неоднозначная ошибка записи/commit или отменённый
wait тоже возвращает unconfirmed, а не ложное «ничего не случилось». Прервать
ожидание join не означает отменить ребёнка.

Явный owner/admin abort неполной неисполненной группы — отдельный web endpoint
с CSRF, текущей web session и revision/confirm
([Model](MODEL.md), «Исполнитель дочерних задач»); дополнительной installation policy
нет. Панель показывает историю детей и подтверждённый abort. Автоматического
восстановления нет. Running/uncertain работа остаётся до настоящего отчёта либо
отдельной сверки. Здесь описан исходный #289 для постоянных workers, не более
поздние ephemeral #292 или policy #290. Сверка внешних эффектов и возобновление
owner-прерванного исполнения пока не реализованы; живая приёмка #288 не заявлена.

## Приватная сессия

Сервер разрешает target по имени только внутри роя, сохраняет UID и
поколение и передаёт caller identity сам. Session RPC идёт по отдельному
ограниченному SSH-каналу `brood-session-rpc-v1`, а не через произвольный exec,
URL или actor-owned socket path.

Root запускает фиксированный helper UID/GID 1000 с NoNewPrivs, очищенными
capabilities и фиксированным окружением. Только helper открывает реестр и
сокеты Claude. Он проверяет peer PID/UID, process-start identity, CWD,
config home, foreground TTY и точный PID/start/epoch текущего PTY child. История читается из фиксированного корня
без symlink traversal; неполная строка остаётся pending, слишком большая
или неверная запись даёт notice. История ограничена 8 MiB prefix scan и
явно сообщает partial/reset.

`session_terminal` — screen-snapshot, не lossless PTY stream. `open` выдаёт
случайный caller-bound `tid`; mode по умолчанию ro, writer один. Последующие
операции используют возрастающий `seq`, начиная с 1. Последний одинаковый
повтор возвращает прежнюю квитанцию без повторного ввода; изменённый payload
с тем же seq отвергается. Неизвестная запись отключает writer. Cursor —
непрозрачная строка снимка, `read --wait` ограничен 15 секундами, `data` —
буквальный UTF-8 ввод до 4096 байт, не base64. `close` отсоединяет только
подключение, не останавливает Claude или PTY holder. Disconnect уничтожает metadata.

Максимум четыре живых подключения, idle TTL 60 секунд, writer TTL 30 секунд.
Закрытые TID не занимают эту квоту; bounded metadata cache (до 64 записей)
сохраняет close replay до TTL либо вытеснения старейшего закрытого TID. Вытеснение
не открывает TID заново и не разрешает повтор ввода; активные writers не вытесняются.
Slash и workspace mutations используют тот же writer gate. Белый список
slash: `/model`, `/clear`, `/compact`, `/rc`, `/status`, `Escape`; текст с
управляющими символами или произвольными аргументами не превращается в shell.
Ввод `/model` не является доказательством выбора конкретной модели.

`stat` читает bounded project/subagent transcripts, дедуплицирует usage по
message identity и не приписывает затраты человеку по имени актора. Это не
вечный биллинг: удалённые transcripts недоступны, неполные сканы отмечаются.

## Граница полномочий и протокол

```text
Claude -> bro --guest mcp (UID 1000)
       -> /run/brood/swarm.sock (root:1000, 0660)
       -> supervisor -> аутентифицированный relay
       -> сервер: текущие identity/generation/swarm/delegation
       -> relay получателя -> fixed helper UID 1000 -> Claude/PTY/transcripts
```

Broker проверяет SO_PEERCRED, держит exclusive lock в root-owned каталоге и
не принимает credentials/UID/endpoint от модели. Старый caller после
reconnect не используется. Legacy agents/add/send envelopes поддерживаются
при переходе; canonical arguments с legacy полями не смешиваются. Запросы
и ответы relay ограничены 128 KiB; одновременно не более восьми RPC/IPC.
Машинные credentials остаются у root supervisor. Ключ CLIProxyAPI остаётся
на сервере; helper использует тот же fixed-loopback gateway, что исходная
Claude-сессия. Ttyd и Go PTY holder живут вне клона; только app wrapper
выбирает `/workspace/project`. Browser writer владеет вводом и размером PTY;
пока он подключён, конфликтующие input/resize и restart/recycle с остановкой
сессии получают отказ, без принудительного захвата. Это не меняет семантику
явных lifecycle stop/reset/delete всей CT. Чтение снимков и transcript доступно по прежним
правам. Приватный holder-сокет root-owned и не выбирается аргументами модели.

MCP tools-only `2025-03-26`: initialize, notifications/initialized, ping,
tools/list, tools/call. Ошибка возвращается с причиной и `isError: true`;
неподтверждённый исход не становится успешным выполнением команды. CLI
выходит ненулевым кодом при отказе/неопределённости. Операторский `bro`
(CLI и `bro mcp`) дописывает к статусу отказа `POST /api/commands/*` только
`reason` сервера (#276): строку UTF-8 до 1024 байт без управляющих
символов из тела до 4096 байт. `detail` и прочие поля тела недоверенные и
не показываются; без `reason` (сервер до #276, внутренний сбой) ошибка —
только статус, предупреждение о неподтверждённом исходе остаётся. Гость
(`bro --guest`) получает текст отказа через relay, как прежде. Долговечное принятие
lifecycle intent не объявляется завершённой очисткой или readiness.

Проверки используют временные SQLite/Git/transcript fixtures, настоящий
stdio-бинарник, Unix sockets и изолированный TLS/WSS/SSH relay. Они не
являются доказательством выкладки нового образа, живого PVE lifecycle или
успешной платной модельной задачи. Пользовательские master/worker не
перезапускаются для приёмки этой разработки.
