# brood

Пул агентов на [Agent Substrate](https://github.com/agent-substrate/substrate).
Сервер `brood` и пользовательский клиент `bro` — самостоятельные Go-бинарники.
Исходная React/Bun-панель в `web` встроена в сервер и расширена страницами
пользователей, прав, проектов и роёв. Python остаётся для инструментов разработки,
управления локальным Substrate и bootstrap изолированного workbench.

## Workflow роя

Рой объединяет акторов проекта для работы над общей задачей. Workflow описывает
порядок этой работы как ориентированный граф: узлы обозначают действия и решения,
а рёбра — переходы между ними. Узел `actor` описывает задание актору; узел
`human` задаёт точку, в которой решение остаётся за человеком. Например, после
анализа актором человек может принять результат или вернуть его на доработку.
Это модель процесса, а не гарантия автоматического исполнения.

Граф отделяет описание процесса от отдельного прогона. В нём заданы `start` и
`exit`, именованные узлы и направленные рёбра. `actor` связывает задание
(`prompt`) с шаблоном окружения актора (`template`); `human` содержит вопрос и
варианты ответа, каждый со своим исходом (`outcome`). Формат также описывает
`condition`, `land`, `parallel`, `fan_in` и `exit`, но наличие типа в схеме не
означает, что его действие исполняется. Список `goalGates` обозначает целевые
точки процесса; схема требует хотя бы одну, но сама по себе не обеспечивает её
прохождение при реальном исполнении.

Ребро связывает `from` и `to` и может задавать условие, подпись и вес. Для
выбора следующего шага модель сначала рассматривает первое совпавшее условное
ребро в порядке документа: условие сравнивает `outcome`, `preferred_label` или
`context.<имя>` с помощью `=`, `!=` и `&&`. Затем среди безусловных рёбер
учитываются предпочитаемая подпись, предложенный узел назначения, наибольший
вес и, при равенстве, лексикографический порядок назначения. Если подходящего
ребра нет, обход завершается ошибкой. Например, решение человека может выбрать
переход к завершению или к узлу доработки. Циклы допустимы, но входящих рёбер у
`start` и исходящих у `exit` быть не должно.

Предполагаемый жизненный цикл: автор описывает граф и проверяет его, затем
отдельный прогон проходит узлы от начала к выходу, при необходимости ожидая
решения человека и возвращаясь на доработку. Это направление развития, а не
описание доступного движка: сохранение состояния, возобновление, повторы,
параллельное исполнение и контроль целевых точек пока не предоставляются как
исполнение workflow в текущем `main`.

`Broodfile` объявляет проект, сборочные входы и шаблоны акторов. В необязательном
словаре `workflows` он также может содержать именованные графы с началом, выходом,
узлами, рёбрами и целевыми gates; ссылки на шаблоны относятся к тому же
Broodfile. Пример графа с актором и решением человека —
[`examples/Broodfile`](examples/Broodfile).

В текущем `main` реализованы локальная проверка, симуляция и отображение графа:

```sh
bro pipeline validate --workflow inspect examples/Broodfile
bro pipeline plan --workflow inspect examples/Broodfile
bro pipeline render --workflow inspect examples/Broodfile --dot
```

`plan` не запускает акторов и не спрашивает человека: симуляция считает узлы
успешными и выбирает первый вариант human gate. `render` поддерживает также
`--svg`. Без `--workflow` команды принимают отдельный документ конвейера.
Сборка и `bro push` не запускают workflow и не публикуют его для исполнения;
реальный запуск графа и обработку решений человека эти команды не предоставляют.
Отдельно от этого акторов можно создавать и использовать через возможности роя.
Подробнее о формате и сборке — [Build](docs/BUILD.md).

## Разработка

Нужны Python 3.12+ с venv, Go из `go/go.mod`, Git и Docker с buildx.

```sh
bin/brood dev setup
bin/brood dev web test
make -C go build
bin/brood dev test
make -C go fmt-check vet test
venv/bin/ruff check
```

`bin/brood` активирует venv своей рабочей копии. `brood dev setup` добавляет
в `.env` случайный `BROOD_SESSION_SECRET`, не печатая его. Go-бинарники
читают настройки из окружения, не загружают `.env` сами. Для локального
сервера экспортируйте настройки из своего доверенного `.env`:

```sh
set -a
. ./.env
set +a
go/bin/brood bootstrap-admin
go/bin/brood serve
```

По умолчанию сервер доступен только на `http://127.0.0.1:8080`.
Внешний адрес требует явной настройки TLS; новая SQLite-база создаётся
с текущей схемой при открытии, legacy данные не импортируются. Управление пользователями, проектами, членством и своими роями —
в панели и API. Администратор имеет доступ ко всем роям; член проекта не
видит чужие рои автоматически.

В другом терминале:

```sh
go/bin/bro login http://127.0.0.1:8080
go/bin/bro whoami
go/bin/bro build development
go/bin/bro push development --project my-workspace
go/bin/bro logout
```

Сборка читает текущий `./Broodfile` и рабочие файлы, использует внешний Docker/buildx
с OCI exporter; Git нужен для внешних pinned-источников и запрошенной Git metadata.
Обычная сборка сначала идемпотентно синхронизирует проект из Broodfile через
`bro login` сессию, затем сохраняет OCI-образ и шаблон локально. Repository
по умолчанию берётся из Git origin текущего проекта. `--plan`/`--export`
остаются офлайн. Отдельный `bro push` публикует готовый комплект через
авторизованный серверный API, но не запускает акторов. Подробности —
[Build](docs/BUILD.md), [Go](docs/GO.md), [Web](docs/WEB.md).

## Инструменты разработчика

```sh
bin/brood dev bug list
bin/brood dev bug show <iid>
bin/brood dev bug new "<title>" --label type::bug --body-file body.md
bin/brood dev bug start <iid>
bin/brood dev ci
bin/brood dev ci why <id>
bin/brood dev ci log <job>
bin/brood dev ci vars
bin/brood substrate install
bin/brood substrate start
```

Координаты трекера берутся из git origin, переопределения и `GITLAB_TOKEN` —
из `.env`. Секреты не коммитятся. Полная справка — `bin/brood` без аргументов.
Локальный Substrate — [Substrate](docs/SUBSTRATE.md), workbench —
[Workbench](docs/WORKBENCH.md), deployment и границы перехода со старой
установки — [Deploy](docs/DEPLOY.md). Правила разработки — `CLAUDE.md`.

Публичный `bin/brood deploy server` создаёт чистое приложение и нового
администратора из защищённых настроек релиза, проверяет вход и только затем
убирает старые Django/Postgres ресурсы. Переноса старых данных нет. Общий
Substrate, worker pools, provider credentials и пользовательские акторы
не пересоздаются.
