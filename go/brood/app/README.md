# brood/app — прикладная авторизация (#31)

Прикладной слой проектов, членства и роёв поверх хранилища и провайдера
atespace'ов. Реализует правила доступа эпика #27 и операции #31.
Пакет молчит: данные и ошибки возвращает, печатает только внешний слой
(HTTP API, CLI).

## Состав

- `store.go` — типы `User`, `Project`, `Membership`, `Swarm`,
  `SwarmState` и интерфейс `Store`, который реализует хранилище #29
  (таблицы users, projects, project_members, swarms, swarm_members) через
  адаптер. Интерфейс минимален: только то, что нужно прикладному слою.
- `service.go` — `Service` с зависимостями: `Store`, `Provisioner`
  (граница Substrate, реальный адаптер — #32), `Clock` (UTC) и `IDGen`
  (строковые ULID/UUID).
- `authz.go` — `Can(user, action, resource)`: действия `view-project`,
  `create-swarm`, `view-swarm`, `manage-swarm`, `delete-swarm`,
  `transfer-ownership`, `manage-swarm-acl`, `manage-users`, `manage-projects`,
  `manage-membership`; ресурсы — проект или рой по ID.
- `swarm_acl.go` — явные роли owner/editor/viewer, чтение, выдача и отзыв
  grants. Запись повторно проверяет права внутри транзакции адаптера.
- `operations.go` — `CreateProject`, `AddMember`, `RemoveMember`,
  `SetUserDisabled`, `CreateSwarm`, `DeleteSwarm`, `TransferSwarm`,
  `GetSwarm`, `ListProjectsFor`, `ListSwarmsFor`, `AdminProjects`,
  `AdminSwarms`.
- `errors.go` — ошибки-значения (`ErrNotAllowed`, `ErrNotFound`,
  `ErrExists`, `ErrConflict`, `ErrState`), отображаются статусами HTTP
  или текстом CLI, без трассировок.

## Правила доступа

- Заблокированный пользователь всегда отказан, включая администратора.
- Активный администратор управляет пользователями, проектами,
  членством и всеми роями, кроме deleted.
- Активный администратор видит проекты и создаёт рои без членства;
  обычному пользователю для этого требуется членство в проекте.
- Доступ обычного пользователя требует и явной роли в рое, и членства
  в его проекте. Членство само по себе чужие рои не открывает.
- viewer читает рой; editor также управляет нагрузкой; owner дополнительно
  управляет ACL, удаляет рой и передаёт владение. Список роёв включает только
  явные grants, кроме администратора, которому доступны все.
- Исключение из проекта отзывает доступ, но не удаляет рои и grants.
- `manage-swarm` разрешает изменять нагрузку и открывать записывающий терминал,
  `manage-swarm-acl` — изменять локальные grants. Изменения и передача требуют
  `active`; owner также удаляет `error`. Просмотр разрешён всем состояниям,
  кроме `deleted`. Native policy остаётся отдельным ресурсом только для admin.
- Хотя бы один owner сохраняется атомарно. `owner_id` временно показывает
  одного из owner для совместимости, но не является источником полномочий.
  Передача снимает grant прежнего основного владельца и выдаёт новому.
- HTTP-представление ACL и разделение read/write операций — следующий слой #49.
- Защита последнего активного администратора — слой #30, здесь не
  проверяется.

## State machine роя

```
provisioning -> active | error
active       -> deleting | error
deleting     -> deleted | error
error        -> active | deleting | error | deleted
deleted      — терминальный, строка остаётся со state=deleted
```

Сбой Substrate — не отказ вызова, а состояние: строка роя получает
`state=error` и поле `Retry` (`create`/`delete`); повтор того же вызова
доводит операцию до конца. `CreateSwarm` идемпотентен по имени в
проекте: незавершённое создание того же владельца продолжается, чужое
имя — отказ. `DeleteSwarm` идемпотентен и сверяет имя atespace
по сохранённому UID; чужая одноимённая область не удаляется и не
присваивается (путь reconcile: `GetAtespace` перед `CreateAtespace`). Если UID
не сохранён, существующий namespace не присваивается автоматически: нужна
операторская проверка. Параллельное создание сериализовано внутри проекта;
после ожидания права перепроверяются. Уникальность действующих имён защищена
SQLite; конфликт вставки возвращает собственный завершившийся запрос, но не
чужой рой. Deleted tombstones не занимают имя нового роя.

`atespace_name` строится только из ID роя:
`swarm-<id без дефисов, lower>` (`AtespaceName`), пользователь не может
подменить область через payload.

## Ёмкость шарда (#48)

`ShardCapacity` задаёт обязательные worker labels и nullable int64-пределы
роёв, акторов, CPU в millicores и памяти в bytes. Nil означает отсутствие
ограничения, zero — запрет резерва. `ShardUsageFromRecords` считает все
неудалённые рои и переданные резервы их акторов, независимо от running/suspended;
отрицательные значения и переполнение отвергаются. Второго счётчика в базе нет.

`CreateSwarm` проверяет свободный слот до записи и native provisioning;
администратор квоту не обходит. Повтор собственного существующего имени не
занимает новый слот. Gateway повторяет проверку и вставку в одной транзакции
хранилища, в том числе для конкурирующих соединений SQLite.

`AdmitWorkload` — граница для доверенного native-адаптера: `Prepare` получает
записи роёв и возвращает актуальные резервы и предлагаемую операцию. Для
обновления/resume резерв прежнего актора заменяется, не складывается с новым.
`Apply` вызывается только после проверки лимитов и селектора, с повторной
проверкой manage-swarm после чтения native-состояния. Если предел снижен ниже
расхода, неизменные и сокращающиеся резервы допускаются, рост — нет. Новый
расход не блокируется из-за уже превышенного несвязанного предела, который
операция не увеличивает.

Адаптер обязан разрешить реальные лимиты из native template, включить
pending golden actor до асинхронного создания и не считать его второй раз
после появления; ошибки чтения не заменяются нулевым расходом. Apply сохраняет
native UID/version предусловия. Блокировка проекта действует от Prepare до
окончания Apply в одном процессе сервера; распределённая блокировка нескольких
экземпляров сервера не заявляется. Подключение native/HTTP actor и template
маршрутов, включая выдачу ошибок и настройки ёмкости, относится к #49; один
вызов чистой проверки сам по себе не ограничивает прямые операции Substrate.
